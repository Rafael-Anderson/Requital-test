# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Requital — a multi-tenant e-commerce "shop manager" SaaS (Salla/Zid/Dukan-style), built for UAE/Gulf florists and gift shops. Three independent apps in one repo, sharing nothing but the HTTP boundary:

- `backend/` — NestJS + MySQL (raw `mysql2`, no ORM — see "Database access" below for why), the single source of truth for both frontends. Well past Phase 1 now: auth/roles, products (with variants, ingredients, attributes, FAQs), categories, collections, orders (kanban + draft orders + returns/refunds + post-purchase survey), outlets, delivery zones, discounts, affiliates, bio-links, dashboard/reporting, search, audit log, theme/SEO settings, WhatsApp integration, and payments (Stripe live, five more gateways stubbed behind the same interface). See "Backend architecture" below for the module roster.
- `admin/` — Next.js Admin Panel (merchant-facing). Login/signup, sales dashboard, order management (kanban + history), inventory (products/categories/ingredients/stock movements), collections, discounts, draft orders, bio-links, affiliate program, reports, activity log, and multi-tab settings (business info, outlets, users, payments, theme, SEO). See "Admin frontend" below.
- `storefront/` — Next.js Storefront (customer-facing, per-shop branding, resolved via a `/[shop]/...` slug in the path — see "Storefront frontend" below). A real app: product browsing with theme-driven homepage layouts, cart, checkout, collections pages, bio page, order tracking.

**Spec docs**: `BUILD_BRIEF.md` at the repo root is the original entry point and points to `REQUITAL_SRS.md` as the full source-of-truth spec (Section 6 has the data model). The SRS is not currently present in the working tree — if it's missing, note that rather than guessing at requirements from memory. Per the build brief, the SRS also specifies things not yet built: i18n + Arabic/RTL and multi-currency (single-currency AED throughout today) — the current implementation is a simpler, shipped-first version of that spec, not a divergence to "fix." Multi-outlet, the Kanban order pipeline, unlimited-depth attributes/variations, and a Customers module, all listed in the SRS as future/Phase-2+ work, **have since been built**. The SRS's separate-top-level-domain-per-merchant plan for the storefront was also **not** what got built — tenant resolution is a `/[shop]/...` slug segment instead (see "Storefront frontend"). Don't treat any of the above as still-pending.

**Other reference docs**, both currently un-linked from anywhere else in this file: `docs/runbook.md` (backup/restore via `tools/backup-db.sh`, plus a migration-by-migration rollback reference) is the one to check before any destructive DB operation. `docs/audit-2026-08.md` is a full verification sweep (auth lifecycle, background jobs/scheduling, file storage, cookie consent, database, checkout/inventory integrity, SEO, observability, security headers/deps, cross-shop isolation) with a consolidated findings list — check it before assuming an area is unaudited.

## Git workflow — branch protection is on

As of the Phase 2 CI pipeline merging to `main` (2026-08-05), `main` has branch protection enabled: PRs are required, and the four CI jobs (`backend`, `admin`, `storefront`, `guardrails` — see `.github/workflows/ci.yml`) are required status checks. **Direct pushes to `main` no longer work at all** — they will be rejected by GitHub, not just discouraged by convention. Do not attempt to push directly to `main` in any session; do not merge PRs yourself even once CI is green — merging is the user's call.

## Tenant isolation and outlet scoping

Every tenant-owned table carries `shopId`, and every query against one is scoped by it at the data-access layer — no code path may return one shop's data to another. This is no longer a hardcoded constant: real merchant auth exists, and every request derives `shopId` (and, for outlet-scoped resources, `outletId`) from the authenticated user, re-read from the DB on every request.

- **`AuthGuard`** (`backend/src/auth/guards/auth.guard.ts`) verifies the JWT, then re-fetches the user from the DB (not trusting token claims for role/outlet) and attaches a `TenantContext` (`backend/src/common/tenant-context.ts`: `{ userId, shopId, role, outletId: number | null }`) to the request, injectable via the `@CurrentUser()` decorator. Re-reading on every request means a role change, outlet reassignment, or account deletion takes effect immediately rather than waiting out the token lifetime.
- **`RolesGuard`** + `@Roles(...)` gates endpoints by role. Both guards are wired as `APP_GUARD` providers in `AuthModule`; routes are protected by default and opt out with `@Public()`.
- **Four roles**: `admin` (full shop access, all outlets, aggregated dashboard), `branch` (pinned to exactly one outlet, `outletId` is never null — see `resolveOutletFilter` below), `order_manager` (shop-wide but scoped to the Orders/Draft Orders domain only — no pricing, catalog, or settings access), and `viewer` (shop-wide read-only — reports, orders, customers, no mutations anywhere). `order_manager`/`viewer` are additive on top of the original admin/branch split and are *not* outlet-pinned. Signing up always creates a Shop + a default Outlet + an Admin user in one `$transaction` (`AuthService.signup`). Only admins can create branch/order_manager/viewer accounts.
- **`resolveOutletFilter(ctx, requestedOutletId?)`** (`backend/src/common/outlet-scope.ts`) is the single shared helper encoding the branch-override rule: a `branch` user's `ctx.outletId` always wins regardless of what the request asked for; an `admin` gets the requested outlet or `undefined` (no filter = all outlets). Every outlet-scoped read/write (orders, stock, dashboard) routes through this helper — do not hand-roll the branch/admin distinction elsewhere. `outlets.service.ts` has a documented gotcha: don't build the `where` clause as `{ id, shopId, ...(role==='branch' && { id: ctx.outletId }) }` — the spread silently overwrites the requested `id` last, turning "reject mismatched outlet" into "silently substitute my own outlet." Check `id !== ctx.outletId` explicitly instead.
- **Unverified `outletId` for a stock write — a bug class that recurred twice, now caught by a structural guardrail.** `confirmImportIngredients` and (independently) `confirmImportProducts` both took a query-param `outletId` and used it directly for `outletstock`/`outletingredientstock` upserts and `stockmovement` creates with no check that the outlet actually belongs to `ctx.shopId` — an admin from Shop A who knew/guessed an outlet id belonging to Shop B could write stock/movement rows into it. Fixed (2026-08-04) by adding an `outlet.findFirst({ id: outletId, shopId: ctx.shopId })` check before either transaction runs, matching the pattern every *other* outlet-taking write in these files already followed (`setLowStockThreshold`, `transferStock`, order creation's outlet re-verification, etc.) — this was two isolated omissions in an otherwise-consistent codebase, not a missing pattern. `node tools/check-outlet-scoping.js` is a grep-based guardrail (same philosophy as `check-page-width.js`) that flags any backend service method taking an `outletId` parameter with no adjacent ownership-check marker in its body — run it after adding or editing any method that accepts an outletId; it has a documented `ALLOWLIST` for genuinely-safe cases (private helpers only ever called with an already-verified outletId, or read-only queries where a foreign outletId can only match zero rows).
- **Catalog vs. stock split**: Products/Collections stay shop-scoped (one shared catalog across all of a shop's outlets). Stock does not — `product.stockQuantity`/`lowStockThreshold` were removed from `Product` entirely and moved to the `outletstock` join table (composite PK `[outletId, productId]`). `trackInventory` (whether a product is stock-tracked at all) stays on `Product` since it's a catalog-level policy, not a per-outlet count. `GET /products` returns `stockQuantity: null` (not `0`) when no outlet is resolved (e.g. an admin viewing "all branches" without picking one) — that's distinct from a genuine zero-stock outlet.
- **Orders are outlet-scoped**: `order.outletId` is a required FK. On create, a branch user's `outletId` is always forced server-side to `ctx.outletId` — any `outletId` they supply in the body is silently ignored, never honored. Admins may specify one.
- **Security regression suite**: `backend/test/security-outlet-isolation.e2e-spec.ts` is the living proof this holds — it spoofs `outletId`/order ids across outlets and across shops (branch user, admin, and cross-tenant) on every outlet-scoped endpoint and asserts each either silently re-scopes or 404s, never leaks. Run it (`npm run test:e2e -- security-outlet-isolation`) after touching any tenant- or outlet-scoped query path; it already caught one real bug (the `outlets.service.ts` spread-overwrite above) that reasoning-only review missed.

### Branch-specific roles — a permission layer on top of the 4-tier system

A per-`(user, outlet)` override that can *restrict* (never grant more than) a staff member's shop-wide role at one specific outlet — e.g. a shop-wide `admin` can be knocked down to view-only at Branch B while staying full-access everywhere else. This is additive: a shop that never assigns an override sees zero behavior change anywhere.

- **Two models**: `branchrole` (shopId, name, `permissions` — a JSON array of a fixed vocabulary, not free-form strings) is an admin-defined bundle; `useroutletrole` (userId, outletId, branchRoleId, unique per user+outlet) points a specific staff member at a specific outlet to one of those bundles.
- **The fixed permission vocabulary** lives in `common/permissions.ts` (`Permission` union — `orders.view`, `orders.manage`, `dashboard.view`, `products.view`, `products.manage_stock`, `ingredients.view`, `search.use`, `outlets.view_own`, `delivery_zones.view`, `payments.generate_link`) alongside `basePermissionsFor(role)`, a static map of what each of the 4 existing tiers already implies in that vocabulary.
- **The actual security guarantee is an intersection, not a convention**: `BranchRolesService.resolveEffectivePermissions(ctx, outletId)` (`branch-roles/`) returns `null` when no override row exists for that `(user, outlet)` — callers must fall through to their existing `ctx.role`-based logic untouched. When an override *does* exist, the effective set is `intersection(basePermissionsFor(ctx.role), branchrole.permissions)` — this is what makes an over-generous or spoofed assignment structurally incapable of granting more than the user's shop-wide ceiling, rather than relying on the admin UI to prevent it. `assertPermission(ctx, outletId, permission)` is the thin wrapper every call site actually invokes, throwing `ForbiddenException` only when an override exists and lacks the permission.
- **Wired into every outlet-scoped read/write** across orders, products (catalog + stock), dashboard, ingredients, payments (`generateLink`), search, delivery-zones, and outlets — deliberately *not* draft-orders/reports/scan, since today's `'branch'` role can't reach those controllers at all (revisit if that ever changes). Two resolution rules matter when adding a new call site: **list/aggregate endpoints** (an admin viewing "all branches", `outletId` unresolved) skip the check entirely — overrides never affect aggregate views, only a concretely-scoped one; **single-resource endpoints** (a specific order, outlet, etc.) must check against the *fetched resource's own* `outletId`, not the pre-fetch query filter — an admin's filter is `undefined` by default, but the resource itself always belongs to one real outlet.
- **Staff management got real update/delete for the first time** here (`PATCH`/`DELETE /auth/users/:id` — previously create-only via `POST /auth/branch-users`), with self-edit blocked (use profile settings instead), last-remaining-admin demotion/deletion blocked, and deletion blocked (409) if the user has existing audit-log/note/stock-movement/return history (those FKs have no cascade, by design — a departed staff member's history isn't silently reassigned or orphaned).
- `backend/test/branch-roles.e2e-spec.ts` is the pattern to extend for adversarial coverage: cross-shop spoofing on every new endpoint (assign/branchrole CRUD), and — the one that actually matters — a real HTTP-level "permission escalation" test proving an over-generous branch-role assignment on a shop-wide `viewer` still can't unlock `orders.manage`.

**`npm run build` (`nest build`) can silently emit nothing at all if `dist/` was ever deleted out from under a stale incremental cache** — found for real during PR #32's deploy (2026-08-15): `nest-cli.json`'s `deleteOutDir: true` wipes `dist/` before compiling, but `tsconfig.json`'s `incremental: true` tracked its `.tsbuildinfo` cache at the *project root* (`tsconfig.build.tsbuildinfo`), outside `dist/` — so after a `dist/` wipe, tsc consulted a cache that still believed every file was already up to date and emitted zero output, while both `nest build` and a raw `npx tsc -p tsconfig.build.json` still reported exit code 0. pm2 then failed to start with `Cannot find module '.../dist/main.js'`. Fixed by pointing `tsconfig.build.json`'s `tsBuildInfoFile` at `./dist/tsconfig.build.tsbuildinfo` instead — the cache now lives inside `dist/` and gets wiped together with it on every build, so this can't recur. If a build ever again reports success but `dist/main.js` is missing, `rm -rf dist backend/tsconfig.build.tsbuildinfo` (the old stray root-level file, if a pre-fix checkout ever recreates it) and rebuild.

Migrations are hand-authored plain MySQL DDL (`prisma/migrations/*/migration.sql`, one timestamped folder per migration). The directory name is a holdover from this backend's pre-2026-08-11 Prisma-based incarnation — see "Database access" below for why Prisma was removed entirely — kept as-is rather than renamed, since every migration folder's *content* was already plain SQL with zero Prisma-specific syntax even before the ORM was removed, and a rename would have bought nothing:

```bash
npm run db:migrate                           # applies any pending migration folders (scripts/migrate.ts)
npm run db:seed                              # seeds the dev shop/admin/starter products (scripts/seed.ts)
```

Make the timestamped folder under `prisma/migrations/` by hand and write `migration.sql` yourself (expand/contract for anything that backfills: add nullable column → backfill via `UPDATE ... JOIN` → tighten to `NOT NULL` → add FK/index). `scripts/migrate.ts` applies every folder containing a `migration.sql`, in filename (timestamp) order, tracking applied folders in a plain `_migrations` table (one row per folder name, created on first run) — a straight mysql2 replacement for `prisma migrate deploy`, no shadow database or generated client involved at any point.

**A hand-authored migration's folder timestamp is the only thing enforcing its position in the apply order — nothing checks that a migration's own SQL only references tables/columns created by an earlier-timestamped folder.** Found for real (2026-08-05, CI Phase 2, back when this ran through `prisma migrate deploy`): `20260723140844_add_outlet_hours_delivery_coords` ran an `ALTER TABLE outlet ...` timestamped *before* `20260723150000_merchant_auth_and_outlets`, the migration that actually `CREATE TABLE outlet`s — invisible against the long-lived local dev database (which had picked up the columns some other way over time) but fatal the first time migrations ever ran against a genuinely clean database, in that session's new CI pipeline. Fixed by emptying the mis-ordered migration to a no-op (left in place, not deleted — every existing database already had it recorded as applied) and moving its real SQL verbatim into a new correctly-ordered folder (`20260723150001_outlet_hours_delivery_coords`, timestamped right after outlet's own creation). This is the general fix pattern for any future out-of-order migration found the same way — don't edit an already-applied migration's SQL in place, add a new correctly-ordered folder instead. Since this bug class is only detectable by actually applying every migration to an empty database in order, and the local dev DB never gets rebuilt from scratch, CI's `db:migrate` step against a fresh service-container database (see `.github/workflows/ci.yml`) is the only thing that exercises this — treat a migration failure there as this bug class, not a flake.

`backend/.env` holds `DATABASE_URL` (MySQL), `JWT_SECRET`, `CREDENTIAL_ENCRYPTION_KEY` (encrypts per-shop payment/WhatsApp credentials at rest, see `common/crypto.ts`), `ADMIN_ORIGINS` (comma-separated CORS allowlist for the admin frontend's origin(s)), `ADMIN_URL`/`STOREFRONT_URL` (used to build reset-password/verify-email/invite links and payment-link URLs respectively), plus one platform-level fallback credential set per payment gateway (`STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`, `TELR_STORE_ID`/`TELR_AUTH_KEY`, `PAYTABS_PROFILE_ID`/`PAYTABS_SERVER_KEY`, `TABBY_PUBLIC_KEY`/`TABBY_SECRET_KEY`/`TABBY_WEBHOOK_SECRET`, `TAMARA_API_URL`/`TAMARA_TOKEN`/`TAMARA_NOTIFICATION_TOKEN`, `PAYPAL_CLIENT_ID`/`PAYPAL_CLIENT_SECRET`/`PAYPAL_WEBHOOK_ID`/`PAYPAL_API_URL`) used only when a shop hasn't configured its own — see "Payments use a strategy pattern" below. `RESEND_API_KEY`/`EMAIL_FROM_ADDRESS` are the same kind of platform-level fallback for real email sending — see "Email sending" below. `PLATFORM_WHATSAPP_PHONE_NUMBER_ID`/`PLATFORM_WHATSAPP_ACCESS_TOKEN` are the same shape again, but for a genuinely single-implementation feature (not a bring-your-own-keys fallback like the others): the one Requital-owned WhatsApp Business account that sends every shop's new-order merchant alert — see `common/whatsapp.ts`'s `sendPlatformWhatsAppAlertOrThrow` and "WhatsApp order alerts (platform-owned)" below. ### Checking lint delta without mutating files — tools/check-lint-baseline.js

Each app has its own `lint-baseline.txt` (a plain integer) tracking its accepted pre-existing lint debt — see the many dated `backend/lint-baseline.txt raised X → Y` entries later in this file for the format and reasoning every bump is expected to carry. To check whether a change introduced *new* debt, run from the repo root: `node tools/check-lint-baseline.js <backend|admin|storefront>` (this is also the exact command the `guardrails`/per-app CI jobs run, just with a `../` prefix from inside each app's own directory — see `.github/workflows/ci.yml`). ### e2e/ (Playwright, cross-app)

A separate `e2e/` package driving all three apps together through a real browser (Playwright/Chromium) — a foundation covering 4 critical paths (merchant onboarding, customer checkout, order kanban, password reset), not full coverage. Needs all three apps already running on their expected ports (backend :3000 first, then `npx next dev -p 3001`/`-p 3002` for admin/storefront — see the Port note above for why backend has to go first):

## Backend architecture

- **Database access is plain `mysql2`, not an ORM (migrated off Prisma 2026-08-11).** Prisma's Rust query engine crashed on Hostinger shared hosting — CloudLinux's per-account thread/process cap (LVE) couldn't accommodate the engine's own thread spawning, confirmed live via SSH, not a fluke. Prisma Accelerate (ongoing per-query cost past 60k ops/month) and the Rust-free driver-adapter engine (still a Prisma dependency, still capable of surprising a shared host the same way again later) were both evaluated and rejected in favor of removing Prisma entirely — zero native binary, zero ongoing cost, runs anywhere. **`DatabaseModule`** (`src/database/`) is `@Global()` the same way `PrismaModule` used to be — `DatabaseService` is injectable anywhere without re-importing the module, and wraps a `mysql2` connection pool with `.query<T>(sql, params)` (SELECT, returns rows directly), `.execute(sql, params)` (INSERT/UPDATE/DELETE, returns a `ResultSetHeader` with `.insertId`/`.affectedRows`), and `.transaction(async (conn) => {...})` (returns a `PoolConnection` whose own `.query()`/`.execute()` work the same way, for use inside the callback). `src/db/types.ts` has a hand-maintained `<Model>Row` TypeScript interface per table (scalar columns only, no relations — join results are typed inline or via `RowDataPacket` at the call site) — there's no code generation step anymore, so a schema change means updating this file by hand alongside the migration that changes the column. `src/database/upsert.util.ts`'s `upsert()` wraps the common `INSERT ... ON DUPLICATE KEY UPDATE` shape for the composite-PK/composite-unique models (an increment-on-conflict upsert, e.g. a stock transfer, is still hand-rolled raw SQL rather than stretched through this helper). `src/database/mysql-errors.ts`'s `isDuplicateKeyError`/`isLockConflict` check MySQL errno 1062/1213/1205, replacing Prisma's `P2002`/`P2034` catches. `src/database/decimal.util.ts`'s `trimDecimal()` trims mysql2's full-precision `DECIMAL(65,30)` string output (e.g. `"75.000000000000000000000000000000"`, the scale every *unannotated* `Decimal` field in the old Prisma schema became at the real DB level) back to a plain trimmed string (`"75"`) at API response boundaries — a fixed-scale column (`@db.Decimal(p,s)` in the old schema, e.g. `taxRate`, `commissionValue`) doesn't need it, since it already comes back at that declared scale. The migration was done in 8 phases (leaf CRUD → single-row upserts → auth/identity → catalog/taxonomy → orders+dependents → payments → reporting/aggregation → invoices, the hardest file) plus a final cutover pass, each phase its own commit with `tsc --noEmit` + the full unit/e2e suites green before moving to the next; the batch-load-then-assemble pattern (parallel `WHERE...IN` queries + a JS `Map` grouping step, replacing a Prisma nested `include`) recurs throughout the codebase wherever a list endpoint used to fetch several relations at once — see `ProductsService.loadProductsWithRelations`/`loadVariantsWithRelations`/`loadIngredientLinks` and `PublicService.loadPublicProductsWithRelations` as the canonical examples to follow for a new one. TINYINT(1) boolean columns and JSON columns both come back already the "right" JS shape (real `true`/`false`, already-parsed objects/arrays) via `DatabaseService`'s pool config — no manual `Boolean()`/`JSON.parse()` needed at call sites. **This auto-parsing is keyed off the column's real MySQL type, not merely "is this column JSON-shaped data" — a `LONGTEXT` column with only a `CHECK (json_valid(...))` constraint (like `job.payload`, see "DB-backed job queue" below) is not a real JSON column and does not get auto-parsed.** Found for real (2026-08-12, not by inspection): `JobsService`'s every read site (`findById`, `claimNextJob`, `claimJobById`, `enqueue`'s own read-back, `listDeadLetter`) had been returning `payload` as the raw stored string since the job queue shipped, and every downstream handler (`handleSendEmailJob`, etc.) crashed on first property access — silently broken in production the entire time, since the existing worker-e2e test only asserted `job.status === 'completed'`, which the stub path still reaches even with `payload` unparsed (interpolating `undefined` into a template literal prints the word "undefined," it doesn't throw — the crash only happens inside `textToSimpleHtml`, on the *real*-send code path `sendEmailOrThrow` takes when `RESEND_API_KEY` is actually configured, which e2e specs run in stub mode). Fixed by `JobsService.parseJobRow()`, routed through every read site; if a future column follows this same LONGTEXT-plus-CHECK-constraint pattern instead of a real `JSON` column type, it needs the same explicit `JSON.parse` at its own read sites — this auto-parsing guarantee does not generalize to it for free.
- **Feature modules** follow the standard Nest triad: `<feature>.module.ts` / `.controller.ts` / `.service.ts`, with request/response shapes in `dto/`. Beyond the core catalog/order/outlet modules, the module roster (each a self-contained domain, not obvious from file structure alone):
  - **Phase C (2026-08-09) renamed the product taxonomy and marketing-groupings modules**: what was `categories/`/`category` (the taxonomy tree) is now `collections/`/`collection`; what was `collections/`/`collection` (marketing groupings) is now `templates/`/`template`. Applied as two ordered hand-authored migrations (`20260809120000_rename_collection_to_template` before `20260809120001_rename_category_to_collection`, to avoid the two renames colliding on the same freed-up name) — see those migrations' own comments for the collision-avoidance reasoning. `ingredientcategory`/`ingredient-categories/` (raw-materials stock organization) was explicitly untouched — an unrelated model that only shares the "category" substring by coincidence.
  - `collections/` (post-rename) — the product taxonomy tree (unlimited depth, cycle-guarded in service code), same shape/behavior as the old `categories/` module, just renamed. Gained a `PATCH /collections/reorder` endpoint (Phase C) mirroring `bio-links/`'s batch-reorder-by-id-array shape, for admin drag-and-drop ordering.

Also owns UAE PDPL self-service: `GET .../account/export` (rate-limited to once per 24h via `customer.lastDataExportAt`) and the two-step `DELETE .../account/me` → `DELETE .../account/me/confirm?token=` deletion flow, which *anonymises* (name/email/phone/addresses scrubbed, `passwordHash` cleared — orders/draftorder/giftcard rows keep their real `customerId` FK, merchant records are explicitly preserved) rather than hard-deleting. The confirmation token reuses `customerauthtoken` (a `purpose: 'account_deletion'` row, same opaque-token/hash-at-rest/single-use-CAS shape as password-reset) rather than a new table. Clearing `passwordHash` is what actually revokes every outstanding access token immediately — `CustomerAuthGuard` already re-reads the customer row every request and rejects one with no `passwordHash` — refresh-token revocation covers the rest. Both PII-touching actions get an `AuditLogService` entry attributed to the shop's own admin (`auditlog.actorUserId` is a required FK to `user`, with no actor-is-a-customer shape), same synthesized-system-actor pattern `PaymentsService.applyAdvanceOrderStatus` uses for BNPL webhooks.

Public `POST`/`DELETE /notify-subscriptions` (no shopSlug in the URL — `shopId` is always derived server-side from the given `productId`'s own shop, never accepted from the client), idempotent per `(shopId, productId, variantId, email)`, soft-rate-limited to 3/hour/email/shop. `NotifySubscriptionsService.triggerForProduct` fires — not awaited, always `.catch()`-guarded — from every real 0→positive stock-crossing point (manual stock adjust, outlet-to-outlet transfer, order-cancellation restock), batching the actual emails in chunks of 50 via `Promise.allSettled` so one bad address can't abort the rest of a chunk. CSV import and scan-to-stock don't trigger it yet (deliberate scope cut, not an oversight).
  - `storefront-search/` — separate from the admin-only `search/` below: a public, typo-tolerant **customer-facing** product search, `GET /public/:shopSlug/search?q=&cursor=`. Exact substring match (name/sku/description/tags/collection title) first; falls back to `fuse.js` fuzzy matching only when exact returns nothing, and only a close-enough fuzzy top hit surfaces as a `suggestion` field for the storefront's "Did you mean X?" prompt. Results are cached per `(shopId, query)` for 60s in a plain in-memory `Map` (no eviction beyond TTL-on-read — fine for a single instance, revisit with an LRU cap only if this ever runs multi-instance) and paginated 20/page via an opaque base64-offset cursor.

  - `common/nominatim.ts` — `geocodeAddress`/`reverseGeocodeAddress`, a shared proxy to OSM Nominatim (free-tier rate limits, so only ever called from a manual merchant/customer trigger — a map click or pin-drag — never autocomplete-as-you-type) used by both `outlets` (admin address entry) and `public` (storefront checkout/saved addresses).
  - `search/`, `audit-log/` — global cross-entity search, but **admin-only** (JWT-guarded product/order/customer command-palette search — not to be confused with the public, typo-tolerant `storefront-search/` above, a separate module with its own separate matching logic); an append-only staff-action log (`AuditLogService.log` deliberately swallows its own write errors so a broken audit insert never fails the real operation it's describing).
  - `theme/`, `seo/`, `whatsapp/` — storefront theme/branding settings (colors, homepage layout, hero content, header/footer layout+density, the `bannerimage` homepage-slideshow gallery), per-shop SEO metadata, WhatsApp integration credentials (encrypted at rest, see `common/crypto.ts` / `CREDENTIAL_ENCRYPTION_KEY`).

  - `public/` — the storefront's entire backend surface, mounted at `/public/:shopSlug/...`. No auth; every other module's admin-facing service is deliberately not reused for public reads (separate, narrower response shapes — see `PublicService`). A globally-unique-token feature (order tracking's `trackingToken`, the post-purchase survey's `surveyresponse.token`) gets its own narrow, un-slugged controller instead (`PublicOrderLookupController`, `PublicSurveyController`) — the token alone is self-sufficient, so no `shopSlug` belongs in that URL, even though the storefront *page* consuming it still lives under `/[shop]/...` for chrome/theming (see "Storefront frontend"). Follow this split for the next such token-based feature rather than bolting it onto the shop-scoped `PublicController`.
- **Validation**: a global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true, transform: true`) is set in `main.ts`. DTOs must use `class-validator`/`class-transformer` decorators — unvalidated fields are silently stripped, not passed through. Type-only imports referenced in a decorated class member must use `import type` (or a namespace import) — plain imports fail the build under `isolatedModules` + `emitDecoratorMetadata`.
- **Auth mechanism**: hand-rolled JWT via `@nestjs/jwt` (no Passport — one guard reading `Authorization: Bearer <token>` is simpler than a strategy layer for a single auth method) and `bcryptjs` (pure JS, not native `bcrypt`, to avoid node-gyp compilation on Windows dev machines). Every route is protected by default via guards registered as `APP_GUARD`; use `@Public()` to opt a route out (signup, login, the payment checkout/webhook endpoints) and `@Roles('admin')` to further restrict one. See "Tenant isolation and outlet scoping" above for the `TenantContext`/`resolveOutletFilter` pattern every feature module routes through.
- **Table naming**: table names throughout `prisma/migrations/*/migration.sql` (and, correspondingly, every raw SQL string in `src/`) are lowercase singular (`product`, `order`, `orderitem`, `outletstock`, `paymenttransaction`, ...) — a holdover from this backend's original Prisma-modeled naming convention (lowercase model names, no `@@map`), kept as the real on-disk table names now that Prisma itself is gone. This only works because local MySQL is case-insensitive for identifiers (Windows default) — keep new tables consistent with the existing lowercase style, but be aware this could break on a case-sensitive MySQL host. **Confirmed, not just theoretical (2026-08-05, CI Phase 2):** the original `20260709131814_init` migration actually `CREATE TABLE`d 8 tables in PascalCase (`Shop`, `User`, `Product`, `ProductVariant`, `Order`, `OrderItem`, `PaymentTransaction`, `ThemeSettings`) — every migration since has referenced them lowercase, which only ever worked locally because Windows MySQL folds table-name case at creation time (so `Shop` was already stored as `shop` on disk). The first-ever genuinely clean migration run (GitHub Actions' Linux `mysql:8.0` service container, case-sensitive by default) failed immediately ("Table 'shop_manager.product' doesn't exist") on the very next migration. Fixed by `20260709131815_rename_init_tables_to_lowercase`, inserted right after init. **First version was a plain `RENAME TABLE` and was itself broken against any pre-existing database** — every real dev/staging DB was created on Windows, so it already has the tables stored lowercase (`shop`, not `Shop`); an unconditional `RENAME TABLE Shop TO shop` there hits the exact same 1050 "table already exists" this migration was written to fix, just one migration later. Confirmed empirically (2026-08-05) by seeding a scratch database with the full migration history minus this one folder (simulating "existing DB, not yet migrated") and running `migrate deploy` against it. **Fixed for real** by making each rename conditional on an `information_schema.tables` existence check for the PascalCase source name, wrapped in `PREPARE`/`EXECUTE` dynamic SQL (MySQL has no `RENAME TABLE IF EXISTS`) — no-ops when the source isn't there, renames for real when it is. One more gotcha inside that fix: the existence check itself must compare with `BINARY table_name = 'Shop'`, not a plain `=` — `information_schema.tables.table_name` compares case-insensitively by default, so an unguarded check matched the lowercase `shop` table too and the guard fired the rename anyway (caught by the same empirical test, second iteration). Verified against three scenarios: a scratch DB seeded with everything-but-this-migration (existing-lowercase-DB path, no-op, confirmed via `SHOW TABLES` that no stray PascalCase table was created), a genuinely fresh scratch DB from migration zero (clean-DB path, all 63 apply), and real Linux CI (the only place the actual case-sensitive rename branch ever executes, since Windows can't produce a genuinely case-sensitive MySQL to test against locally).
- **Many-to-many relations** (Product↔Collection, Product↔Tag) use explicit join tables (`productcollection`, `producttag`) with a composite primary key, rather than a surrogate `id` column — follow this pattern for future join tables so cascade behavior and indexes stay explicit. `outletstock` (composite PK `[outletId, productId]`) follows the same style. `src/database/upsert.util.ts`'s `upsert()` helper (see "Database access" above) handles the common `INSERT ... ON DUPLICATE KEY UPDATE` case for these.
- **Product images are upserted by `url` on update, not deleted-and-recreated.** `ProductsService.update` matches `dto.images` against the existing `productimage` rows by url, updates `order` in place for a url that already exists, and only creates/deletes rows for genuinely added/removed urls. This matters beyond tidiness: `productvariant.imageId` is `onDelete: SetNull`, and the frontend's product-edit form always resends the full `images` array on every save (even when images didn't change) — a naive delete-all-then-recreate assigns every image a fresh id on every save, which silently wipes every variant's image assignment on its very next unrelated edit. Don't revert to delete+recreate for this relation.
- **Two patterns for a per-product child list, chosen by whether it drives variant generation.** `productimage`/`productattribute`/`productfaq` are plain ordered lists embedded directly in `CreateProductDto`/`UpdateProductDto` (full-replace on update inside the same transaction — upsert-by-url for images per above since `productvariant.imageId` FKs into it, plain delete-then-recreate for attributes/faqs since nothing FKs into those) — no dedicated endpoint. `productoption`/`productvariant` instead get their own `PUT /products/:id/options`, because changing them regenerates the variant cartesian product (`variant-generator.ts`) with id-preserving reconciliation against existing variants — a side effect a main-DTO field can't express. When adding a new simple per-product list, embed it in the DTO; only reach for a standalone endpoint if it has real generation/reconciliation logic like options does. `productattribute` (informational, e.g. Material: Cotton) is deliberately a separate model from `productoption`/`productoptionvalue` for this reason — it's not a purchasable variant axis and must never be extended to become one.
- **`product.isCheckoutAddon`** flags a product to be offered in the storefront checkout's "would you like to add any extras?" popup (`storefront/components/checkout/AddonPrompt.tsx`) for any cart that doesn't already contain it — filterable via `GET /public/:shopSlug/products?isCheckoutAddon=true`. A plain catalog flag, no separate config table — same "doesn't earn its own model" reasoning as `product.isGiftCard`/`giftCardDenominations`/etc. (the config for *selling* a gift-card product; the redeemable card itself is a real `giftcard` model, see `gift-cards/` above).
- **`orderitem.note`** is an optional customer-typed note captured on the storefront PDP (below Add to Cart, ~200 char cap), carried verbatim through `CartItem.note` → `CreatePublicOrderDto.items[].note` → `orderitem.note` — no parsing or merchant editing. Shown staff-side on the admin live-orders kanban card (only rendered for items that actually have one, to stay compact) and per line item in `OrderDetailModal`. Distinct from `ordernote` (an order-level, staff-authored note thread) and `order.deliveryNotes` — there is no merchant-authored per-item note anywhere in the schema, only this customer-authored one.
- **Order status transitions are compare-and-swap, not read-then-write.** `OrdersService.updateStatus`/`.cancel` re-check the row's status inside the same `$transaction` via `updateMany({ where: { id, status: <expected>, outletId: order.outletId } })` and inspect `result.count` — this is load-bearing, not incidental style. A plain `findOne` then `update` has a real race: two concurrent "confirm" calls on the same order would both read `pending` and both decrement stock. The CAS pattern means only one write can match per transition; the loser gets a `ConflictException` (409) instead of silently double-applying a stock change. The `outletId` in the `where` clause is defense-in-depth on top of the outlet-scope check already done in `findOne`. Follow this pattern for any future status-driven side effect (stock, payment, notifications) — don't revert to a plain `update`.
- **Stock is decremented on `pending → confirmed`, not on order creation** (so an abandoned cart never holds stock hostage), and restored on cancellation from any status where it was already decremented. `OrdersService.adjustStockForOrder` upserts into `outletstock` keyed by `[outletId, productId]`, not `product.stockQuantity` (removed — see "Tenant isolation and outlet scoping").
- **Editing a confirmed order's item quantities adjusts BOM ingredient stock by delta, not a from-scratch recompute.** `OrdersService.updateItems` only touches `outletingredientstock` when `order.status === 'confirmed' && order.ingredientsConsumedAt !== null` — a still-pending order's ingredients were never consumed yet (that only happens at the `pending → confirmed` transition above), and an order whose ingredients were never consumed to begin with (auto-deduct was off at confirm time) must stay untouched by an edit rather than start being tracked mid-order. A quantity increase reuses `ProductsService.consumeForOrderItems` with `throwOnInsufficientStock: false` — it never blocks the save, even into negative ingredient stock; going negative is surfaced instead as `ingredientStockWarnings: string[]` on the response for the admin UI to toast. A decrease (or item removal) returns exactly its own delta, unconditionally.
- **Payments use a strategy pattern, resolved per-shop, not per-deployment**: `payments/payment-provider.interface.ts` defines `PaymentProvider` (`createCheckoutSession`, `parseWebhookEvent`, and an *optional* `refundPayment` — optional because Nomod/Telr/PayTabs are still structural stubs with no real API integration; Stripe, Tabby, and Tamara implement it for real). `payments/providers/` has one file per gateway; `PaymentProviderRegistry` registers every implemented provider at boot, and `PaymentsService`/`PublicService` resolve the right one at call time from `shop.paymentGateway` (the shop's chosen card processor) or `shoppaymentprovider.enabled` (the independent BNPL-style providers) — there is no single app-wide `PAYMENT_PROVIDER` env selection anymore. Per-shop bring-your-own-keys credentials are resolved via `PaymentSettingsService.resolveCredentials` (encrypted at rest) and fall back to the matching platform-level env var (`STRIPE_SECRET_KEY`, `TELR_STORE_ID`/`TELR_AUTH_KEY`, `PAYTABS_PROFILE_ID`/`PAYTABS_SERVER_KEY`, `TABBY_PUBLIC_KEY`/`TABBY_SECRET_KEY`/`TABBY_WEBHOOK_SECRET`, `TAMARA_API_URL`/`TAMARA_TOKEN`/`TAMARA_NOTIFICATION_TOKEN`) for shops that predate per-shop credential storage. The Stripe client itself is constructed lazily per-key (on first use, cached by key), not in the constructor, so a shop without its own keys configured doesn't crash the whole app at boot.
- **Payment provider toggle-bypass guard — a bug class that has recurred 3 times in this codebase.** Whether a gateway is actually usable for a shop (has real, non-empty credentials) must be checked *inside* the provider's own `createCheckoutSession`/`parseWebhookEvent` (throwing `PaymentProviderNotConfiguredException`), not only by whatever outer caller resolved credentials or checked `shoppaymentprovider.enabled` first (`PublicService.assertPaymentMethodAvailable`, `PaymentsService.getCheckoutSession`, etc.) — an outer-only check is exactly what's been bypassed each time, by some other call path that forgot to repeat it. See `TabbyPaymentProvider`/`TamaraPaymentProvider`'s own "MANDATORY GUARD" comments for the concrete pattern to copy when adding a 4th real provider (Telr/PayTabs/Nomod, if one of those ever gets a real implementation).
- **BNPL webhooks can drive the order's own status, not just `paymentStatus`** — `WebhookResult.advanceOrderStatus` (`'confirmed' | 'cancelled'`, optional, undefined for Stripe/every non-BNPL provider) tells `PaymentsService.handleWebhook` to additionally run the order through the same CAS state machine `OrdersController`'s own status/cancel endpoints use (`OrdersService.updateStatus`/`.cancel`), under a synthesized system `TenantContext` (`role: 'admin'`, attributed to the shop's own admin user — every shop always has at least one, since the last remaining admin can never be demoted/deleted). Only ever applied while the order is still `'pending'` — a provider's approval/expiry signal arriving after a merchant already moved the order forward (or cancelled it) is stale and silently ignored, never forced through; `updateStatus`/`cancel`'s own exceptions on an invalid/superseded transition are swallowed for exactly that reason and never allowed to fail the webhook response itself. Stripe's own `checkout.session.completed` handling deliberately does *not* set this field — payment success there has never implied order confirmation, and this addition doesn't change that.
- **Refunds reuse the webhook's charge reference, not the event id**: `paymenttransaction.gatewayReference` is the *webhook event id* (used only for the delivery-idempotency unique constraint below) — issuing a real refund needs the charge/payment-intent id instead, stored separately as `paymenttransaction.providerChargeReference` (captured from `WebhookResult.chargeReference` at webhook-handling time). Don't try to refund against `gatewayReference`; it's the wrong identifier.
- **Webhook idempotency**: `paymenttransaction` has a unique constraint on `(gateway, gatewayReference)`, and the idempotency key is the gateway's *event* id (Stripe's `event.id`), not the object the event is about (a checkout session id can't tell two different events about the same session apart). `PaymentsService.handleWebhook` relies on that unique constraint failing — catching both `isDuplicateKeyError` (MySQL errno 1062, duplicate key, the common case) and `isLockConflict` (errno 1213/1205, write conflict/deadlock, observed under truly concurrent duplicate delivery — see `src/database/mysql-errors.ts`) as "already processed, no-op." Don't replace this with a `findFirst`-then-`create` check — that's exactly the TOCTOU race this design avoids.
- **Raw body for webhooks**: `main.ts` passes `{ rawBody: true }` to `NestFactory.create`; the webhook controller reads `req.rawBody` (typed via `RawBodyRequest<Request>` from `@nestjs/common`) because Stripe signature verification needs the exact unparsed bytes, not the JSON-parsed body.
- **Dashboard date math is UAE-local (UTC+4), not server-local or UTC.** `DashboardService` computes "today"/"this week"/"this month" boundaries by shifting into a hardcoded +4h offset before truncating — UAE doesn't observe DST, so this is a stable constant, not a shortcut that will drift. The 30-day daily revenue series and top-products query use raw parameterized SQL via `DatabaseService.query()` (`DATE(DATE_ADD(createdAt, INTERVAL 4 HOUR))`, plus a conditional `AND outletId = ?` fragment appended only when an outlet is resolved) since grouping by a derived/truncated expression like this has no ORM-level equivalent to reach for anyway now.
- **CORS** is an explicit allowlist (`ADMIN_ORIGINS` env var, comma-split) passed to `app.enableCors({ origin })` in `main.ts` — not `app.enableCors()` wide-open. Auth is JWT-header-based (`Authorization: Bearer`), so `credentials: true` is not needed.
- **Email sending** (`common/email.ts`'s `sendEmail()`) is platform-level, not per-shop bring-your-own — one Resend API key, one verified sending domain, unlike Payments/WhatsApp. Chosen deliberately: merchants don't need their own DNS/SPF/DKIM setup to get transactional email working. `sendEmail()` falls back to `sendEmailStub()` (console.log) whenever `RESEND_API_KEY` is unset *or* the real Resend call itself fails (bad key, unverified domain, network error) — never throws, so a broken email provider can't fail order creation/checkout/auth. `email/providers/resend-email.provider.ts` is the real implementation (plain `fetch` against Resend's HTTP API, same as `MetaWhatsAppProvider` — no SDK dependency). Every call site must go through `sendEmail()`, never `sendEmailStub()` directly — `common/email-callsites.spec.ts` statically enforces this across `src/`. `RESEND_API_KEY=test` is a reserved sentinel `sendEmail()` short-circuits to the stub on (no network call at all) — this repo's local `.env` is set to it specifically so the e2e suite (every signup fires a verification email) isn't paying for a real, slow, and in this sandbox always-failing Resend round trip on every single spec; swap in a real `re_...` key only to test actual delivery locally. **Fixed for real on the VPS, then backported here (2026-08-15):** the originally-planned `"${shopName} <notifications@${EMAIL_FROM_ADDRESS domain}>"` shop-identity-in-display-name scheme (`DEFAULT_FROM_ADDRESS = 'notifications@requital.app'`, overridable via `EMAIL_FROM_ADDRESS`) was a placeholder for a domain that was never actually verified with Resend — every real send failed and silently fell back to the stub. `resend-email.provider.ts` now hardcodes `from: 'Requital <noreply@requital.io>'` (a real, verified sending domain), dropping both `EMAIL_FROM_ADDRESS` and the per-shop `fromName` display name entirely — every shop's transactional email now sends as generic "Requital," not the merchant's own name. Revisit true per-shop sending (own domain, and/or restoring the display-name customization against the now-verified domain) only if a merchant specifically needs it for reputation/branding reasons; mirror `PaymentSettingsService`'s resolveCredentials pattern if so.
- **WhatsApp order alerts (platform-owned)**: separate from the per-shop, bring-your-own-credentials `WhatsAppProvider` strategy pattern in `whatsapp/` (used for the customer-facing "your order is confirmed" message) — this is one Requital-owned WhatsApp Business account, env-configured (`PLATFORM_WHATSAPP_PHONE_NUMBER_ID`/`PLATFORM_WHATSAPP_ACCESS_TOKEN`), that messages the merchant's own outlet on every new order, with zero per-shop setup. ## Domains — subdomain and custom domain configuration

A shop's storefront is reachable at either its default `{subdomain}.requital.io` or a merchant-connected custom domain, chosen via `shop.domainType` (`'subdomain' | 'custom'`, plain string column per this schema's established small-fixed-string-set convention). `shop.subdomain` is not a new concept here — it already existed (set once at signup, immutable after — see `SignupDto`'s note above and `ShopService.update`'s country-lock precedent for the established "no mutation path for this field" pattern) and is reused as-is; only `shop.customDomain` (nullable, `UNIQUE`) and `shop.domainType` are new columns (`20260811120000_shop_domain_config`). `RESERVED_SUBDOMAINS` (`shop/constants.ts`, checked once at signup; mirrored by hand in `admin/lib/validators.ts` with no shared package, same cross-app-duplication convention as every other regex/list in this codebase) blocks a shop from claiming a subdomain that collides with a real platform hostname (`admin`, `api`, `www`, ...).

- **`GET`/`PATCH /shop/domain`** (`ShopController`, ctx-scoped like every other `/shop/*` route — no `:shopId` param, since `TenantContext.shopId` is never client-suppliable). `PATCH` body is `{ type: 'subdomain' }` or `{ type: 'custom', customDomain: string }`; switching back to `'subdomain'` clears `customDomain` (frees it for another shop). `ShopService.updateDomain` validates the hostname (`shop/domain-validation.ts`'s `isValidCustomDomain`, a pure regex-based check mirrored on the frontend) after normalizing a pasted full URL down to a bare hostname (`common/normalize.ts`'s `normalizeCustomDomain`, the inverse of `normalizeWebsiteUrl` — strips protocol/path rather than adding one), and maps the `customDomain` unique-index conflict (`isDuplicateKeyError`) to a 409, same idempotency-via-unique-constraint philosophy as the webhook/discount-redemption CAS patterns elsewhere in this file.
- **`GET /domains/verify?domain=`** (`domains/`, `@Public()`) is the Caddy on-demand-TLS `ask` endpoint — called on every TLS handshake for a hostname Caddy doesn't already have a cert for, so it stays a single indexed lookup and nothing heavier, and answers via HTTP status alone (200 = issue, 404 = don't). It has to recognize two shapes of "known domain," not one: a `{subdomain}.requital.io` host (matched against `shop.subdomain` directly, regardless of that shop's current `domainType` — a shop that switched to a custom domain shouldn't break its own default URL) and a connected `shop.customDomain`. This two-shape check exists because the Caddyfile's global `on_demand_tls.ask` config applies to every site block using `tls { on_demand }`, including the `*.requital.io` wildcard block, not just the custom-domain catch-all — a verify that only checked `customDomain` would silently break certificate issuance for every ordinary subdomain-type shop.
- **Caddy** (`/etc/caddy/Caddyfile` on the VPS) has three domain-routing blocks in precedence order: the explicit `requital.io`/`www.requital.io` (301 → `admin.requital.io`) and `admin.requital.io`/`api.requital.io` blocks from the original VPS cutover always win for those exact hosts; a `*.requital.io` wildcard block (on-demand TLS, routed by host to admin/api/storefront) handles per-shop subdomains; a catch-all block (on-demand TLS, routed to the storefront app) handles connected custom domains. On-demand TLS against a wildcard host pattern issues individual real (non-wildcard) certificates per concretely-visited hostname via the `ask` round-trip — it does not require a DNS-01 challenge/provider plugin the way an actual wildcard certificate would.
- **`storefrontUrlFor(shop)`** (`admin/lib/api.ts`) is the one place the *merchant-facing* "your store's public address" gets built (Business Information's "Your store is live at", the outlet QR code, TopBar's "View store" link) — kept deliberately separate from `admin/lib/api.ts`'s own `STOREFRONT_URL` constant, which is for admin's *internal* storefront navigation (order/payment deep-links) and stays on the old bare-path shape. `storefrontUrlFor` mirrors `ShopService.getDomainConfig`'s `storefrontUrl` computation by hand on the `Shop` object's own `domainType`/`customDomain`/`subdomain` fields (already present on every `GET /shop` response, so no second `GET /shop/domain` round-trip is needed) rather than calling the backend a second time. **Found for real (2026-08-12): this function predated the domains feature and was never updated when it shipped** — it kept building `{STOREFRONT_URL}/{subdomain}` (`requital.io/acme`) for every shop regardless of `domainType`, silently wrong from the moment per-shop domains landed, since nothing type-checks a URL's *shape*. `GET /shop/domain`'s own `storefrontUrl` field was correct from day one; the bug was specifically this second, independent, never-updated construction.
- **Storefront subdomain/custom-domain routing** (`storefront/proxy.ts`, Next 16's renamed `middleware.ts` — see `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`) is what actually makes the `*.requital.io`/custom-domain traffic Caddy already forwards to port 3002 (above) resolve to a real shop. Tenant resolution in this app was, and still is, a path segment (`/[shop]/...`, see "Tenant resolution is a path segment, not a domain" below) — `proxy.ts` doesn't change that contract, it just rewrites an incoming *hostname*-based request onto that same path-based tree before any page ever sees it, so `app/[shop]/...` stays completely unaware a rewrite happened. `GET /domains/resolve?host=` (`domains/`, `@Public()`, same shape as `verify` above but returns `{ subdomain }` instead of a bare 200/404 — both now share `DomainsService.resolveSubdomain`, with `isKnownDomain` just checking the result is non-null) is what supplies the subdomain to rewrite to; a `{subdomain}.requital.io` host resolves for free from the hostname alone, but a custom domain has no way to derive the shop's real subdomain (the app's internal routing key, never the custom domain itself) without asking the backend. A host that resolves to nothing (or a `localhost`/`*.local` dev host, left alone entirely so the existing manual `/[shop]/...` path-testing flow keeps working) rewrites to `app/store-not-found/page.tsx` with a real `404` status set directly on the `NextResponse.rewrite()` call, rather than a generic crash or an unstyled empty shop.
- **Two bugs found in the above once real subdomain traffic hit it for real (2026-08-12), both fixed together**: (1) CORS in `main.ts` was still the pre-domains static `ADMIN_ORIGINS` allowlist, so a browser on `{subdomain}.requital.io` or a merchant's custom domain got its `/public/:shopSlug/...` fetches blocked outright. `app.enableCors` now takes an `origin` function: `ADMIN_ORIGINS` (dev + the fixed admin/api hosts) as a fast-path array check, then a `/^https:\/\/([a-z0-9-]+\.)?requital\.io$/` regex covering every subdomain for free, then `DomainsService.isCustomDomain` (a new, narrow method — just the `customDomain`-column half of `resolveSubdomain`, since the regex already covers the subdomain shape) for anything else, resolved via `app.get(DomainsService)` in `bootstrap()`. `credentials: true` was deliberately *not* added despite being in the originally-proposed snippet — auth is still bearer-token-in-header everywhere (staff and customer both), so the file's existing "not needed" reasoning still holds; flipping it on would have enabled cookie-credentialed cross-origin requests nothing in this codebase needs. (2) Every storefront-internal `<Link>`/`router.push`/`redirect()` still hardcoded an absolute `/${shopSlug}/...` path — a leftover from before `proxy.ts` existed. On a subdomain/custom-domain visit the browser's own URL bar never has the `/{slug}` prefix (the rewrite is server-side and invisible to it), so a hardcoded-prefixed link double-prefixes after `proxy.ts` rewrites it again and 404s.

  **First fix attempt unconditionally stripped the prefix everywhere and broke `e2e/`'s own suite in CI**, which drives the storefront via bare `http://localhost:3002/{shop}/...` (`e2e/urls.ts`'s `STOREFRONT_URL`) — exactly the direct-path flow `proxy.ts`'s `isLocalHost()` deliberately leaves un-rewritten (a bare `localhost` host carries no per-shop info to resolve). An unprefixed link there 404s just as surely as a prefixed one does on a real subdomain. **Fixed for real** with dual-mode link generation instead of a blanket strip: `lib/shop-context.tsx`'s `ShopContextValue` gained `shopBasePath` (`useShop().shopBasePath`), computed in `ShopProvider` from `usePathname()` — `/${shopSlug}` if the *current* pathname already carries that prefix (direct-path/local/CI access, where the browser's own address bar has it), `""` otherwise (hostname-resolved access, where it structurally can't). Every internal `href`/`router.push`/`redirect()` target is now built as `` `${shopBasePath}/whatever` `` (or `shopBasePath || "/"` for the home link) instead of a bare or unconditionally-prefixed string — correct in both flows because it reads the signal the browser itself is already showing, not an assumption about which flow this deployment uses. `shopSlug` itself stays untouched everywhere it's used for an actual API call (`/public/:shopSlug/...`) or a localStorage key. The one server-component case (`products/[slug]/page.tsx`'s legacy-id-to-slug redirect, which has no `usePathname()` to read) instead reads the request's `Host` header via `next/headers` and replicates `proxy.ts`'s own `isLocalHost()` check (now factored into a shared `lib/is-local-host.ts` so the two can't silently diverge) to decide whether to prefix. Verified by actually running `e2e`'s full 4-spec suite locally (backend + admin + storefront all started per the README) — all 4 pass, including the one that caught the original regression.

## Delivery zones

Per-outlet named flat-fee zones (`deliveryzone`, additive to the outlet's own single `deliveryRadiusKm`/`latitude`/`longitude` — see `DeliveryZonesService`'s own header comment) gained an optional per-zone map center + radius on 2026-08-19: `lat`/`lng`/`radiusKm` (`DECIMAL(10,6)`/`DECIMAL(10,6)`/`DECIMAL(8,2)`, all nullable — a zone created via the API with none of the three still works exactly as before). `CreateDeliveryZoneDto`/`UpdateDeliveryZoneDto` validate `lat`/`lng` against real coordinate bounds (`-90..90`/`-180..180`) and `radiusKm` against `1..100`; `DeliveryZonesService.create`/`.update` pass them straight through — no distance/haversine calculation exists anywhere in this codebase, this is captured/persisted only, same as the pre-existing outlet-level radius. Admin's "New zone"/"Edit zone" modal (`DeliveryZoneFormModal.tsx`) renders `DeliveryZoneMap.tsx`, a Google Maps view defaulting to a UAE-wide center (`UAE_CENTER`, zoom 7) with a draggable pin + a `google.maps.Circle` overlay sized by a 1–100km slider; clicking the map or dragging the pin both move the zone's center. Every new zone gets a real lat/lng/radiusKm from the moment the modal is used (defaults to `UAE_CENTER`/5km rather than leaving the fields empty) — the nullable columns exist for backward compatibility with zones created before this shipped or via a direct API call, not because the admin UI ever leaves them unset.

## Auto-apply discounts

`discount.discountType` (`'code' | 'auto'`, plain string column, default `'code'`, added 2026-08-19) is orthogonal to `discount.type` (PERCENTAGE/FIXED_AMOUNT/FREE_SHIPPING, the amount math) and `appliesTo` (which products/collections it's scoped to) — an `'auto'` discount applies itself to every matching cart/product with no code entered, reusing the *existing* `appliesTo`/`discountproduct`/`discountcollection` many-to-many scoping infrastructure rather than a new single product/collection FK. `discount.code` is nullable as of the same migration (`20260819110000_auto_discounts`) — multiple `'auto'` rows with a NULL code coexist fine under the pre-existing `(shopId, code)` unique index, since InnoDB treats every NULL as distinct from every other NULL. `DiscountsService.assertDiscountKindFields` is the cross-field guard: a `'code'` discount must have a code (moved from a DTO-level `@IsNotEmpty` to a service-level check, since `code` had to become `@IsOptional()` at the DTO layer to allow `'auto'`), and an `'auto'` discount must NOT have a code and must NOT be scoped `ALL_PRODUCTS` (it needs a concrete product/collection set to know when to fire). `DiscountsService.listActiveAutoDiscounts(shopId)` — every currently-active, in-date-range `'auto'` discount, public-safe fields only — backs the new `GET /public/:shopSlug/discounts/auto` endpoint (`@Public()`, no throttle beyond the default; unlike `discounts/validate` it takes no user input, so it isn't enumeration-sensitive).

Storefront: `lib/auto-discounts.ts`'s pure `computeAutoDiscountedPrice(product, autoDiscounts)` picks the single best (largest) matching discount for a product and returns `{ originalPrice, discountedPrice }` or `null` — mirrors `DiscountsService.computeAmount`'s math client-side. The discount list is fetched once per session in `shop-context.tsx` (alongside `shop`/`outlets`) and exposed as `useShop().autoDiscounts`; `ProductCard.tsx` and the PDP (`ProductDetailClient.tsx`) both call the pure function directly rather than re-fetching per card. On the PDP, an active auto discount takes priority over the merchant-set per-variant `compareAtPrice` strikethrough when both exist (not stacked) — computed against `displayPrice` (the effective price, accounting for the selected variant), not the base `product.price`, and skipped entirely for gift cards.

**Deliberate scope boundary, not an oversight**: this only drives *pricing display*. Actual order-total redemption of an auto discount (a matching cart auto-applying at checkout the way a code does via `PublicService.createOrder`'s `discountCode` branch) is not wired — that touches the same CAS/payment-sensitive transaction `discountId`/`discountAmount`/`DiscountsService.redeem()` already run through, and was deliberately left out of the pass that shipped pricing display rather than risked blind in the same session. If this needs finishing, `PublicService.createOrder` is where the `discountCode`-provided branch already lives; a no-code auto-apply would need `DiscountsService.listActiveAutoDiscounts` (or a variant of it) consulted there when `dto.discountCode` is absent.

### Product wizard (`ProductForm.tsx`)

`/inventory/new` and `/inventory/[id]/edit` both render `ProductForm`, a 3-step wizard (Basics → Pricing & Inventory → Organization), not a single long-scroll form. ### Account Setup wizard (`AccountSetup.tsx`)

`/signup` renders `AccountSetup`, a 4-step wizard (Personal Info → Business Info → Location & Setup → Review & Confirm), replacing the old single-page signup form — same `useProductForm`-style split as the Product wizard above: `lib/useAccountSetupForm.ts` owns all state/validation/submit logic (individual `useState` per field, not a single dynamic record, matching `useProductForm`'s convention), the four `AccountSetupStep*.tsx` components are pure presentation, and `components/ui/Stepper.tsx` is reused as-is for the progress indicator (its existing click-to-jump-on-completed-step behavior doubles as the wizard's "edit a previous step from Review" affordance — there's no separate per-field Edit button).
- **`lib/validators.ts`** has the pure field validators (`validateEmail`/`validatePhone`/`validatePassword`/`validateTrn`/`validateUrl`, plus `passwordRequirements()` for the live checklist) — framework-free so they're directly unit-testable and so `backend/src/auth/dto/signup.dto.ts`'s hand-mirrored regexes (email/phone/websiteUrl) can be kept in sync by hand against a single source of truth on the frontend side.

The error modal's "Back" returns to Step 1; "Try Again" stays on Step 4.
- **`AuthCard`'s `maxWidthClassName` prop** (default `"max-w-sm"`, unchanged for every other pre-auth screen) lets this wizard opt into `"max-w-2xl"` for its 2-column Business/Location steps, instead of widening the shared card for every login/forgot-password/etc. screen that doesn't need it.
- Backend support for the extra fields collected on Steps 2–3 (phone, businessType, trn, websiteUrl, address, operatingModel, branchCount) is covered above under "Backend architecture"'s `SignupDto` note — they're wizard-required but DTO-optional.

### Settings/config page layout convention

Worked out iteratively across several passes on Business Settings and the Outlet edit tabs, then generalized — apply it by default to every settings/config page built from here on, not just on request:

1. **Card containers**: every distinct section (a named group of related fields) is wrapped in `components/ui/Card.tsx` (`rounded-lg border border-black/10 dark:border-white/10 bg-white dark:bg-zinc-900 p-6` — the same shade `StatCard` and the `Table` wrapper already use). Never separate sections with just a heading on bare page background. Card boundaries follow whatever headings the content already has — don't invent new sub-sections just to have more cards, and don't split a group of related fields (e.g. Business Type + Currency + Default Language, all under one "General" heading) into one card each.
2. **Grid density matches field length**: short fields (dropdowns, numbers, short text — email, phone, currency, time zone) go `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`, never a single stacked column. Long-form fields (descriptions, addresses, radio groups with long option text) get `sm:col-span-2 lg:col-span-3` to stay full-width within that same grid.
3. **Fill height gaps between side-by-side sections**: if two cards sit side by side (`sm:grid-cols-2`) and a later section could reasonably sit in the shorter column instead of stacking full-width below, do that. Judgment call, not automatic — don't force an unrelated section sideways just to fill space, and don't override an explicit instruction to keep something full-width (e.g. Business Hours, which is a table, not a field).
4. **Toggle, not Checkbox, for binary state fields**: anything representing an on/off *status* (active/inactive, open/closed, enabled/disabled as a single state of one thing — outlet active, delivery/pickup available, force-closed override) uses `components/ui/Toggle.tsx` (green = on, neutral grey = off — off used to be red, but that read as "broken," not "not configured yet"; red is not used anywhere in this control), the same switch `OutletEditSidebar`'s "Outlet is Active" control uses. `Checkbox` is reserved for actual multi-select option lists where several independent boxes are ticked together (e.g. Store Configuration's "Product image zoom", "Show category menu") — not a single status field standing alone.
5. **Compact grouping over spread rows**: related controls in one row (a value plus its own status toggle) sit close together, left-aligned — not stretched to opposite edges of a wide card with `justify-between` dead space in between, unless there's a specific reason (a card header + its action button) to do that.
6. **Responsive collapse**: every grid above degrades to `grid-cols-1` below `sm`. Never ship a multi-column layout that doesn't collapse on mobile.

### Store Configuration "Coming Soon" toggles

Business Settings > Store Configuration has a "Coming Soon" card of `shop.xEnabled` boolean toggles that ship ahead of the feature they'll gate — they persist a preference but do nothing until wired up. `customerSurveyEnabled`/`disableStoreCart` started there and were later wired; only `dynamicThemeBuilderEnabled` remains inert as of this writing. (`productVariantsEnabled`/`productAttributesEnabled`/`productFaqsEnabled` also went through this same path once, but were later removed entirely — the Variants/Attributes/FAQs sections are no longer gated by a shop-wide toggle at all; see "Simple/Advanced product editor mode" below.) The convention for wiring one up, once its feature is actually built:

- The toggle is a pure **admin-UI/storefront-rendering gate**, not backend enforcement — the backend DTO/service usually has no idea the toggle exists (see `customerSurveyEnabled`: `OrdersService` reads it only to decide whether to fire the survey email, nothing in the catalog/pricing path branches on it). Admin fetches it via `getShop()` and conditionally renders the gated behavior. See `disableStoreCart`/`cartDisabledMode` for the pattern.
- Move the toggle out of the "Coming Soon" `Card` into its own real section on the Store Configuration page once wired (see `store-configuration/page.tsx`'s Cart & Checkout/Post-Purchase cards) — don't leave a functional toggle sitting under "Coming Soon" copy.
- A toggle can carry a second field for its own mode/config, validated with `@IsIn` rather than a dedicated enum column for a small fixed string set (see `cartDisabledMode`) — only reveal that control in the admin UI when the parent toggle is on.

### Simple/Advanced product editor mode, and per-product Variants/Attributes/FAQs

`shop.productEditorMode` (`'simple' | 'advanced'`, plain string column rather than a dedicated enum, per this schema's convention of favoring small fixed string sets over enum columns, not the shop-wide `xEnabled` toggle pattern above) picks which experience `ProductForm.tsx` renders: `'simple'` is the existing 3-step wizard (Basics → Pricing & Inventory → Organization); `'advanced'` is a single scrollable page (all six sections, including Variants/Attributes/FAQs, stacked with a sticky left anchor nav, `hidden` below `lg`) with no stepper. Set on the Account Setup wizard's Review & Confirm step (defaults to `'simple'`), editable later via a `SegmentedToggle` on Business Information ("Product Editor" card).

This replaced the old shop-wide `productVariantsEnabled`/`productAttributesEnabled`/`productFaqsEnabled` toggles (see "Coming Soon toggles" above) with a **per-product** opt-in instead: `product.showVariants`/`showAttributes`/`showFaqs` (plain booleans, persisted with the product, `@default(false)`). `productEditorMode` only controls a *new* product's starting values for these three (false for simple, true for advanced) — an existing product's own saved values always win regardless of the shop's current mode (see `useProductForm`'s `getShop()` effect). `VariantsSection`/`AttributesSection`/`FaqsSection` all route through the shared `ProductFeatureSection.tsx` wrapper: disabled renders just a "+ Add X" link; enabled wraps the real editor in a native `<details>` (no JS accordion lib) plus a "Remove X" action, with `defaultOpen` read once on mount (simple mode opens immediately since enabling *is* the user's action; advanced mode starts collapsed) — never re-applied on re-render, so a user's manual expand/collapse always sticks. Storefront gating for Attributes/FAQs on the PDP moved the same way, from `shop.productAttributesEnabled`/`productFaqsEnabled` to `product.showAttributes`/`showFaqs`.

`shop.productEditorMode` was later extended beyond the product form to gate UI on Orders, Customers, and the Dashboard too — `lib/useShopMode.ts` is the shared hook for this (a `getShop()` effect identical to `useProductForm`'s own, refetched fresh on every mount rather than held in a shared context, so a mode change saved in Settings shows up on the next client-side navigation with no reload or cross-tab sync needed). Each page branches on the resolved mode rather than maintaining two parallel page trees: `app/orders/page.tsx` hides the History tab and trims kanban-card fields (no delivery date/age/item notes) in simple mode, swapping in `components/SimpleOrderDetailModal.tsx` (status/items/total/Cancel+advance only) for the full `OrderDetailModal`; `app/customers/page.tsx`/`[id]/page.tsx` swap in an Email column for the selection-checkbox/bulk-export column and hide the stat-card row + Birthday field; `app/dashboard/page.tsx` renders `components/SimpleDashboard.tsx` (Revenue Today/Orders Today/Top 3 Products, using `defaultDateRange(1)` instead of the date picker) in place of the full week/month dashboard; and the home page (`app/page.tsx`) greys out — doesn't hide — the Reports tile. Same as every other `xEnabled` toggle in this file: a pure admin-UI rendering gate, no backend enforcement, and simple mode never removes a capability the merchant can't still reach directly (Order History stays a live route, just unlinked from the simple kanban page).

### Page width convention — always route through the shared shell

Narrow/constrained-width layout bugs have recurred repeatedly across both frontends (Settings tabs, the admin homepage tile grid, Theme Advanced, Collections/Draft Orders detail pages, the storefront trust strip, sign-in/order-tracking cards). The root cause each time was the same: a `page.tsx` hand-rolling its own `max-w-*` wrapper instead of rendering through the one component that owns that decision — `admin/components/ui/PageShell.tsx` or `storefront/components/StorefrontPageShell.tsx` — so nothing enforced a deliberately-chosen width; it just inherited whatever cap a wrapper div happened to use at write time.

- **Every `app/**/page.tsx` routes its top-level content through `PageShell` (admin) / `StorefrontPageShell` (storefront).** Pick the variant that matches the content (see the variant comments atop each component) — don't reach for a raw `max-w-*` div as a shortcut, even for content that's genuinely single-column. Single-column doesn't mean "cap it as narrow as looks reasonable in the editor" — measure the rendered result against real available width before assuming a tight cap is correct (see PageShell's `"form"` variant history: `max-w-3xl` was picked once, never re-measured, and read as an arbitrary ~400px dead-space gap on real desktop viewports even though the content genuinely had no multi-column grid).
- **Raw `max-w-*` outside those two files is fine for small elements** (an image, a modal/drawer, a text-truncation span, a preview widget nested inside an already-shelled page) — it's specifically the page's own outermost content wrapper that must not hand-roll a width.
- Exceptions: pages with no dashboard/storefront chrome at all (admin's pre-auth login/signup/forgot-password/reset-password/accept-invite/verify-email) legitimately have nothing to route through. The storefront bio page is deliberately phone-width by design regardless of viewport, matching every other "link in bio" tool's convention.
- **Guardrail**: `node tools/check-page-width.js` greps every `page.tsx` in both apps for a `max-w-` that isn't inside a file importing `PageShell`/`StorefrontPageShell`, modulo a short allowlist for the exceptions above. Run it after adding or editing any page — it should report zero violations. **Known blind spot**: it only scans `page.tsx` files, so a `max-w-` hidden one level down inside a *component* a page renders is invisible to it — e.g. `admin/components/CollectionForm.tsx` hand-rolls `className="max-w-3xl"` on its own `<form>`, nested inside a plain, unconstrained `<PageShell>`; `app/collections/new/page.tsx` itself has no `max-w-` and passes clean. Known, not yet fixed as of this writing.
  It also can't catch a page that imports the shell correctly but picks a variant too narrow for its content (a design judgment, not a text pattern — see the Product Wizard's own `variant="form"` → `"wide"` fix above, where every input already had `w-full` and every grid was already responsive). Two follow-up tools exist for the two other failure modes: `node tools/check-form-width.js` (static heuristic — flags a hardcoded non-responsive `grid-cols-N` or a fixed-width text input missing `w-full`; expect legitimate false positives for grids inside intentionally-narrow containers like Modals or `StorefrontPageShell variant="medium"`, documented in the script itself) and `tools/screenshot/measure.js` (a reusable puppeteer helper — locate your landmark element by text/class in your own `page.evaluate`, never a guessable structural selector, then measure its gap to the viewport's right edge at the four standard breakpoints; `check-wizard-step2-width.js` in the same directory is the example to copy). Neither of these two replaces `check-page-width.js` — each catches a genuinely different failure mode.

### Location picking — Google Maps, duplicated (not shared) between the two apps

`MapPicker.tsx` (address search + draggable-pin map) exists as **separate, independently-maintained copies** in `admin/components/` and `storefront/components/` — same deliberate no-shared-package duplication as every other cross-app UI piece. Both were rewritten off Leaflet onto the Google Maps JavaScript API on 2026-08-19 (`NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`, the same key value in both apps' `.env.local`): a `lib/google-maps-loader.ts` in each app lazily injects the Maps `<script>` tag once (no `@react-google-maps/api` wrapper — the raw API is a handful of calls), `google.maps.places.Autocomplete` drives the search input, and a `google.maps.Marker` + `Geocoder` handle the draggable-pin/reverse-geocode flow the old Leaflet version had. The old `MapPickerLeaflet.tsx`/`.css` files, the `leaflet`/`react-leaflet` deps, and the frontend `geocodeAddress`/`reverseGeocodeAddress` (admin) / `geocode`/`reverseGeocode` (storefront) calls into the backend's `common/nominatim.ts` proxy are all gone — search/reverse-geocode now happen entirely client-side via Google's API, not through the backend. `common/nominatim.ts` itself was left in place (removing backend code wasn't in scope for that change) but as of this rewrite has no remaining frontend caller — flagged as dead code, not silently removed. Both apps' CSP (`next.config.ts`) allowlists `maps.googleapis.com`/`maps.gstatic.com`/Google Fonts domains for this — see Google's own documented CSP recipe for embedding the Maps JS API if extending it further.

**Runtime auth/billing failures, confirmed live and fixed (2026-08-22).** The outlet-address `MapPicker.tsx` (admin) hit a real `BillingNotEnabledMapError` during the QA audit — the script itself loads fine, but the API renders its own unbranded error dialog into the map div at *runtime*, a failure mode the loader's original `onerror`/`onload` script-tag handling never covers (that only catches the script failing to fetch at all). `admin/lib/google-maps-loader.ts`'s `loadGoogleMaps` now accepts an optional `onAuthFailure` callback and wires it to `window.gm_authFailure` — confirmed against Google's own current Maps JS API docs as a real, still-supported global hook (`@types/google.maps` just has no typed declaration for it). `MapPicker.tsx` uses it to fall into the same `failed` fallback state script-load failure already used, with copy that reads sensibly for both cases. **Not yet ported to the storefront's separate `MapPicker.tsx`/`google-maps-loader.ts` copy** (out of scope for this fix — the QA finding was specifically the admin outlet-address map) — the identical gap likely exists there too, since it's an independent copy of the same pre-fix loader. **Action item, not yet done**: verify the Maps API key's billing status on Google Cloud Console before production launch — this exact error was hit live against the shared dev key.

## Storefront frontend (`storefront/`)

- **No em dashes in user-facing copy** — same rule as admin's, see that section above.
- **Tenant resolution is a path segment, not a domain.** Every route lives under `app/[shop]/...`; the dynamic `shop` param is the shop's slug/subdomain, resolved backend-side by `/public/:shopSlug/...`. This is a deliberate departure from the original SRS's separate-top-level-domain-per-merchant plan (see "What this is") — no middleware/domain routing exists.
- **`lib/shop-context.tsx`** (`ShopProvider`/`useShop()`) fetches the shop + its outlets once per mount and drives live per-shop theming: `resolveThemeCssVars` reads `shop.brandColor`/`shop.colors`/`shop.fontFamily` (falling back to a default teal accent) and sets CSS custom properties directly on the root, including an auto-contrast text color (`color-contrast.ts`, same WCAG-AA-guard pattern as admin's `--color-accent-text`) rather than ever hardcoding white/black on top of a merchant-chosen color.
- **Homepage layout is theme-driven**: `app/[shop]/page.tsx` dispatches on `shop.homepageLayout` (`classic` / `slideshow` / `featured_grid`, set from the admin Theme editor's Advanced tab) to one of `components/home-layouts/*` — an unrecognized/`"custom"` value falls back to Classic rather than rendering nothing.
- **Header/footer chrome is real and theme-driven, not a fixed shell**: `components/AnnouncementBar.tsx` (off by default; static-joined or CSS-marquee-scrolling text — name any new keyframe-animation class without an `animate-` prefix, Tailwind v4 tries to resolve that prefix against a `--animate-*` theme token and silently produces no animation if one doesn't exist), `components/Footer.tsx` (`footerLayout`: `columns` | `centered`; brand/logo/description, `Useful Links` linking only to policy types that actually have content, `Follow Us` from `shop.socialLinks`, `Contact Us`, payment-method badges derived from real enabled providers), and `components/WhatsAppFloatingButton.tsx` (gated on `shop.whatsappFloatingButtonEnabled`) are all real, independently-toggleable sections, not a static per-template shell. `headerDensity`/`footerDensity` (`compact` | `regular` | `spacious`, height/padding only) are orthogonal to `topBarLayout`/`footerLayout` (arrangement) — any density pairs with any arrangement. `components/home-layouts/SlideshowHero.tsx` reads real `shop.banners` (the `bannerimage` model, admin-managed, uncapped) with a product-thumbnail fallback only when no banners exist.
- **Policy pages** (`policypage` model — `TERMS`/`PRIVACY`/`REFUND`/`PAYMENT`/`SHIPPING`, admin-authored rich text) are per-shop-optional: `app/[shop]/policies/[type]/page.tsx` renders a real 404-shaped "not published" state rather than a broken/empty page when a type has no content, and the footer's Useful Links column only ever links to types that do. `components/CookieConsentBanner.tsx` (mounted in `ShopLayoutClient.tsx` alongside `WhatsAppFloatingButton`) is a separate, dismissible, non-blocking bottom bar (Accept all / Decline non-essential) — choice persisted per-shop in localStorage (`requital_storefront_cookie_consent:${shopSlug}`, same scoped-key convention as `lib/cart.tsx` below) with no analytics wiring behind it yet, just the preference.
- **`components/SearchBar.tsx`** — the header search icon (wired into all 3 `TopBar` layout variants), a debounced (300ms) dropdown against `storefront-search/` (see Backend architecture) with a loading state and a "Did you mean X?" prompt when the response's `suggestion` field is set. `components/NotifyMeForm.tsx` is the PDP's "notify me when available" form, shown only when the selected product/variant is out of stock (see `notify-subscriptions/` above); its restock email links to `app/[shop]/unsubscribe-notify/page.tsx`, a one-click unsubscribe landing page.
- **`lib/cart.tsx`** is a localStorage-persisted cart context (items + `outletId` + `discountCode`, plus an optional per-item `note` typed on the PDP that rides along to order creation as `orderitem.note`). The discount code rides along with the cart for UX, but the discount *amount* is never trusted client-side — checkout re-validates and the server atomically claims/computes it at order-creation time, same as the admin-side discount redemption path.
- **Checkout add-ons**: before rendering `CheckoutSteps`/`CheckoutSinglePage`, `app/[shop]/checkout/page.tsx` gates on a one-time `AddonPrompt` popup (`components/checkout/AddonPrompt.tsx`) whenever the shop has any `isCheckoutAddon` product not already in the cart — skipped entirely for `cartDisabledMode === "contact_to_order"` shops. Selecting an add-on just calls the same `useCart().addItem` any normal add-to-cart action uses; skipping/dismissing (or having zero eligible add-ons) proceeds straight to the real checkout layout.
- **`lib/payment-methods.ts`**'s `resolvePaymentMethods` is a pure function (no React, directly unit-tested) computing the delivery vs. pickup payment-method lists from the shop's per-method toggles — it also checks that the shop's active card processor is actually enabled, not just that "online card" is toggled on, so checkout never offers an option that would 400.
- **`lib/api.ts`** follows the same plain-`fetch`, no-data-library convention as `admin/lib/api.ts` (`resolveImageUrl` for backend-relative upload paths, etc.) but is unauthenticated throughout — every call hits a `/public/:shopSlug/...` route, never an admin-authenticated one.
- Order tracking (`app/[shop]/orders/track/`) looks orders up by `order.trackingToken`, an opaque per-order token handed to the customer at checkout — not the sequential order id, which is never treated as a lookup credential on its own.
- The logged-in customer's own order-history detail page (`app/[shop]/account/orders/[id]/`) shows a "Download Invoice" link only when `hasInvoice` is true on that order's summary (see backend `customer-account/`'s note) — fetched as an authenticated JS request and turned into a Blob download client-side, not a plain `<a href>`, since the endpoint needs the customer's bearer token attached.

A second effect keyed on `usePathname()` resets stale `selected` state on any real navigation — the actual click/drag listeners never needed "reinitializing" the way a vanilla injected script would, since this component is a normal part of the React tree (mounted once at the root layout) and never loses its `document`-level listeners across either an SPA transition (which never destroys `document`) or a hard reload (which remounts the whole component and re-runs its effects on its own). `admin/components/theme-builder/PreviewFrame.tsx`'s iframe now has an `onLoad` handler that immediately (no debounce) re-posts the current `config`/`legacyTheme` — this only fires on a genuine hard reload of the iframe's document (never an SPA transition), which is exactly the one case where in-memory live-edited state that had only ever reached the iframe via postMessage would otherwise be lost.
- **Drag rework: pointer events, not HTML5 drag-and-drop** — `draggable="true"` + `dragstart`/`dragover`/`drop` gave the browser's own default ghost-image drag and needed every drop target to call `preventDefault()` in `dragover` just to avoid a "not allowed" cursor. Replaced with `pointerdown`/`pointermove`/`pointerup` + `setPointerCapture`, repositioning the dragged element with a live CSS `transform` and resolving the drop target geometrically (which sibling's vertical band the pointer sits in) rather than via native drag events. **Root cause of a real bug found only by testing this live, not by reading the code**: capturing the pointer only once a drag genuinely starts (deferred into the first `pointermove` past the drag threshold, matching how the old code deferred `dragstart`) caused Chrome to fire a spurious `pointercancel` on the very next move and silently drop the capture — traced with `gotpointercapture`/`lostpointercapture` tracing down to Chrome's default native drag-and-drop behavior on `<a>`/`<img>` elements, which are draggable via `-webkit-user-drag: auto` even without `draggable="true"` ever being set; the native drag gesture was winning the race against the still-uncaptured pointer. Fixed two ways together: `setPointerCapture` now happens immediately in `pointerdown` (before the threshold check, not after), and `[data-requital-reorderable="true"]` elements get `-webkit-user-drag: none` in `PREVIEW_MODE_CSS` to disable the browser's native drag path outright. Verified end-to-end via puppeteer with a simulated `document.referrer` (needed since `postToAdmin` no-ops without one) that the full flow — select, drag past a sibling's midpoint, release — posts a correctly-ordered `element-moved` message.

- **Click-to-select silently navigating the preview away instead of selecting, root-caused 2026-08-23**: the `logo`/`cart_icon` (non-drawer layout)/`account_icon` header blocks (`ThemeDrivenHeader.tsx`) are simultaneously tagged `data-requital-editable="true"` (a `PreviewInteraction.tsx` click-to-select target) *and* wrapped in a real `next/link` `<Link>`. `PreviewInteraction.tsx`'s click listener was registered on `document`'s bubble phase (`addEventListener("click", handleClick)`, no capture flag) — but `Link`'s own `onClick` is bound directly on the anchor and always ran first (target phase precedes a bubble-phase ancestor listener), calling `router.push()` before this handler's `preventDefault()` ever ran. Next's `Link.onClick` checks `e.defaultPrevented` before navigating (`node_modules/next/dist/client/link.js`) — since that flag was still `false` when Link's own handler ran, the click silently completed a real client-side navigation instead of ever reaching the tagged element's selection logic. This was masked on Home (the logo's `href` *is* Home, a same-URL no-op) and only became visibly disruptive on any other previewed page (Collection/Product, via the Preview page switcher) — the admin's `previewPath`/dropdown state was never told the iframe had navigated (only the iframe's own in-page router changed, not the `<iframe src>` attribute PreviewFrame.tsx set), so the merchant saw a stale "Collection page" label over Home content, and every further click/drag read as broken against a page that no longer matched what the UI claimed. **Fixed by registering the listener on the capture phase instead** (`document.addEventListener("click", handleClick, true)`) — capture runs before the event ever reaches the target/bubbles to `Link`'s handler, so `preventDefault()` here now actually lands in time. If a future taggable element is *also* a real `<Link>`/anchor, this is the mechanism that keeps it selectable rather than silently navigating away; don't revert this listener back to the bubble phase.
