# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Requital — a multi-tenant e-commerce "shop manager" SaaS (Salla/Zid/Dukan-style), built for UAE/Gulf florists and gift shops. Three independent apps in one repo, sharing nothing but the HTTP boundary:

- `backend/` — NestJS + MySQL (raw `mysql2`, no ORM — see "Database access" below for why), the single source of truth for both frontends. Auth/roles, products (variants, ingredients, attributes, FAQs), collections/templates/menu, orders (kanban + draft orders + returns/refunds + post-purchase survey), outlets, delivery zones (including Slider on-demand courier dispatch), discounts, affiliates, bio-links, dashboard/reporting, search, audit log, theme/SEO settings, WhatsApp integration, payments (Stripe/Tabby/Tamara/PayPal live, three more gateways stubbed behind the same interface), and a platform-admin tier above shop admin. See "Backend architecture" below for the module roster.
- `admin/` — Next.js Admin Panel (merchant-facing). Login/signup, sales dashboard, order management (kanban + history), inventory, collections, discounts, draft orders, bio-links, affiliate program, reports, activity log, Integrations (delivery/payments/messaging/webhooks), a visual theme builder, and a separate `/platform/*` tier for Requital staff. See "Admin frontend" below.
- `storefront/` — Next.js Storefront (customer-facing, per-shop branding, resolved via a `/[shop]/...` slug in the path, or a subdomain/custom domain rewritten onto that same tree — see "Domains" and "Storefront frontend" below). Product browsing with theme-driven homepage layouts, cart, checkout, collections pages, bio page, order tracking, customer accounts.

**Spec docs**: `BUILD_BRIEF.md` at the repo root points to `REQUITAL_SRS.md` as the full source-of-truth spec (Section 6 has the data model) — the SRS itself is not present in the working tree; note that rather than guessing at requirements from memory if you need it. The SRS describes some things not yet built (i18n + Arabic/RTL, multi-currency — single-currency AED throughout today) and lists some things as future work that **have since been built** (multi-outlet, the Kanban pipeline, unlimited-depth attributes/variations, a Customers module). The SRS's separate-top-level-domain-per-merchant plan was also **not** what got built — tenant resolution is a `/[shop]/...` slug segment instead.

**Other reference docs**: `docs/runbook.md` (backup/restore via `tools/backup-db.sh`, plus a migration-rollback reference) — check before any destructive DB operation. `docs/audit-2026-08.md` is a full verification sweep with a consolidated findings list — check it before assuming an area is unaudited.

## Git workflow — branch protection is on

`main` has branch protection: PRs required, four CI jobs (`backend`, `admin`, `storefront`, `guardrails` — see `.github/workflows/ci.yml`) are required status checks. Direct pushes to `main` are rejected by GitHub. Every phase of work is: branch off `main` → open a PR → get the four checks green → the user merges it. Never push directly to `main`, and never merge a PR yourself even once CI is green — merging is the user's call.

## Tenant isolation and outlet scoping

Every tenant-owned table carries `shopId`, and every query against one is scoped by it at the data-access layer. `shopId`/`outletId` are always derived from the authenticated user, re-read from the DB on every request — never trusted from a token claim or request body.

- **`AuthGuard`** (`backend/src/auth/guards/auth.guard.ts`) verifies the session, re-fetches the user from the DB (not trusting token claims for role/outlet/suspension), and attaches a `TenantContext` (`backend/src/common/tenant-context.ts`: `{ userId, shopId, role, outletId: number | null }`) via `@CurrentUser()`. Re-reading every request means a role change, outlet reassignment, or shop suspension takes effect immediately, not at next login.
- **`RolesGuard`** + `@Roles(...)` gates by role; both are `APP_GUARD` providers in `AuthModule`, so routes are protected by default and opt out with `@Public()`.
- **Four roles**: `admin` (full shop, all outlets), `branch` (pinned to exactly one outlet — `resolveOutletFilter` below), `order_manager` (shop-wide, Orders/Draft Orders only), `viewer` (shop-wide read-only). Signup always creates a Shop + a default Outlet + an Admin user in one transaction; only admins create other staff.
- **`resolveOutletFilter(ctx, requestedOutletId?)`** (`backend/src/common/outlet-scope.ts`) is the single shared helper: a `branch` user's `ctx.outletId` always wins over what the request asked for; an `admin` gets the requested outlet or `undefined` (no filter). Route every outlet-scoped read/write through this — don't hand-roll the branch/admin distinction. **Gotcha**: never build a `where` clause as `{ id, shopId, ...(role==='branch' && { id: ctx.outletId }) }` — the spread silently overwrites the requested `id` last, turning "reject mismatched outlet" into "silently substitute my own outlet." Check `id !== ctx.outletId` explicitly instead.
- **A stock write taking an `outletId` param must verify it belongs to `ctx.shopId` before using it** — this exact omission recurred twice for real (`confirmImportIngredients`/`confirmImportProducts`) before every outlet-taking write got a consistent `outlet.findFirst({ id, shopId })` guard. `node tools/check-outlet-scoping.js` is a grep-based guardrail flagging any backend method taking an `outletId` param with no adjacent ownership-check marker — run it after adding/editing one; it has a documented `ALLOWLIST` for genuinely-safe cases.
- **Catalog vs. stock split**: Products/Collections are shop-scoped (one catalog across all outlets). Stock is not — `outletstock` (composite PK `[outletId, productId]`), not `product.stockQuantity` (doesn't exist). `trackInventory` stays on `Product` (catalog-level policy). `GET /products` returns `stockQuantity: null` (not `0`) when no outlet is resolved.
- **Orders are outlet-scoped**: `order.outletId` is required. On create, a branch user's `outletId` is always forced server-side to `ctx.outletId` — any value they supply is ignored.
- **`backend/test/security-outlet-isolation.e2e-spec.ts`** spoofs `outletId`/order ids across outlets and shops on every outlet-scoped endpoint, asserting each either re-scopes or 404s. Run it (`npm run test:e2e -- security-outlet-isolation`) after touching any tenant/outlet-scoped query path.

### Branch-specific roles — a permission layer on top of the 4-tier system

A per-`(user, outlet)` override that can only *restrict* a staff member's shop-wide role at one outlet — additive, zero behavior change for a shop that never assigns one.

- `branchrole` (shopId, name, `permissions` — a JSON array from the fixed vocabulary in `common/permissions.ts`) is an admin-defined bundle; `useroutletrole` (userId, outletId, branchRoleId) points a staff member + outlet at one.
- **The security guarantee is an intersection, not a convention**: `BranchRolesService.resolveEffectivePermissions(ctx, outletId)` returns `null` when no override exists (callers fall through to plain `ctx.role` logic); when one does exist, the effective set is `intersection(basePermissionsFor(ctx.role), branchrole.permissions)` — structurally incapable of granting more than the user's shop-wide ceiling. `assertPermission(ctx, outletId, permission)` is the thin wrapper every call site invokes.
- Wired into orders, products (catalog + stock), dashboard, ingredients, payments, search, delivery-zones, outlets — not draft-orders/reports/scan (`'branch'` can't reach those controllers today). Two rules for a new call site: list/aggregate endpoints (outlet unresolved) skip the check entirely; single-resource endpoints must check against the *fetched resource's own* outletId, not the pre-fetch filter.
- `backend/test/branch-roles.e2e-spec.ts` has the adversarial pattern to extend: cross-shop spoofing, plus an HTTP-level "permission escalation" test proving an over-generous assignment on a shop-wide `viewer` still can't unlock `orders.manage`.

## Next.js version warning

This is Next 16, which has breaking API/convention changes from what training data assumes — read `node_modules/next/dist/docs/` before writing Next.js code in `admin/` or `storefront/` (each has its own `AGENTS.md` reiterating this, auto-regenerated by `next dev`; commit it if it shows as changed). Confirmed in practice: route `params`/`searchParams` are `Promise`s that must be `await`ed in Server Components; client components use `useParams()`/`useSearchParams()` instead of destructuring props; middleware is renamed `proxy.ts`.

## Commands

### backend/ (NestJS)

```bash
npm run start:dev        # dev server with watch mode, http://localhost:3000 (see port note below)
npm run build             # nest build
npm run lint               # eslint --fix
npm run test                # jest, all unit tests (*.spec.ts, colocated with source)
npm run test -- app.controller     # run a single spec by filename match
npm run test:watch
npm run test:e2e            # jest against test/*.e2e-spec.ts (real AppModule + real dev MySQL DB, not mocked)
npm run test:e2e -- security-outlet-isolation   # run a single e2e spec by filename match
```

**`npm run build` can silently emit nothing if `dist/` was ever deleted out from under a stale incremental cache.** `nest-cli.json`'s `deleteOutDir: true` wipes `dist/` before compiling; `tsconfig.build.json`'s `tsBuildInfoFile` now lives inside `dist/` specifically so it gets wiped together with it (it used to live at the project root, outside `dist/`, so a wipe left tsc consulting a cache that believed every file was already up to date — zero output, exit code 0, and pm2 then fails with `Cannot find module '.../dist/main.js'`). If a build ever again reports success but `dist/main.js` is missing, `rm -rf dist` and rebuild — this has recurred on both local dev and a VPS deploy since the fix, always from the same root cause (a stale `dist/` wiped by something outside a normal `npm run build`).

Migrations are hand-authored plain MySQL DDL (`prisma/migrations/*/migration.sql`, one timestamped folder per migration — the directory name is a holdover from this backend's pre-2026-08-11 Prisma incarnation, kept since every migration's content was already plain SQL):

```bash
npm run db:migrate                           # applies any pending migration folders (scripts/migrate.ts)
npm run db:seed                              # seeds the dev shop/admin/starter products (scripts/seed.ts)
```

Make the timestamped folder by hand and write `migration.sql` yourself (expand/contract for anything backfilled: nullable column → `UPDATE ... JOIN` backfill → `NOT NULL` → FK/index). `scripts/migrate.ts` applies every folder in filename order, tracking applied folders in a plain `_migrations` table.

**A migration's folder timestamp is the only thing enforcing its position in the apply order — nothing checks that its SQL only references tables/columns created by an earlier folder.** This has caused a real failure (an `ALTER TABLE outlet` migration timestamped before the migration that `CREATE TABLE outlet`d it) that was invisible against the long-lived local dev DB but fatal against a genuinely clean database — the only place this bug class is ever exercised is CI's `db:migrate` step against a fresh service-container DB (see `.github/workflows/ci.yml`); treat a migration failure there as this bug class, not a flake. Fix pattern: don't edit an already-applied migration's SQL in place — empty it to a no-op (every existing DB already has it recorded as applied) and move its real SQL into a new, correctly-ordered folder.

`backend/.env` holds `DATABASE_URL` (MySQL — **percent-encode special characters in the password**, e.g. `#`→`%23`, `@`→`%40`, or the connection string silently breaks), `JWT_SECRET` (staff), `CUSTOMER_JWT_SECRET` (customer, genuinely separate secret), `PLATFORM_JWT_SECRET` (platform admin, genuinely separate), `CSRF_SECRET`, `CREDENTIAL_ENCRYPTION_KEY` (encrypts per-shop payment/WhatsApp credentials, `common/crypto.ts`), `ADMIN_ORIGINS` (CORS allowlist), `ADMIN_URL`/`STOREFRONT_URL` (reset-password/verify-email/invite/payment-link URLs). Per-gateway platform-level fallback credentials (`STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`, `TELR_STORE_ID`/`TELR_AUTH_KEY`, `PAYTABS_PROFILE_ID`/`PAYTABS_SERVER_KEY`, `TABBY_PUBLIC_KEY`/`TABBY_SECRET_KEY`/`TABBY_WEBHOOK_SECRET`, `TAMARA_PUBLIC_KEY`/`TAMARA_API_URL`/`TAMARA_TOKEN`/`TAMARA_NOTIFICATION_TOKEN`, `PAYPAL_CLIENT_ID`/`PAYPAL_CLIENT_SECRET`/`PAYPAL_WEBHOOK_ID`/`PAYPAL_API_URL`) are used only when a shop hasn't configured its own — see "Payments" below. `RESEND_API_KEY`/`EMAIL_FROM_ADDRESS` are the same shape for email. `PLATFORM_WHATSAPP_PHONE_NUMBER_ID`/`PLATFORM_WHATSAPP_ACCESS_TOKEN` are for the one Requital-owned WhatsApp account that alerts merchants of new orders (not bring-your-own-keys). `SLIDER_API_KEY`/`SLIDER_ENVIRONMENT`/`SLIDER_WEBHOOK_TOKEN` are the platform-level Slider partner credentials — the *only* credential shape for that integration, not a fallback (see "Slider on-demand delivery" below). There is no `.env.example`. e2e specs `import 'dotenv/config'` at the top since `main.ts`'s bootstrap never runs under Jest.

`scripts/seed.ts` creates a dev admin login: `admin@test-shop.com` / `dev-password-123`, plus a "Main Branch" outlet.

### admin/ and storefront/ (Next.js)

```bash
npm run dev      # next dev
npm run build    # next build
npm run lint      # eslint
npm run test      # vitest run — unit tests for pure/testable logic, colocated as *.test.ts(x)
npm run test -- ProductForm     # run a single spec by filename match
```

Both apps' `.env.local` sets `NEXT_PUBLIC_API_URL` (defaults to `http://localhost:3000`); no server actions/route handlers. **Admin** calls the backend directly from the browser (`admin.requital.io` → `api.requital.io`, cross-origin but same-site). **Storefront** calls a **relative `/api/*` path** which `next.config.ts` rewrites to `${NEXT_PUBLIC_API_URL}/*` server-side (docs/plans/custom-domain-resolver.md Phase 5) — every storefront→API request is same-origin with the storefront host, so `SameSite=Strict` customer cookies are actually sent on a connected custom domain. **Port note**: none of the three apps pin a port. Backend takes 3000 if started first; whichever Next app starts next auto-increments (admin → 3001, storefront → 3002). Simultaneous startup is a race (Next binds faster than Nest) — start backend, wait for it to respond, then start the Next apps.

### Checking lint delta without mutating files

Each app has a `lint-baseline.txt` (a plain integer) tracking accepted pre-existing lint debt. To check whether a change introduced *new* debt: `node tools/check-lint-baseline.js <backend|admin|storefront>` from the repo root (same command CI's `guardrails`/per-app jobs run). It runs eslint in `--fix-dry-run` mode and only reports the count — never writes to disk. **Don't substitute a plain `npm run lint` for this, especially in `backend/`** — that script is `eslint --fix` and will silently reformat every fixable file in the app, not just the ones you touched. If the checker reports a genuine new delta, either fix the finding or bump `lint-baseline.txt` with a one-line dated reason (see the "Known lint gaps" notes below each app's section for the format).

Two more guardrails run in CI's `guardrails` job: `node tools/check-no-console-log.js` (backend-only — flags a raw `console.log`/`warn`/`error`/`debug`/`info` in `backend/src`, which bypasses the structured logger's request-id/shopId/redaction pipeline) and `node tools/check-form-width.js` (see "Page width convention" below). `tools/backup-db.sh` and its restore counterpart are documented in `docs/runbook.md`.

### e2e/ (Playwright, cross-app)

Drives all three apps together through a real browser — 4 critical paths (merchant onboarding, customer checkout, order kanban, password reset), not full coverage. Needs all three apps already running on their expected ports (backend :3000 first, then `-p 3001`/`-p 3002` for admin/storefront):

```bash
cd e2e && npm install && npx playwright install --with-deps chromium   # one-time
npm test
```

Each run seeds a fresh shop via the real backend API (`global-setup.ts` → `seed.ts`) with a timestamp-suffixed subdomain, so repeated runs never collide. Tests run serially (`workers: 1`) — the kanban spec advances the one seeded order's own status, so parallel workers would race. See `e2e/README.md` for the per-spec breakdown.

## Backend architecture

- **Database access is plain `mysql2`, not an ORM (migrated off Prisma).** Prisma's Rust query engine crashed on the shared-hosting deploy target — CloudLinux's per-account thread cap couldn't accommodate the engine's own thread spawning. `DatabaseModule` (`src/database/`) is `@Global()`; `DatabaseService` wraps a `mysql2` pool with `.query<T>(sql, params)` (SELECT), `.execute(sql, params)` (INSERT/UPDATE/DELETE, returns `ResultSetHeader`), and `.transaction(async (conn) => {...})`. `src/db/types.ts` has a hand-maintained `<Model>Row` interface per table — no code generation, update it by hand alongside any migration that changes a column. `src/database/upsert.util.ts`'s `upsert()` wraps `INSERT ... ON DUPLICATE KEY UPDATE` for composite-key models. `src/database/mysql-errors.ts`'s `isDuplicateKeyError`/`isLockConflict` check errno 1062/1213/1205. `src/database/decimal.util.ts`'s `trimDecimal()` trims mysql2's full-precision `DECIMAL(65,30)` string output back to a plain string at API response boundaries — only needed for *unannotated*-scale decimal columns, not fixed-scale ones. The batch-load-then-assemble pattern (parallel `WHERE...IN` queries + a JS `Map` grouping step, replacing a Prisma nested `include`) recurs wherever a list endpoint fetches several relations — see `ProductsService.loadProductsWithRelations`/`PublicService.loadPublicProductsWithRelations` as the pattern to follow for a new one. TINYINT(1) and JSON columns come back already the right JS shape (real booleans, parsed objects/arrays) via the pool config — **but this is keyed off the column's real MySQL type, not "is this JSON-shaped data"**: a `LONGTEXT` column with only a `CHECK (json_valid(...))` constraint is *not* a real JSON column and does not get auto-parsed. This bug class has hit twice for real — `job.payload` (fixed by `JobsService.parseJobRow()`) and `themesettings.notificationText`/`contactNumbers`/`colors` (fixed by converting the columns to real `JSON` type, sanitizing any non-JSON-valid existing value to `NULL` *before* the `ALTER` since MySQL validates on `MODIFY COLUMN ... JSON`). If a future column follows this same LONGTEXT-plus-CHECK pattern, it needs an explicit `JSON.parse` at its own read sites — the auto-parsing guarantee doesn't extend to it for free.
- **Feature modules** follow the standard Nest triad (`.module.ts`/`.controller.ts`/`.service.ts`, DTOs in `dto/`). Module roster, each a self-contained domain:
  - `collections/` — the product taxonomy tree (unlimited depth, cycle-guarded), with `PATCH /collections/reorder` for admin drag-and-drop. (Renamed from `categories/`; the pre-rename `collections/` — marketing groupings — is now `templates/`. `ingredientcategory`/`ingredient-categories/` is unrelated, untouched by that rename.)
  - `brands/` (added 2026-08-29) — a first-class product brand/manufacturer, shop-scoped like collections. `brand` table (`shopId`, `name`, `logoUrl`, unique `[shopId, name]`); `product.brandId` is a nullable FK with `ON DELETE SET NULL` (deleting a brand never cascades into products — `BrandsService.remove` also nulls affected rows explicitly inside the delete transaction). Standard admin CRUD (`/brands`, writes admin-only, reads any authed role); `GET /public/:shopSlug/brands` returns only brands with an Available product; `GET /public/:shopSlug/products?brandId=` filters. Product loaders (`ProductsService.loadProductsWithRelations` + `PublicService.loadPublicProductsWithRelations`) attach `brand: {id,name,logoUrl} | null`. CSV import is deliberately not brand-aware.
  - `templates/` — marketing-driven product groupings: `MANUAL` (explicit ordered list), `RULE_BASED` (collection/tag/price/age conditions computed live), or `COLLECTION_GROUP` (a curated list of Collections via `templatecollection`, effective product list = union of members' products) — deliberately separate from `collections/`, the taxonomy tree.
  - `menu/` — the storefront top bar's configurable menu: `menuitem` rows, each `LINK` (one Collection) or `DROPDOWN` (several via `menuitemcollection`). Falls back to an auto-generated top-level-Collections pill list when unconfigured.
  - `returns/` — post-delivery returns/refunds: per-line-item and running-total caps, provider-refund-with-manual-fallback, restock via the same stock-movement pattern orders use.
  - `draft-orders/` — quotes/manual invoices that become a real `order` on completion; reuses `PaymentsService.generateLink` for "send invoice."
  - `invoices/` — invoice/packing-slip document generation for an already-placed order. One row per `(orderId, type)`, `@@unique` makes `generateForOrder` idempotent; `invoiceNumber` comes from a per-`(shopId, type)` counter row incremented via `INSERT ... ON DUPLICATE KEY UPDATE lastNumber = LAST_INSERT_ID(...)` — both the seed and increment branches must wrap the value in `LAST_INSERT_ID(...)`, or a later `SELECT LAST_INSERT_ID()` on the pooled connection can read back an unrelated insert. No PDF library — `GET /invoices/:id/pdf` serves styled `text/html`, relying on the browser's Print → Save as PDF. Staff-only; the storefront's own "Download Invoice" goes through `customer-account`'s separate, customer-scoped endpoint.
  - `discounts/` — promo codes; redemption is claimed atomically at order-creation time (same CAS philosophy as webhook idempotency below).
  - `bio-links/` — a "link in bio" page builder; each link has exactly one target type (`EXTERNAL_URL`/`PRODUCT`/`CATEGORY`/`COLLECTION`/`SOCIAL_ICON`) via a discriminated-fields pattern (`assertFieldsMatchType` in `bio-links.service.ts`) — follow it for a 6th type.
  - `affiliate/` — referral codes + attributed order tracking and payout summary.
  - `ingredients/` — raw materials tracked for stock but never sold; deliberately separate from `product` (no price/SKU/variants/SEO), no code path from `src/public`.
  - `delivery-zones/`, `external-deliveries/` — per-outlet delivery zone config (see "Delivery zones" below), and logging a third-party courier handoff for orders not delivered in-house (also see "Slider on-demand delivery").
  - `customers/` — the shared customer record for both storefront checkout and the admin CRM, upserted by `[shopId, phone]` with a P2002-race fallback; order count/LTV computed live, excluding cancelled orders, never stored.
  - `customer-auth/` — a fully separate JWT/refresh stack for shoppers, parallel to but independent from staff `auth`; "register" just sets a password on the same `[shopId, phone]` customer row guest checkout already created.
  - `customer-account/` — the storefront "my account" API. Addresses are a JSON array on `customer`, not their own table. Owns UAE PDPL self-service: `GET .../account/export` (rate-limited once/24h) and the two-step `DELETE .../account/me` → `.../me/confirm?token=` deletion flow, which *anonymises* (scrubs PII, clears `passwordHash`) rather than hard-deletes — orders/draftorder/giftcard rows keep the real `customerId` FK. Clearing `passwordHash` is what revokes every outstanding access token immediately (`CustomerAuthGuard` re-reads the row every request).
  - `abandoned-carts/` — checkout-progress capture (name+phone before order completes), upserted on `[shopId, customerPhone]`; recovery emails are cron-swept but CAS-claimed row-by-row.
  - `gift-cards/` — real `giftcard`/`giftcardredemption` models (not fields on `product` — those only configure *selling* a gift-card product); redeem/credit-refund are CAS balance updates inside the same transaction as order creation/return; buying quantity N issues N independent single-balance cards.
  - `notify-subscriptions/` — back-in-stock subscriptions, idempotent per `(shopId, productId, variantId, email)`, soft-rate-limited to 3/hour/email/shop. Fires from every real 0→positive stock-crossing point (manual adjust, transfer, cancellation restock) — not from CSV import or scan-to-stock (deliberate scope cut).
  - `storefront-search/` — public, typo-tolerant customer-facing search (separate from admin `search/` below). Exact substring match first, falls back to `fuse.js` fuzzy matching only when exact returns nothing. Cached per `(shopId, query)` for 60s in an in-memory `Map`.
  - `reports/` — read-only aggregation with no dedicated tables, querying `order`/`orderitem` directly. General Report does NOT exclude cancelled orders (raw audit view); Product Sales Report does (matching Dashboard's convention).
  - `common/nominatim.ts` — a shared proxy to OSM Nominatim (free-tier rate limits, only ever called from a manual map click/pin-drag, never autocomplete-as-you-type), used by outlets and public/checkout.
  - `search/`, `audit-log/` — admin-only cross-entity search and an append-only staff-action log (`AuditLogService.log` swallows its own write errors so a broken audit insert never fails the real operation).
  - `theme/`, `seo/`, `whatsapp/` — the *legacy* theme/branding settings row, SEO metadata, WhatsApp integration credentials (encrypted at rest). See "Storefront frontend" for how this relates to the newer `themes/` (Sections builder) module.
  - `themes/templates.ts` (Phase G0, 2026-09-04) — `THEME_TEMPLATES: Record<TemplateKey, ThemeConfig>` (Atelier / Market / Bloom / Heritage): four **full, explicitly-typed `ThemeConfig` literals** built by deep-cloning `DEFAULT_THEME_CONFIG` and overriding. The `: ThemeConfig` annotation is the primary drift guard (`tsc` enforces the current shape — stronger than the shallow `assertValidThemeConfig`); the belt is one `accepts THEME_TEMPLATES.<key> unchanged` validation case + a per-template clone / byte-cap / scheme-ref spec (`templates.spec.ts`). Held to the same in-lockstep-with-`theme-config.types.ts` discipline as `DEFAULT_THEME_CONFIG`. **G0 scope: a template sets only keys that render today (Phases A + B — motion / radius / density / typography pairing+scale / colour schemes / product-card style+aspect / sale-price / shipped section types); zero keys without a live consumer, so there is nothing to no-op.** Each template's `// ── Deferred to C–F ──` block is the re-author checklist; `animations.addToCart` / `pageTransition` are deliberately `false` (no silent behaviour change when a later phase's consumer lands). Flow A only: `POST /themes { fromTemplate }` (`CreateThemeDto`, `@IsIn(TEMPLATE_KEYS)`, mutually exclusive with `duplicateFromId`) → a new **unpublished** row via `cloneConfigWithFreshIds` (regenerates every id + remaps scheme refs); the merchant's live theme is never read or written. `GET /themes/templates` returns preview metadata only (name / blurb / `previewColors`) for the admin library picker — the full config only ever leaves the server as a created row. Flow B (`applyTemplate` + confirm modal, D1/D3) is deferred to G1.
  - `policy-pages/` — the 5 fixed legal page types, one `policypage` row per type per shop (unwritten types have no row).
  - `public/` — the storefront's entire backend surface, mounted at `/public/:shopSlug/...`. No auth; every response shape is separate and narrower than the admin-facing equivalent. A globally-unique-token feature (order tracking, the post-purchase survey) gets its own narrow, un-slugged controller instead, since the token alone is self-sufficient.
- **Validation**: a global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true, transform: true`) — unvalidated fields are silently stripped. Type-only imports referenced in a decorated class member need `import type`, or the build fails under `isolatedModules` + `emitDecoratorMetadata`.
- **Auth mechanism**: hand-rolled JWT (`@nestjs/jwt`, no Passport) and `bcryptjs` (pure JS, avoids node-gyp on Windows). Three independent token tiers — staff, customer, platform admin — each with its own JWT secret and cookie names, so one tier's token structurally cannot validate against another's guard. All three now live as **httpOnly, `SameSite=Strict` cookies**, not `localStorage`/`Authorization` headers (a 2026-08 migration off the original bearer-token design, closing an XSS-exfiltration finding). **Cookie-name prefixes (`common/cookies.ts`)**: `__Host-` for a cookie at `Path=/` (staff/platform access), `__Secure-` for one deliberately scoped to a sub-path (`pathScopedCookieName` — customer access/refresh/CSRF at `/public/<slug>`, staff refresh at `/auth/refresh`). `__Host-` mandates `Path=/`, so a `__Host-...; Path=/public/x` cookie is silently dropped by every browser — using it on the sub-path cookies was a real latent bug (customer sessions never persisted in prod) fixed in Phase 5 of the custom-domain work. `isProd()` is a function (not a load-time const) so a test can exercise the production shapes. CSRF protection is mandatory alongside this, not optional — see the "CSRF" bullet under Platform admin below for why `SameSite=Strict` alone doesn't cover this platform's threat model (open self-signup means an attacker can host arbitrary HTML on their own same-site `{shop}.requital.io`). Every route is protected by default (`APP_GUARD`); `@Public()` opts out, `@Roles('admin')` restricts further.
- **Table naming**: lowercase singular (`product`, `order`, `outletstock`, ...) — a holdover from this backend's original Prisma-modeled naming, now the real on-disk names. **This only works because local MySQL is case-insensitive for identifiers (Windows default) — a genuinely case-sensitive MySQL host (confirmed for real against Linux CI) can silently disagree with the migration history if a table was ever created with different casing than later migrations reference it with.** If you ever add a migration that creates a table, use the same lowercase-singular casing everywhere from the start — retrofitting a case mismatch later needs a `PREPARE`/`EXECUTE`-wrapped conditional rename (MySQL has no `RENAME TABLE IF EXISTS`) checked with `BINARY table_name = '...'` (a plain `=` compares case-insensitively by default and will fire the rename against a table that doesn't actually need it).
- **Many-to-many relations** use explicit join tables with a composite primary key (`productcollection`, `producttag`, `outletstock`), not a surrogate `id` — follow this for new join tables.
- **Product images are upserted by `url` on update, not deleted-and-recreated.** `ProductsService.update` matches `dto.images` against existing `productimage` rows by url, updating `order` in place and only creating/deleting genuinely added/removed urls. This matters because `productvariant.imageId` is `onDelete: SetNull` and the edit form always resends the full `images` array — a naive delete-all-then-recreate assigns every image a fresh id on every save, silently wiping every variant's image assignment on the next unrelated edit.
- **Two patterns for a per-product child list, chosen by whether it drives variant generation.** `productimage`/`productattribute`/`productfaq` are plain ordered lists embedded directly in the product DTO (full-replace on update). `productoption`/`productvariant` get their own `PUT /products/:id/options`, since changing them regenerates the variant cartesian product with id-preserving reconciliation — a side effect a DTO field can't express. Embed a new simple list in the DTO; only reach for a standalone endpoint if it needs real generation/reconciliation logic.
- **`product.isCheckoutAddon`** flags a product for the checkout's "would you like to add extras?" popup — a plain catalog flag, no separate config table.
- **`orderitem.note`** is an optional customer-typed note from the storefront PDP, carried verbatim to `orderitem.note` — no parsing or merchant editing. Distinct from `ordernote` (staff-authored order-level thread) and `order.deliveryNotes`.
- **Order status transitions are compare-and-swap, not read-then-write.** `OrdersService.updateStatus`/`.cancel` re-check the row's status inside the transaction via `updateMany({ where: { id, status: <expected>, outletId } })` and inspect `result.count` — this is load-bearing. A plain `findOne` then `update` has a real race (two concurrent "confirm" calls both reading `pending`, both decrementing stock); CAS means only one write matches, the loser gets a 409. Follow this pattern for any future status-driven side effect.
- **Stock is decremented on `pending → confirmed`, not on order creation** (an abandoned cart never holds stock hostage), restored on cancellation from any status where it was already decremented. Keyed by `[outletId, productId]` in `outletstock`.
- **Editing a confirmed order's item quantities adjusts BOM ingredient stock by delta, not a from-scratch recompute** — `OrdersService.updateItems` only touches `outletingredientstock` when the order is confirmed and ingredients were actually consumed. A quantity increase never blocks the save even into negative ingredient stock, surfacing `ingredientStockWarnings` instead; a decrease returns its own delta unconditionally.
- **Payments use a strategy pattern, resolved per-shop.** `payments/payment-provider.interface.ts` defines `PaymentProvider`; `payments/providers/` has one file per gateway, `PaymentProviderRegistry` registers implemented ones at boot. Per-shop credentials resolve via `PaymentSettingsService.resolveCredentials` (encrypted at rest) and fall back to the platform env var. The Stripe client is constructed lazily per-key so a shop without its own keys doesn't crash the app at boot.
- **Payment provider toggle-bypass guard — a bug class that has recurred repeatedly in this codebase.** Whether a gateway is actually usable (real, non-empty credentials) must be checked *inside* the provider's own `createCheckoutSession`/`parseWebhookEvent`, throwing `PaymentProviderNotConfiguredException` — not only by whatever outer caller resolved credentials or checked `enabled` first. An outer-only check is exactly what's been bypassed each time by some other call path that forgot to repeat it. See `TabbyPaymentProvider`/`TamaraPaymentProvider`'s "MANDATORY GUARD" comments for the pattern to copy when adding a real 4th provider.
- **BNPL webhooks can drive the order's own status**, not just `paymentStatus` — `WebhookResult.advanceOrderStatus` runs the order through the same CAS state machine `OrdersController`'s status/cancel endpoints use, under a synthesized system context. Only ever applied while the order is still `pending` — a stale approval/expiry signal is silently ignored, never forced through.
- **Refunds reuse the webhook's charge reference, not the event id.** `paymenttransaction.gatewayReference` is the webhook *event* id (for the delivery-idempotency unique constraint only); a real refund needs `providerChargeReference` instead.
- **Webhook idempotency**: `paymenttransaction` has a unique constraint on `(gateway, gatewayReference)`, keyed by the gateway's event id (not the object the event is about). `PaymentsService.handleWebhook` relies on that constraint failing — catching both `isDuplicateKeyError` and `isLockConflict` (observed under truly concurrent duplicate delivery) as "already processed." Don't replace with a `findFirst`-then-`create` check — that reopens the TOCTOU race this design avoids.
- **Raw body for webhooks**: `main.ts` passes `{ rawBody: true }`; the webhook controller reads `req.rawBody` since Stripe signature verification needs the exact unparsed bytes.
- **Dashboard date math is UAE-local (UTC+4), hardcoded**, not server-local/UTC — UAE doesn't observe DST, so this is stable.
- **CORS**: `main.ts`'s `origin` is a function, not a static allowlist — `ADMIN_ORIGINS` array fast-path, then a `/^https:\/\/([a-z0-9-]+\.)?requital\.io$/` regex covering every subdomain (admin lives here), then `DomainsService.isCustomDomain` for anything else. `credentials: true` and `exposedHeaders: ['X-CSRF-Token']` are both required by the cookie/CSRF auth design (see Platform admin below). Since the storefront's same-origin `/api/*` proxy (Phase 5, above), the storefront browser no longer calls this API cross-origin from a custom domain — the `isCustomDomain` branch is now a safety net for any *other* cross-origin caller on a connected custom domain, not load-bearing for normal storefront traffic (kept because "no other caller" can't be fully proven).
- **Email sending** (`common/email.ts`) is platform-level, not per-shop — one Resend API key/verified domain (`resend-email.provider.ts`, plain `fetch`, no SDK). `sendEmail()` falls back to a stub (console.log) whenever the key is unset or the real call fails — never throws. `RESEND_API_KEY=test` is a reserved sentinel forcing the stub with no network call, which is what local `.env` and e2e use. Every call site must go through `sendEmail()`, never the stub directly — `common/email-callsites.spec.ts` enforces this statically. Sends as generic `Requital <noreply@requital.io>`, not the merchant's own name (per-shop sending was planned but the display-name domain was never actually verified with Resend).
- **WhatsApp order alerts (platform-owned)** are separate from the per-shop bring-your-own-credentials `WhatsAppProvider` in `whatsapp/`. One Requital-owned WhatsApp Business account (env-configured) messages the merchant's own outlet on every new order — `common/whatsapp.ts`'s `sendPlatformWhatsAppAlertOrThrow`, queued through the same DB-backed job queue `send_email` uses. Recipient is `outlet.whatsapp` (falling back to `outlet.phone`), never `shop.whatsappNumber` or `user.phone`.
- **`SignupDto`'s wizard-only fields are all `@IsOptional()` at the DTO level**, even though the admin Account Setup wizard treats most as required — dozens of e2e specs call `POST /auth/signup` with the old minimal payload. "Required" is enforced client-side only.
- **Lint baseline**: `backend/lint-baseline.txt` currently tracks 261 pre-existing findings. It climbed 287 → 297 → 325 across 2026-08-30..09-02 as every new `theme-config.validation.spec.ts` case added `no-unsafe-*` findings against a deliberately `any`-typed `baseConfig()` fixture — then **dropped 325 → 261 on 2026-09-02 (cleanup batch)** when `baseConfig()` was given a real `: ThemeConfig` return type. The ~5 adversarial cases that must construct a structurally-invalid config now carry a narrow `as unknown as …` cast at the exact bad value instead, so a future *valid*-data case can't silently re-inflate the count. Former category (2) (the `any` fixture) is retired — `theme-config.validation.spec.ts`'s `baseConfig()` is now `: ThemeConfig`; a new *valid*-data validation case adds no lint findings, so it should not bump the baseline. The one remaining dominant, already-reviewed-and-accepted category: the standard Jest-mock-typing false positive (`unbound-method` on `expect(mock.method).toHaveBeenCalledWith`, `no-unsafe-*` on a loosely-typed mock/`RowDataPacket` result) — cosmetic, not a real bug. When a change adds new instances of that shape, bump the baseline with a one-line dated note (`raised N → M on YYYY-MM-DD (what changed): why`) rather than fighting the mock's typing. A genuinely new, unrelated finding should be fixed outright, not folded into the baseline.

## Domains — subdomain and custom domain configuration

A shop's storefront is reachable at `{subdomain}.requital.io` or a merchant-connected custom domain, via `shop.domainType` (`'subdomain' | 'custom'`). `shop.subdomain` is set once at signup, immutable after; `shop.customDomain` and `domainType` are the core columns. `RESERVED_SUBDOMAINS` (`shop/constants.ts`, mirrored by hand in `admin/lib/validators.ts`) blocks collisions with real platform hostnames.

**Custom-domain ownership verification (`docs/plans/custom-domain-resolver.md` Phase 2, landed 2026-08-31).** A custom domain is only served (and only cert-eligible) once the merchant proves control via a DNS TXT record. State lives on `shop`: `customDomainStatus` (`null` | `pending` | `verifying` | `verified` | `failed`), `customDomainVerifyToken` (per-claim random, rotated on every re-save / disconnect), `customDomainClaimedAt` / `customDomainLastCheckedAt` / `customDomainVerifiedAt`. **CD2**: `shop.customDomain` is no longer plainly `UNIQUE` — several shops may hold a `pending`/`verifying` claim on the same hostname at once; exclusivity is enforced only for `verified` rows, via the DB-generated `customDomainVerifiedKey` column (`= customDomain` while verified, else `NULL`) + a `UNIQUE` index over it. `CustomDomainVerificationService` (`shop/`) does the DNS-TXT check (CAS transitions, DNS lookup outside any transaction) for both `POST /shop/domain/verify` ("Verify now") and a `@Cron` recheck sweep (`runLocked('custom-domain-verify-sweep', …)`; 5-min ticks, backoff 5m→30m→60m keyed off claim age, `failed` after 48h). `irmain.com` (real live merchant) was grandfathered straight to `verified` in the migration to avoid an outage — **a flagged fast-follow: it has never actually passed the DNS-TXT check**, see the plan doc.

- **`GET`/`PATCH /shop/domain`** validates the hostname (`shop/domain-validation.ts`, mirrored by hand in `admin/lib/validators.ts` — keep the two in sync). `isValidCustomDomain` rejects Requital-owned hostnames: the bare `requital.io` apex, anything ending `.requital.io` (which is what actually covers every reserved subdomain in one shot), and a bare `RESERVED_SUBDOMAINS` label. `PATCH` with `type: 'custom'` starts a fresh `pending` claim (new token) — re-saving the same domain re-arms verification from scratch, which is how the merchant "retries" after a `failed` claim; it 409s only if another shop has already **verified** that exact domain (the generated-key unique index is the hard backstop at verify time). `GET` returns `status` + a `verification: {recordName, recordValue}` block (the TXT record to add) while a claim is unverified (so also on `failed`). `getDomainConfig` does **not** expose `customDomainClaimedAt` — the merchant UI shows a static propagation hint, not an elapsed-time counter.
- **Merchant UI (`docs/plans/custom-domain-resolver.md` Phase 3, landed 2026-08-31): `admin/app/settings/business/domain/page.tsx`** (Settings → Business Settings → Domain, in `BusinessSettingsSubNav`). Consumes the endpoints above via `getShopDomain` / `updateShopDomain` / `verifyShopDomain` (`admin/lib/api.ts`) — five states keyed off `status`: subdomain-only (Connect form), pending/verifying (shows the TXT record + "Verify now" + a 15s poll so a sweep-driven transition shows without a refresh), verified (Disconnect, behind a confirm modal), failed (Retry = re-save the same domain, new token), and a 409 → "connected to another account". Every state is rendered from the live `GET /shop/domain` on load — nothing is carried client-side across navigation. The signup wizard (`AccountSetup.tsx` / `useAccountSetupForm.ts`) only *starts* the claim at signup, then deep-links here (CD7).
- **`GET /domains/verify?domain=`** (`@Public()`, throttled 60/min/IP) is the Caddy on-demand-TLS `ask` endpoint — answers via HTTP status alone. Returns 200 for a real `{subdomain}.requital.io` host or a **`verified`** `customDomain`; a `pending`/`verifying`/`failed` claim gets 404 (no cert). Delegates to `DomainsService.resolveSubdomain`, so this and `/domains/resolve` share the verified-only gate. (Only the custom-domain catch-all Caddy block actually consults this — see below.)
- **Caddy** — the live `/etc/caddy/Caddyfile` on the VPS is mirrored in the repo at **`deploy/Caddyfile`** (+ `deploy/README.md` for the deploy steps). Site blocks, in precedence order: `requital.io`/`www` (301 → admin); `admin.requital.io` → :3001; `api.requital.io` → :3000; **`*.requital.io` → :3002 with ONE Cloudflare DNS-01 wildcard cert (`tls { dns cloudflare ... }`), NOT on-demand TLS** — every subdomain shop rides that proactively-issued wildcard; `https://` catch-all → :3002 with `tls { on_demand }`, the **only** block using on-demand TLS, gated by the `ask` hook. `CLOUDFLARE_API_TOKEN` comes from `/etc/caddy/caddy.env` (not in the repo).
- **`storefrontUrlFor(shop)`** (`admin/lib/api.ts`) builds the merchant-facing "your store is live at" URL from `shop.domainType`/`customDomain`/`subdomain` directly — kept separate from `STOREFRONT_URL` (admin's own internal navigation, stays on the bare-path shape).
- **Storefront subdomain/custom-domain routing** (`storefront/proxy.ts`) rewrites an incoming hostname-based request onto the same `/[shop]/...` path tree Caddy already forwards to port 3002 — tenant resolution stays a path segment; `proxy.ts` just makes the page unaware a rewrite happened. `GET /domains/resolve?host=` supplies the subdomain to rewrite to (a custom domain has no way to derive it without asking the backend) — it resolves a custom domain **only when `customDomainStatus = 'verified'`**; an unverified claim resolves to nothing. Not throttled (its one legit caller is the storefront server itself, all lookups from one IP — a per-IP limit would 404 real traffic; Phase 6 hardens it). A host that resolves to nothing rewrites to `store-not-found` with a real 404.
- **Every internal `<Link>`/`router.push`/`redirect()` must build its target with `useShop().shopBasePath`**, not a hardcoded `/${shopSlug}/...` path. `shopBasePath` is `/${shopSlug}` when the *current* pathname already carries that prefix (direct-path/local/CI access) or `""` otherwise (hostname-resolved access, where the browser's URL bar structurally can't have it) — computed from `usePathname()` in `ShopProvider`. A hardcoded prefix double-prefixes after `proxy.ts` rewrites and 404s on a real subdomain; an unconditionally-stripped prefix 404s against `e2e/`'s own bare-path flow. The one server-component exception (`products/[slug]/page.tsx`'s legacy-id redirect) reads the `Host` header via `next/headers` and replicates `proxy.ts`'s own `isLocalHost()` check (factored into shared `lib/is-local-host.ts` so the two can't diverge).
- **Custom-domain resolver — wired end to end (`docs/plans/custom-domain-resolver.md`, Phases 1–6, 2026-08-31).** One real shop (`irmain.com`) runs a custom domain in prod. P1: `shop.customDomain*` groundwork columns, `isValidCustomDomain` tightening, `deploy/Caddyfile`. P2: DNS-TXT ownership verification (the block above). P3: the merchant Settings → Domain page (the bullet above). P4: docs only — Caddy 2.7 removed `on_demand_tls { rate_limit }`, so the `ask`-gated-on-`verified` endpoint + its 60/min throttle *are* the abuse-resistance mechanism (`deploy/README.md`); `docs/runbook.md` has the "connected but no cert" triage. **P5: the storefront's same-origin `/api/*` proxy** (`next.config.ts` rewrites + `lib/api.ts`'s `apiBase()`) so `SameSite=Strict` customer cookies are sent on a custom domain — plus the `__Secure-` cookie-prefix fix (see Auth mechanism above), which also un-broke customer sessions on plain subdomain shops. P6: a 30s TTL cache in `DomainsService.resolveSubdomain` (invalidated on connect/disconnect/verify) + stale-on-backend-failure routing in `proxy.ts` + structured verify/cache logging. Deploy-verification step for the true cross-site custom-domain session case is in `deploy/README.md`.

## Delivery zones

Per-outlet named flat-fee zones (`deliveryzone`, additive to the outlet's own single `deliveryRadiusKm`/`latitude`/`longitude`) have an optional per-zone map center + radius (`lat`/`lng`/`radiusKm`, all nullable). No distance/haversine calculation exists anywhere — this is captured/persisted only. Admin's zone modal renders a Google Maps view (draggable pin + a `Circle` overlay sized by a 1–100km slider); every new zone gets a real center/radius by default (`UAE_CENTER`/5km) — the nullable columns exist only for zones created before this shipped or via a direct API call.

## Slider on-demand delivery

`backend/src/delivery-providers/` — a real courier API integration (quote/dispatch/cancel), distinct from `external-deliveries/`'s manual "log a courier handoff" (both live on the same `externaldelivery` table, `provider: 'manual' | 'slider'`).

- **Credential model: one PARTNER key (Requital), every merchant a CUSTOMER ACCOUNT under it, identified by `account_id` — there is no per-shop Slider API key.** (A first version got this wrong, storing an encrypted per-shop key like the bring-your-own-keys Payments/WhatsApp pattern; corrected before it saw real traffic.) The platform key/environment/webhook token are env vars, resolved directly by `SliderSettingsService`/`SliderWebhookJobHandler`. The only per-shop state is `shop.sliderAccountId` (plain identifier, not encrypted) and `shop.sliderEnabled`. `SliderSettingsService.resolveCredentials(shopId)` collapses "shop enabled it + account id is set + platform env vars configured" to one null-or-real result.
- **A merchant cannot set their own `sliderAccountId`** — they have no Slider dashboard access. `PATCH /platform-admin/shops/:shopId/slider-account-id` is how a platform admin sets it.
- **Webhook**: one platform-level, unauthenticated route (`POST /slider/webhook`, `@Public()`) shared across every merchant. Does the minimum DB work before responding 2xx, enqueues the real work onto the DB-backed job queue — `SliderWebhookJobHandler` does the status/driver-info update and the optional-token check (a bad token never becomes valid on retry). A `delivered` webhook ties into `OrdersService.collectCash` so a Slider-delivered COD order satisfies the cash-collected gate automatically.
- **Caps enforced before ever calling `POST /deliveries`** (`slider/slider-caps.ts`, pure functions): COD orders over AED 350, card-on-delivery over AED 500, 35km cap on `vehicleType: 'bike'` (checked against a fresh fare re-quote, never a client-supplied distance). Retries happen once, only on a genuine 5xx — never on a thrown/network error, so a timeout is never blindly retried into a duplicate delivery.
- **`webhookevent`** (`webhook-log/`) is a shared diagnostics log across every provider (Slider and every payment gateway), read via `GET /webhook-log` — "did the webhook even arrive" is the #1 troubleshooting question. `WebhookLogService.log` swallows its own write errors.

## Auto-apply discounts

`discount.discountType` (`'code' | 'auto'`) is orthogonal to `discount.type` (the amount math) and `appliesTo` — an `'auto'` discount applies with no code entered, reusing the existing product/collection scoping infrastructure. `discount.code` is nullable for `'auto'` rows (InnoDB treats every NULL as distinct under the unique index). `DiscountsService.assertDiscountKindFields` is the cross-field guard: `'code'` must have one, `'auto'` must not and must not be scoped `ALL_PRODUCTS`. `GET /public/:shopSlug/discounts/auto` (`@Public()`) backs the storefront's pure `lib/auto-discounts.ts`'s `computeAutoDiscountedPrice(product, autoDiscounts)`, which picks the single best matching discount and mirrors the backend's own amount math client-side.

**Deliberate scope boundary**: this only drives pricing *display*. Actual order-total redemption of an auto discount (auto-applying at checkout the way a code does) is not wired — `PublicService.createOrder`'s `discountCode`-provided branch is where a no-code auto-apply would need `listActiveAutoDiscounts` consulted, if this is ever finished.

## Platform admin

A genuinely separate access tier above shop admin — Requital staff managing the platform itself, not a shop's own staff. Backend: `platform-auth/` (login/session) + `platform-admin/` (shops, integrations, actions, settings, webhooks, audit log). Frontend: `admin/app/platform/*`, a second, visually distinct app inside the same Next.js project.

- **Platform admins are not `user` rows** — a separate `platformadmin` table, no `shopId`, no signup route. Seeded via `npm run db:seed-platform-admin -- <email> <password> <name>` (CLI-only; the real security boundary is already having deploy access).
- **A completely separate JWT scope**: `PlatformAuthModule` keys its own `JwtModule` off `PLATFORM_JWT_SECRET` — a merchant token fails signature verification outright against `PlatformAdminGuard`, and vice versa, no shared-secret fallback either side could hit. Sessions are a single 12h token, no refresh pair.
- **`PlatformAdminGuard` 404s on every failure path, never 401/403** — missing/malformed/expired/wrong-`typ` token, admin no longer exists, all collapse to `NotFoundException`, so an unauthenticated scan can't tell "route doesn't exist" from "not authorized." Applied via `@Public()` + `@UseGuards(PlatformAdminGuard)` together (the global merchant `AuthGuard` would otherwise 401 first). **`PLATFORM_JWT_SECRET` must live in `.env`, not be set inside a test's `beforeAll`** — `JwtModule.register()` reads it at module-import time, before any `beforeAll` body runs.
- **All three tiers (platform, staff, customer) now use httpOnly, `SameSite=Strict` cookies**, migrated off `localStorage` bearer tokens (the security audit's #1 finding — 30-day refresh tokens in `localStorage` meant XSS anywhere handed an attacker a month of access). Cookie names: `req-platform-at`, `req-staff-at`/`req-staff-rt` (refresh scoped to `Path=/auth/refresh`), `req-customer-at`/`req-customer-rt` (shared cookie *name* across every shop but Path-scoped per shop — `/public/{shopSlug}` — so two shops' sessions coexist as two distinct cookies in one browser, matching what per-shop `localStorage` keys used to give for free). `__Host-` prefixed in production (browser-enforced Secure+no-Domain+Path=/), bare in dev (plain HTTP can't set Secure cookies at all). Every existing refresh token was force-revoked on deploy, requiring a real re-login for everyone — a clean cut-over, not a dual-support transition window, matching the "payment provider toggle-bypass guard" lesson above (a guard accepting two legitimate auth shapes eventually has one path forget a check the other has).
- **CSRF is mandatory, not optional, on top of `SameSite=Strict`** — open self-signup means an attacker can host arbitrary HTML on their own `{shop}.requital.io`, same-*site* (not same-origin) with `api.requital.io`; `SameSite=Strict` blocks classic cross-site forgery but not a same-site-but-cross-origin forged request from a page like that. `common/csrf.ts`'s `createTierCsrf` wraps `csrf-csrf` in a double-submit-cookie factory, one instance per tier, wired via `AppModule.configure()`'s `MiddlewareConsumer` (not `app.use()` in `main.ts`, which never runs under Jest — `cookie-parser` itself had to move there too, for the same reason). Platform admin's CSRF is scoped to its own narrow route prefixes (`forRoutes(prefix)`); staff's has to be global (`forRoutes('*')`, since virtually every controller sits behind the staff cookie) and relies on `skipIfNoAccessCookie` (skip when this tier's cookie is absent — exactly the case that needs no guarding, since a forged request can only be dangerous when the browser auto-attaches a real cookie) plus an explicit `skipPathPrefixes` for `/platform-admin`/`/platform-auth` (found for real: a platform admin who *also* has a personal merchant login in the same browser would otherwise get their own impersonate call blocked by staff's global CSRF seeing their staff cookie present).
  - **`skipCsrfProtection` matches on `req.originalUrl`, not `req.path`** — under `forRoutes('*')` Nest reports `req.path` as `"/"` (the whole path is the mount), so the real route is only on `req.originalUrl`. Both the `skipPathPrefixes` check and the login/signup/register skip below use `originalUrl` (minus query string).
  - **Staff/customer `/auth/login`, `/auth/signup`, `/auth/register` are CSRF-exempt** (2026-09-03), the same exclusion platform-auth/login already had in `app.module.ts` — done inside `skipCsrfProtection` rather than via `.exclude()` since the customer route carries a `:shopSlug` segment. **Why it was needed**: `sessionCookieOptions()` set no `maxAge`, so the access cookie was a *session cookie* that outlived its 15‑minute JWT until the browser process exited. A "logged out" user still carried that stale `__Host-req-staff-at` / `__Secure-req-customer-at`, so `skipIfNoAccessCookie` did *not* skip on the recovery `/auth/login` POST — but a cold page has no in-memory CSRF token, so login 403'd `"invalid csrf token"`, which `admin/app/login/page.tsx`'s `describeLoginError` rendered as "Incorrect email or password." A full browser restart (clearing the session cookie) was the only fix. Also fixed alongside: the access cookie now carries `maxAge` = its JWT lifetime (`*_ACCESS_COOKIE_MAX_AGE_MS` in each tier's `*.constants.ts`; the refresh cookie stays a session cookie — persisting it is a "stay signed in" product choice, not done), and `describeLoginError` trusts an `ApiError` status outright instead of falling through to substring-matching `"invalid"`. `/auth/refresh` stays CSRF-protected (a forged same-site refresh is a session-DoS; and with the access-cookie `maxAge` the legit cold-refresh path sends no access cookie, so `skipIfNoAccessCookie` covers it).
- **The CSRF token itself is distributed via a dedicated `X-CSRF-Token` response header, not a JS-readable cookie.** The original design made the CSRF cookie non-httpOnly specifically so `document.cookie` could read it — this only ever worked in local dev, where every app shares the bare `localhost` hostname and cookies aren't port-scoped; in any real deployment (admin.requital.io vs. api.requital.io vs. `{shop}.requital.io`) a cookie set by the API is invisible to `document.cookie` on a page loaded from a different hostname, regardless of `httpOnly`. Fixed by making the CSRF cookie `httpOnly: true` too (it never needed JS readability — only the server needs it back, via the ordinary auto-sent `Cookie` header) and returning the value via `CSRF_RESPONSE_HEADER` on every request that mints/refreshes one (login/signup/refresh, and each tier's own "me" bootstrap endpoint) — `main.ts`'s CORS needs `exposedHeaders: ['X-CSRF-Token']` for a custom response header to be readable by `fetch()` at all cross-origin. Every frontend holds the token in a module-level in-memory variable, never `localStorage`. `TierCsrf.issue()`'s `reuseExisting` option lets a "me" bootstrap call reuse the still-valid existing value instead of rotating it (which would silently invalidate the token any other already-open tab is still holding).
- **Staff keeps a narrowly-scoped, `NODE_ENV === 'test'`-only bearer-header fallback** in `AuthGuard.extractToken` — a deliberate, reasoned exception (roughly 60 pre-existing e2e specs each read `body.accessToken`; converting all of them was judged not worth the risk at that scale, since the guard's downstream role/context derivation is identical regardless of which branch extracted the token). The fallback is compiled-in but genuinely inert outside Jest — not the "two live auth paths in production" shape the toggle-bypass-guard lesson warns against. `AuthController`'s login/signup/refresh/accept-invite responses mirror this with an `isTest` branch that additionally returns raw tokens in the JSON body.
- **Impersonation mints a real merchant token, short-lived and non-refreshable** (`typ: 'staff'` + an `imp: platformAdminId` claim, 1 hour, no `refreshtoken` row ever inserted for it — cannot be silently extended). Set as a same-origin cookie directly on the impersonate response (not a token handed back for the frontend to store) — the staff *refresh* cookie is explicitly cleared, not merely omitted, so a platform admin who also holds their own real merchant refresh cookie in this browser doesn't get the impersonation access cookie silently paired with it on the next silent-refresh. `GET /auth/me` exposes `impersonating: boolean` for `ImpersonationBanner.tsx`. **The audit-log write is a hard precondition of returning the token** — `PlatformAdminService.impersonate` awaits `PlatformAuditLogService.log(...)` before returning either value; if the log insert fails, the whole request fails. This is the opposite of `AuditLogService.log`'s swallow-errors philosophy — for cross-shop, security-sensitive actions, "it happened but nobody can prove it" is worse than "it didn't happen."
- **Theme builder live preview needs its own narrow token**, `typ: 'theme_preview'` (`POST /themes/:id/preview-token`), since `PreviewFrame.tsx` can't read a real staff token out of `localStorage` anymore to embed in the iframe URL. `{shopId, exp}` only, no user identity, 15min TTL, deliberately meant to be URL-embedded unlike the real session.
- **Shop suspension is enforced at two independent choke points**: `AuthService.login` (checked only after a correct password, so a wrong-password attempt doesn't leak suspension state) and `AuthGuard`'s per-request re-fetch (so a suspension mid-session takes effect immediately). The storefront half lives in `PublicService.resolveShop`, the one real choke point every public content-serving call routes through.
- **Frontend: two structurally separate apps sharing one Next.js project.** `admin/lib/platform-api.ts`/`platform-auth-context.tsx` never touch the merchant `lib/api.ts`'s token handling at all. `app/platform/layout.tsx` renders distinct chrome (dark slate, amber accent, a permanent "PLATFORM ADMIN" banner); `RequireAuth`/`AppChrome` bypass entirely for `pathname.startsWith("/platform")`. "Impersonate" navigates same-tab (`window.location.href`) after a `window.confirm()` — an earlier version tried `window.open()` after an awaited call, which browsers silently popup-block since only a *synchronous* click-handler call is exempt. `lib/impersonation.ts`'s `IMPERSONATION_SHOP_KEY` (localStorage) survives the session dying (by the time a dead impersonation token's 401 reaches `RequireAuth`, `user` is already null) so a merchant-token 401 during impersonation routes to `/impersonation-ended?shopId=X` instead of a bare `/login`.
- **Known gap**: `GET /platform-admin/shops` has no pagination — harmless at a real shop count, but this dev DB's ~26k leftover shops (repeated e2e runs) has crashed at least one verification script trying to enumerate every row.

## Admin frontend (`admin/`)

- **No em dashes (—) in user-facing UI copy** — labels, hints, placeholders, toasts, errors, empty-state text. Use a period, comma, colon, semicolon, or parentheses, or restructure the sentence. Code comments are exempt. Applies to both `admin/` and `storefront/`.
- Plain `fetch` wrapper in `lib/api.ts` (`apiFetch<T>`) calling the backend directly via `NEXT_PUBLIC_API_URL` — no server actions/route handlers, no SWR/React Query. Every page is a client component fetching in `useEffect`, re-fetching after mutations via the same `refresh()` closure. The orders list also polls every 20s — deliberately polling, not websocket/SSE.
- **Auth/routing**: sessions are httpOnly cookies (see "Platform admin" above for the shared cookie/CSRF architecture) — `apiFetch` sends `credentials: 'include'` and attaches `X-CSRF-Token` from an in-memory value on non-GET requests, captured off every response's own header; there is no client-readable token to store. `lib/auth-context.tsx` (`AuthProvider`/`useAuth()`) always calls `api.me()` on mount. `components/RequireAuth.tsx` gates the whole app — redirects unauthenticated users to `/login`, authenticated users away from `/login`/`/signup`.
- **Outlet filtering**: `lib/outlet-context.tsx` — `selectedOutletId` defaults to `null` ("all branches") for admins, force-pinned to `user.outletId` for branch users. UX-only; real enforcement is server-side (`resolveOutletFilter`). `components/OutletSwitcher.tsx` renders `null` entirely for non-admins.
- Shared response/DTO shapes live in `lib/types.ts`, kept in sync with backend DTOs by hand — no generated client.
- **`components/ui/`** is a local design system: tables, cards, skeletons, `Button`/`Input`/`Toggle`/`SegmentedToggle`, `BackButton`, `PageShell`, `Modal`, `Select`/`Combobox`, `ColorPicker`, `SecretField`, a `Toast`/`useToast` context (call `useToast()`, never `alert()`). `Select` is the default dropdown (a real `<select>`, wrapped for styling — free keyboard/mobile/a11y semantics); `Combobox` (hand-rolled popover+list) only for genuinely long/searchable option lists; `MultiCombobox` (added 2026-08-29) is the multi-select sibling (chips trigger + searchable checkbox list + optional `onCreateNew` row), also does single-select via `single` — used for the product form's Collections and Brand pickers. Neither wraps Radix/cmdk or shadcn — no shadcn theme is installed here, several primitives are adapted from 21st.dev community components with attribution comments at the top of their files.
- **`Button`'s `loading` prop** shows an inline spinner and forces `disabled` — set it in addition to (not instead of) an existing `disabled={saving}`.
- **Row actions on list/table pages are icon-only buttons** (a lucide icon + `aria-label`, no visible text), one per action in a trailing column — the converged treatment after two other patterns (labeled buttons, text links) existed on different pages.
- **`BackButton`** always navigates to an explicit hardcoded parent route, never `router.back()` — switching tabs within a section used to pollute history so "Back" could land on the wrong tab.
- **Theming**: `dark:` is selector-based (`.dark` class via `@custom-variant`), not `prefers-color-scheme` — a manual toggle needs JS control. Light is the hard default with no stored preference (an earlier version fell back to OS dark-mode detection, which silently dark-mode'd the admin for anyone with OS dark mode on). Brand accent is `--color-accent` in `globals.css`'s `@theme inline` — change the value there, not at call sites. `--color-accent-text` is a darker shade for accent text on a light background (the base accent is only ~3.7:1 against white, under WCAG AA).
- **Tailwind v4 gotcha — a bare `border` class renders `currentColor`, not gray** (v3's default was gray-200). Always pair `border` with an explicit color utility.
- **Tailwind v4 gotcha — a custom property in a recognised namespace (`--color-*`, `--radius-*`, `--spacing-*`, `--text-*`, `--font-*`, `--breakpoint-*`, …) redefines that whole utility family everywhere it is defined — `@theme` AND plain `:root` alike** — because v4 compiles the utilities as `var(--radius-md)` (no fallback), reading the live property. This bit us for real: Phase B1 named its runtime radius-scale tokens `--radius-sm/-md/-lg` (in `storefront/app/globals.css`'s `@theme`) to feed its `.theme-round-*` classes, and silently shifted `rounded-sm/-md/-lg` +2 to +4px on ~88 unrelated call sites (account/bio/brands/collections/checkout/cart/modals; v4 defaults `0.25`/`0.375`/`0.5rem`). Fixed in `fix/radius-tokens-out-of-theme-block` by **renaming the property to `--theme-round-*`** (outside every TW namespace) in `lib/radius.ts` + the `.theme-round-*` class fallbacks; the `rounded-*` utilities are left on their stock scale. **Rule: name a bespoke runtime design token so it does NOT collide with a TW namespace** (`--theme-*` is the established prefix here) unless you explicitly mean to move the utility scale. `storefront/app/globals.css.test.ts` guards the narrower "no `--radius-*`/`--spacing-*` inside an `@theme` block" case. Deliberate utility-scale overrides (`--color-sale-price` → `text-sale-price`, `--color-popover*`, the `@theme inline` font/background tokens) stay in `@theme` on purpose.
- **Navigation feedback is two independent layers**: `NavigationProgress.tsx` drives an nprogress bar via a capture-phase document click listener (App Router has no built-in "navigation started" event); `app/**/loading.tsx` files give the actual skeleton content. Under a persistent `layout.tsx` (Settings, Theme editor), a route's `loading.tsx` must cover only the content area, since the layout stays mounted.
- **Known lint gap**: `react-hooks/set-state-in-effect` fires on the `useEffect(() => { refresh(); }, [refresh])` fetch-on-mount pattern used across nearly every data page — cosmetic (`next build` doesn't fail on it), not yet fixed since resolving it means restructuring the fetch pattern repo-wide. `admin/lint-baseline.txt` currently tracks 77 (raised 76 → 77 on 2026-08-29 (Brands batch): new `/products/brands` page's fetch-on-mount `useEffect(() => { refresh(); }, [refresh])`, the accepted pattern above). Adding a new page with this same pattern is expected to bump the count by one; bump the baseline with a one-line dated note rather than trying to eliminate the pattern in an unrelated change.
- **All modal components route through the shared `components/ui/Modal.tsx`**. `size` is `"sm"|"md"|"lg"`; every size gets `max-h-[90vh]` with a `modal-scroll` body and sticky header. **Modals close only via their own X/Cancel button, never backdrop click** (`CommandPalette.tsx`, Cmd+K search, is the one deliberate exception). `children`/`footer` accept a render-prop form, `(requestClose) => ReactNode` — for anything with a native `type="submit"`, keep the whole form (fields *and* action row) inside `children`, never split the submit button into `footer` (which renders outside the `<form>` DOM subtree).

### Settings/config page layout convention

Apply by default to every settings/config page, not just on request:

1. **Card containers**: every distinct section wrapped in `components/ui/Card.tsx`. Never separate sections with just a heading on bare background; don't invent sub-sections just to have more cards.
2. **Grid density matches field length**: short fields (`grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`), long-form fields (`sm:col-span-2 lg:col-span-3`).
3. **Fill height gaps** between side-by-side cards where a later section can reasonably sit in the shorter column — judgment call, not automatic.
4. **`Toggle`, not `Checkbox`, for binary status fields** (active/inactive, open/closed) — green=on, neutral grey=off (not red; red reads as "broken," not "unconfigured"). `Checkbox` is only for real multi-select lists.
5. **Compact grouping** — a value plus its own status toggle sit close together, left-aligned, not stretched to opposite edges with dead space.
6. **Responsive collapse** — every grid degrades to `grid-cols-1` below `sm`.

### Page width convention — always route through the shared shell

Narrow/constrained-width layout bugs have recurred repeatedly. The root cause each time: a `page.tsx` hand-rolling its own `max-w-*` wrapper instead of rendering through the component that owns that decision — `PageShell.tsx` / `StorefrontPageShell.tsx`.

- **Every `app/**/page.tsx` routes its top-level content through `PageShell`/`StorefrontPageShell`.** Pick the variant matching the content — measure the rendered result against real available width before assuming a tight cap is correct (see the Product Wizard's own `"form"` → `"wide"` fix). Raw `max-w-*` is fine for small elements nested inside an already-shelled page (an image, a modal, a preview widget) — it's specifically the page's own outermost wrapper that must not hand-roll a width.
- Exceptions: pages with no dashboard/storefront chrome at all (admin's pre-auth screens); the storefront bio page (deliberately phone-width regardless of viewport).
- **`node tools/check-page-width.js`** greps every `page.tsx` for a `max-w-` outside a file importing the shell. Run it after adding/editing any page. **Blind spot**: it only scans `page.tsx`, so a `max-w-` hidden inside a *component* a page renders is invisible to it. It also can't catch a page that imports the shell correctly but picks a variant too narrow for its content — that's `node tools/check-form-width.js` (a static heuristic for hardcoded non-responsive grids/fixed-width inputs) and `tools/screenshot/measure.js` (a puppeteer helper measuring an element's gap to the viewport edge at standard breakpoints) instead. All three catch different failure modes; none replaces another.

### Location picking — Google Maps, duplicated between the two apps

`MapPicker.tsx` exists as separate, independently-maintained copies in `admin/components/` and `storefront/components/` — same deliberate no-shared-package duplication as everywhere else. Both use the raw Google Maps JavaScript API (`lib/google-maps-loader.ts` in each app lazily injects the script once, no `@react-google-maps/api` wrapper) — `google.maps.places.Autocomplete` for search, a draggable `Marker` + `Geocoder` for reverse-geocode. `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` in both apps' `.env.local`.

**Two distinct runtime failure modes, both real, confirmed live, not theoretical**: (1) `BillingNotEnabledMapError` — the script loads but the API renders its own error dialog into the map div at runtime, a failure the script-tag `onerror`/`onload` handling doesn't cover. `window.gm_authFailure` is the documented global hook for this (confirmed against Google's current docs, no typed declaration exists for it) — wired in the admin outlet-address `MapPicker.tsx`, **not yet ported to the storefront's separate copy**. (2) A grey overlay + repeating "For development purposes only" watermark — the map renders functional but watermarked when the key is valid but the *project* has no billing account attached (a different symptom than #1, not a hard failure). If this persists after confirming the env var is set correctly in both apps, the fix is enabling billing on the Google Cloud project, not a code change.

## Storefront frontend (`storefront/`)

- **No em dashes in user-facing copy** — same rule as admin's.
- **Tenant resolution is a path segment, not a domain.** Every route lives under `app/[shop]/...`; `proxy.ts` rewrites hostname-based traffic onto this same tree before any page sees it (see "Domains" above) — a deliberate departure from the SRS's original separate-domain-per-merchant plan.
- **`lib/shop-context.tsx`** (`ShopProvider`/`useShop()`) fetches the shop + outlets once per mount, drives live per-shop theming (`resolveThemeCssVars` reads `shop.brandColor`/`colors`/`fontFamily`, with an auto-contrast text color rather than ever hardcoding white/black on a merchant-chosen color), and exposes `shopBasePath` (see "Domains" above), `themeConfig` (the new Sections builder's published config, or `null`), and `autoDiscounts`.

- **Header/footer chrome is real and theme-driven**: `AnnouncementBar.tsx`, `Footer.tsx` (`footerLayout`: columns|centered), `WhatsAppFloatingButton.tsx` are independently toggleable sections, not a static per-template shell. `headerDensity`/`footerDensity` (height/padding) are orthogonal to `topBarLayout`/`footerLayout` (arrangement) — any density pairs with any arrangement.

The discount *code* rides along for UX; the discount *amount* is never trusted client-side — checkout re-validates and the server atomically claims/computes it at order-creation time.
- **`lib/payment-methods.ts`**'s `resolvePaymentMethods` is a pure function (directly unit-tested) computing delivery/pickup payment-method lists from the shop's per-method toggles — it also checks the active card processor is actually enabled, not just that "online card" is toggled on, so checkout never offers an option that would 400.
- **`lib/api.ts`** is unauthenticated throughout for storefront reads — every call hits `/public/:shopSlug/...`, never an admin-authenticated route.
- Order tracking looks orders up by `order.trackingToken`, an opaque per-order token — never the sequential order id.
- Real `vitest` coverage on the pure-logic modules — `cart`, `api`, `bio-page`, `phone`, `referral`, `seo`, `sitemap`, `slots`, `color-contrast`, `auto-discounts`, `bnpl-widgets`, and the `home-layouts` components.
