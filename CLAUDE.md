# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Requital — a multi-tenant e-commerce "shop manager" SaaS (Salla/Zid/Dukan-style), built for UAE/Gulf florists and gift shops. Three independent apps in one repo, sharing nothing but the HTTP boundary:

- `backend/` — NestJS + Prisma + MySQL, the single source of truth for both frontends. Well past Phase 1 now: auth/roles, products (with variants, ingredients, attributes, FAQs), categories, collections, orders (kanban + draft orders + returns/refunds + post-purchase survey), outlets, delivery zones, discounts, affiliates, bio-links, dashboard/reporting, search, audit log, theme/SEO settings, WhatsApp integration, and payments (Stripe live, five more gateways stubbed behind the same interface). See "Backend architecture" below for the module roster.
- `admin/` — Next.js Admin Panel (merchant-facing). Login/signup, sales dashboard, order management (kanban + history), inventory (products/categories/ingredients/stock movements), collections, discounts, draft orders, bio-links, affiliate program, reports, activity log, and multi-tab settings (business info, outlets, users, payments, theme, SEO). See "Admin frontend" below.
- `storefront/` — Next.js Storefront (customer-facing, per-shop branding, resolved via a `/[shop]/...` slug in the path — see "Storefront frontend" below). A real app: product browsing with theme-driven homepage layouts, cart, checkout, collections pages, bio page, order tracking.

**Spec docs**: `BUILD_BRIEF.md` at the repo root is the original entry point and points to `REQUITAL_SRS.md` as the full source-of-truth spec (Section 6 has the data model). The SRS is not currently present in the working tree — if it's missing, note that rather than guessing at requirements from memory. Per the build brief, the SRS also specifies things not yet built: i18n + Arabic/RTL and multi-currency (single-currency AED throughout today) — the current implementation is a simpler, shipped-first version of that spec, not a divergence to "fix." Multi-outlet, the Kanban order pipeline, unlimited-depth attributes/variations, and a Customers module, all listed in the SRS as future/Phase-2+ work, **have since been built**. The SRS's separate-top-level-domain-per-merchant plan for the storefront was also **not** what got built — tenant resolution is a `/[shop]/...` slug segment instead (see "Storefront frontend"). Don't treat any of the above as still-pending.

## Tenant isolation and outlet scoping

Every tenant-owned table carries `shopId`, and every query against one is scoped by it at the data-access layer — no code path may return one shop's data to another. This is no longer a hardcoded constant: real merchant auth exists, and every request derives `shopId` (and, for outlet-scoped resources, `outletId`) from the authenticated user, re-read from the DB on every request.

- **`AuthGuard`** (`backend/src/auth/guards/auth.guard.ts`) verifies the JWT, then re-fetches the user from the DB (not trusting token claims for role/outlet) and attaches a `TenantContext` (`backend/src/common/tenant-context.ts`: `{ userId, shopId, role, outletId: number | null }`) to the request, injectable via the `@CurrentUser()` decorator. Re-reading on every request means a role change, outlet reassignment, or account deletion takes effect immediately rather than waiting out the token lifetime.
- **`RolesGuard`** + `@Roles(...)` gates endpoints by role. Both guards are wired as `APP_GUARD` providers in `AuthModule`; routes are protected by default and opt out with `@Public()`.
- **Four roles**: `admin` (full shop access, all outlets, aggregated dashboard), `branch` (pinned to exactly one outlet, `outletId` is never null — see `resolveOutletFilter` below), `order_manager` (shop-wide but scoped to the Orders/Draft Orders domain only — no pricing, catalog, or settings access), and `viewer` (shop-wide read-only — reports, orders, customers, no mutations anywhere). `order_manager`/`viewer` are additive on top of the original admin/branch split and are *not* outlet-pinned. Signing up always creates a Shop + a default Outlet + an Admin user in one `$transaction` (`AuthService.signup`). Only admins can create branch/order_manager/viewer accounts.
- **`resolveOutletFilter(ctx, requestedOutletId?)`** (`backend/src/common/outlet-scope.ts`) is the single shared helper encoding the branch-override rule: a `branch` user's `ctx.outletId` always wins regardless of what the request asked for; an `admin` gets the requested outlet or `undefined` (no filter = all outlets). Every outlet-scoped read/write (orders, stock, dashboard) routes through this helper — do not hand-roll the branch/admin distinction elsewhere. `outlets.service.ts` has a documented gotcha: don't build the `where` clause as `{ id, shopId, ...(role==='branch' && { id: ctx.outletId }) }` — the spread silently overwrites the requested `id` last, turning "reject mismatched outlet" into "silently substitute my own outlet." Check `id !== ctx.outletId` explicitly instead.
- **Unverified `outletId` for a stock write — a bug class that recurred twice, now caught by a structural guardrail.** `confirmImportIngredients` and (independently) `confirmImportProducts` both took a query-param `outletId` and used it directly for `outletstock`/`outletingredientstock` upserts and `stockmovement` creates with no check that the outlet actually belongs to `ctx.shopId` — an admin from Shop A who knew/guessed an outlet id belonging to Shop B could write stock/movement rows into it. Fixed (2026-08-04) by adding an `outlet.findFirst({ id: outletId, shopId: ctx.shopId })` check before either transaction runs, matching the pattern every *other* outlet-taking write in these files already followed (`setLowStockThreshold`, `transferStock`, order creation's outlet re-verification, etc.) — this was two isolated omissions in an otherwise-consistent codebase, not a missing pattern. `node tools/check-outlet-scoping.js` is a grep-based guardrail (same philosophy as `check-page-width.js`) that flags any backend service method taking an `outletId` parameter with no adjacent ownership-check marker in its body — run it after adding or editing any method that accepts an outletId; it has a documented `ALLOWLIST` for genuinely-safe cases (private helpers only ever called with an already-verified outletId, or read-only queries where a foreign outletId can only match zero rows).
- **Catalog vs. stock split**: Products/Categories stay shop-scoped (one shared catalog across all of a shop's outlets). Stock does not — `product.stockQuantity`/`lowStockThreshold` were removed from `Product` entirely and moved to the `outletstock` join table (composite PK `[outletId, productId]`). `trackInventory` (whether a product is stock-tracked at all) stays on `Product` since it's a catalog-level policy, not a per-outlet count. `GET /products` returns `stockQuantity: null` (not `0`) when no outlet is resolved (e.g. an admin viewing "all branches" without picking one) — that's distinct from a genuine zero-stock outlet.
- **Orders are outlet-scoped**: `order.outletId` is a required FK. On create, a branch user's `outletId` is always forced server-side to `ctx.outletId` — any `outletId` they supply in the body is silently ignored, never honored. Admins may specify one.
- **Security regression suite**: `backend/test/security-outlet-isolation.e2e-spec.ts` is the living proof this holds — it spoofs `outletId`/order ids across outlets and across shops (branch user, admin, and cross-tenant) on every outlet-scoped endpoint and asserts each either silently re-scopes or 404s, never leaks. Run it (`npm run test:e2e -- security-outlet-isolation`) after touching any tenant- or outlet-scoped query path; it already caught one real bug (the `outlets.service.ts` spread-overwrite above) that reasoning-only review missed.

### Branch-specific roles — a permission layer on top of the 4-tier system

A per-`(user, outlet)` override that can *restrict* (never grant more than) a staff member's shop-wide role at one specific outlet — e.g. a shop-wide `admin` can be knocked down to view-only at Branch B while staying full-access everywhere else. This is additive: a shop that never assigns an override sees zero behavior change anywhere.

- **Two models**: `branchrole` (shopId, name, `permissions` — a JSON array of a fixed vocabulary, not free-form strings) is an admin-defined bundle; `useroutletrole` (userId, outletId, branchRoleId, unique per user+outlet) points a specific staff member at a specific outlet to one of those bundles.
- **The fixed permission vocabulary** lives in `common/permissions.ts` (`Permission` union — `orders.view`, `orders.manage`, `dashboard.view`, `products.view`, `products.manage_stock`, `ingredients.view`, `search.use`, `outlets.view_own`, `delivery_zones.view`, `payments.generate_link`) alongside `basePermissionsFor(role)`, a static map of what each of the 4 existing tiers already implies in that vocabulary.
- **The actual security guarantee is an intersection, not a convention**: `BranchRolesService.resolveEffectivePermissions(ctx, outletId)` (`branch-roles/`) returns `null` when no override row exists for that `(user, outlet)` — callers must fall through to their existing `ctx.role`-based logic untouched. When an override *does* exist, the effective set is `intersection(basePermissionsFor(ctx.role), branchrole.permissions)` — this is what makes an over-generous or spoofed assignment structurally incapable of granting more than the user's shop-wide ceiling, rather than relying on the admin UI to prevent it. `assertPermission(ctx, outletId, permission)` is the thin wrapper every call site actually invokes, throwing `ForbiddenException` only when an override exists and lacks the permission.
- **Wired into every outlet-scoped read/write** across orders, products (catalog + stock), dashboard, ingredients, payments (`generateLink`), search, delivery-zones, and outlets — deliberately *not* draft-orders/reports/scan, since today's `'branch'` role can't reach those controllers at all (revisit if that ever changes). Two resolution rules matter when adding a new call site: **list/aggregate endpoints** (an admin viewing "all branches", `outletId` unresolved) skip the check entirely — overrides never affect aggregate views, only a concretely-scoped one; **single-resource endpoints** (a specific order, outlet, etc.) must check against the *fetched resource's own* `outletId`, not the pre-fetch query filter — an admin's filter is `undefined` by default, but the resource itself always belongs to one real outlet.
- **Staff management got real update/delete for the first time** here (`PATCH`/`DELETE /auth/users/:id` — previously create-only via `POST /auth/branch-users`), with self-edit blocked (use profile settings instead), last-remaining-admin demotion/deletion blocked, and deletion blocked (409) if the user has existing audit-log/note/stock-movement/return history (those FKs have no cascade, by design — a departed staff member's history isn't silently reassigned or orphaned).
- `backend/test/branch-roles.e2e-spec.ts` is the pattern to extend for adversarial coverage: cross-shop spoofing on every new endpoint (assign/branchrole CRUD), and — the one that actually matters — a real HTTP-level "permission escalation" test proving an over-generous branch-role assignment on a shop-wide `viewer` still can't unlock `orders.manage`.

## Next.js version warning

`admin/AGENTS.md` and `storefront/AGENTS.md` (referenced from each app's `CLAUDE.md` via `@AGENTS.md`) warn that this is Next 16, which has breaking API/convention changes from what training data assumes — read `node_modules/next/dist/docs/` before writing Next.js code in either app. Confirmed in practice: route `params`/`searchParams` are `Promise`s that must be `await`ed in Server Components; client components should use the `useParams()`/`useSearchParams()` hooks instead of destructuring props.

Prisma — this project's `prisma migrate dev` cannot run in a non-interactive shell (it refuses with "Prisma Migrate has detected that the environment is non-interactive"). Migrations here are hand-authored instead:

```bash
npx prisma generate                          # regenerate client after schema.prisma changes
npx prisma migrate deploy                    # applies any pending migration folders
npx prisma db seed                            # run prisma/seed.ts
npx prisma studio                             # browse local data
```

Make the timestamped folder under `prisma/migrations/` by hand and write `migration.sql` yourself (expand/contract for anything that backfills: add nullable column → backfill via `UPDATE ... JOIN` → tighten to `NOT NULL` → add FK/index). `migrate deploy` picks up any folder containing a `migration.sql`.

**Never pass the primary `DATABASE_URL` as `--shadow-database-url` to `prisma migrate diff`** — Prisma resets whatever database that URL points to as part of its shadow-db workflow. This has happened before in this project (recovered via `prisma migrate resolve --applied` re-baselining against the existing table structure); treat the shadow-db flag as write-destructive to its target, full stop.

**A hand-authored migration's folder timestamp is the only thing enforcing its position in `migrate deploy`'s apply order — nothing checks that a migration's own SQL only references tables/columns created by an earlier-timestamped folder.** Found for real (2026-08-05, CI Phase 2): `20260723140844_add_outlet_hours_delivery_coords` ran an `ALTER TABLE outlet ...` timestamped *before* `20260723150000_merchant_auth_and_outlets`, the migration that actually `CREATE TABLE outlet`s — invisible against the long-lived local dev database (which had picked up the columns some other way over time) but fatal (P3018, "Table 'outlet' doesn't exist") the first time `migrate deploy` ever ran against a genuinely clean database, in this session's new CI pipeline. Fixed by emptying the mis-ordered migration to a no-op (left in place, not deleted — every existing database already has it recorded as applied in `_prisma_migrations`, and Prisma tracks migrations by folder name, not content) and moving its real SQL verbatim into a new correctly-ordered folder (`20260723150001_outlet_hours_delivery_coords`, timestamped right after outlet's own creation), then `prisma migrate resolve --applied` on the new folder name for every database that already had the old migration's effect. This is the general fix pattern for any future out-of-order migration found the same way — don't edit an already-applied migration's SQL in place. Since this bug class is only detectable by actually applying every migration to an empty database in order, and the local dev DB never gets rebuilt from scratch, CI's `migrate deploy` against a fresh service-container database (see `.github/workflows/ci.yml`) is now the only thing that exercises this — treat a P3018 there as this bug class, not a flake.

`backend/.env` holds `DATABASE_URL` (MySQL), `JWT_SECRET`, `CREDENTIAL_ENCRYPTION_KEY` (encrypts per-shop payment/WhatsApp credentials at rest, see `common/crypto.ts`), `ADMIN_ORIGINS` (comma-separated CORS allowlist for the admin frontend's origin(s)), `ADMIN_URL`/`STOREFRONT_URL` (used to build reset-password/verify-email/invite links and payment-link URLs respectively), plus one platform-level fallback credential set per payment gateway (`STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`, `TELR_STORE_ID`/`TELR_AUTH_KEY`, `PAYTABS_PROFILE_ID`/`PAYTABS_SERVER_KEY`, `TABBY_PUBLIC_KEY`/`TABBY_SECRET_KEY`/`TABBY_WEBHOOK_SECRET`, `TAMARA_API_URL`/`TAMARA_TOKEN`/`TAMARA_NOTIFICATION_TOKEN`) used only when a shop hasn't configured its own — see "Payments use a strategy pattern" below. `RESEND_API_KEY`/`EMAIL_FROM_ADDRESS` are the same kind of platform-level fallback for real email sending — see "Email sending" below. There is no `.env.example`. **Percent-encode special characters in the DB password** (e.g. `#` → `%23`, `@` → `%40`) — an unescaped character silently breaks the connection string. e2e specs `import 'dotenv/config'` at the top of the file since `main.ts`'s bootstrap (which would otherwise load env vars) never runs under Jest.

`prisma/seed.ts` creates a dev admin login: `admin@test-shop.com` / `dev-password-123`, plus a "Main Branch" outlet.

**Port note**: none of the three apps pin a port. If you start backend first it takes 3000; whichever Next app starts next auto-increments to the next free port (typically admin → 3001, storefront → 3002), but simultaneous startup is a race — Next's dev server binds faster than Nest's, so starting them all at once can leave backend crashing with `EADDRINUSE` after a Next app grabs 3000 first. Start backend, wait for it to actually respond, then start the Next apps.

## Backend architecture

- **PrismaModule** (`src/prisma/`) is `@Global()` — `PrismaService` is injectable anywhere without re-importing the module.
- **Feature modules** follow the standard Nest triad: `<feature>.module.ts` / `.controller.ts` / `.service.ts`, with request/response shapes in `dto/`. Beyond the core catalog/order/outlet modules, the module roster (each a self-contained domain, not obvious from file structure alone):
  - `collections/` — marketing-driven product groupings (`MANUAL` explicit ordered list, or `RULE_BASED` category/tag/price/age conditions computed live, never stored membership) — deliberately separate from `categories/` (the taxonomy tree); see the model's schema comments for the full reasoning.
  - `returns/` — post-delivery returns/refunds: per-line-item and running-total (never exceed `order.total`) caps, provider-refund-with-manual-fallback (see payments below), restock via the same stock-movement pattern orders use.
  - `draft-orders/` — quotes/manual invoices that become a real `order` on completion; reuses `PaymentsService.generateLink` verbatim for "send invoice" rather than a second payment-link mechanism.
  - `invoices/` — real invoice/packing-slip *document* generation for an already-placed `order` (distinct from `draft-orders/`'s pre-order quotes). One `invoice` row per `(orderId, type)` (`INVOICE` | `PACKING_SLIP`), `@@unique([orderId, type])` making `generateForOrder` idempotent; `invoiceNumber` (`INV-0001`/`PS-0001`) comes from a separate `invoicecounter` row per `(shopId, type)`, incremented atomically via a raw `INSERT ... ON DUPLICATE KEY UPDATE lastNumber = LAST_INSERT_ID(...)` — the *seed* branch (first invoice ever for a shop+type) has to wrap its value in `LAST_INSERT_ID(1)` too, not just the increment branch, or `SELECT LAST_INSERT_ID()` reads back whatever unrelated auto-increment insert last ran on that pooled connection instead (see `InvoicesService.nextInvoiceNumber`'s own comment — this was a real bug caught by the e2e "sequencing" test). No PDF library is installed in this repo — `GET /invoices/:id/pdf` serves a styled, self-contained `text/html` document instead (`invoice-html.ts`), relying on the browser's own Print → Save as PDF. Staff-only (`/invoices/*`, JWT-guarded); the storefront's own "Download Invoice" goes through `customer-account`'s separate endpoint instead (see that module's own note) since a customer token can't satisfy the staff guard.
  - `discounts/` — promo codes, redemption is claimed atomically at order-creation time (see webhook idempotency note below for the same CAS philosophy).
  - `bio-links/` — a "link in bio" page builder (own public page, not the storefront homepage); each link has exactly one target type (`EXTERNAL_URL` / `PRODUCT` / `CATEGORY` / `COLLECTION` / `SOCIAL_ICON`) enforced via a discriminated-fields pattern (`assertFieldsMatchType`/`clearedTargetFields` in `bio-links.service.ts`) — follow that pattern when adding a 6th type.
  - `affiliate/` — referral codes + affiliate-attributed order tracking and payout summary.
  - `ingredients/` — raw materials/components tracked for stock but never sold; a deliberately separate model from `product` (no price/SKU-for-sale/variants/SEO), with no code path from `src/public` to it at all.
  - `delivery-zones/`, `external-deliveries/` — per-outlet delivery zone config, and logging a third-party courier handoff (carrier/price/status) for orders not delivered in-house.
  - `customers/` — the shared customer record used by both guest/registered storefront checkout and the admin CRM, upserted by `[shopId, phone]` (`findOrCreateForOrder`) with a P2002-race fallback so two concurrent first-time orders can't 500 each other; order count/lifetime value are computed live via raw SQL, excluding cancelled orders, never stored.
  - `customer-auth/` — a fully separate JWT/refresh-token stack for shoppers (own guard, tokens, rotation-with-reuse-detection) parallel to but independent from the staff `auth` module; "register" doesn't create a new entity, it just sets a password on the same `[shopId, phone]` customer row guest checkout already created.
  - `customer-account/` — the storefront-facing "my account" API (profile/order history/addresses) for the shopper themselves, distinct from admin's `customers` CRM; addresses are a JSON array on the `customer` row, not their own table, and order history spans all outlets of the shop. `GET .../account/orders/:id/invoice` is the customer-facing "Download Invoice" (read-only — never generates, only downloads an invoice the merchant already generated from the admin Invoice tab; see `invoices/` above), scoped by `(shopId, customerId)` via `InvoicesService.renderHtmlForCustomerOrder` rather than reusing that module's own staff-only `/invoices/:id/pdf`. Also owns UAE PDPL self-service: `GET .../account/export` (rate-limited to once per 24h via `customer.lastDataExportAt`) and the two-step `DELETE .../account/me` → `DELETE .../account/me/confirm?token=` deletion flow, which *anonymises* (name/email/phone/addresses scrubbed, `passwordHash` cleared — orders/draftorder/giftcard rows keep their real `customerId` FK, merchant records are explicitly preserved) rather than hard-deleting. The confirmation token reuses `customerauthtoken` (a `purpose: 'account_deletion'` row, same opaque-token/hash-at-rest/single-use-CAS shape as password-reset) rather than a new table. Clearing `passwordHash` is what actually revokes every outstanding access token immediately — `CustomerAuthGuard` already re-reads the customer row every request and rejects one with no `passwordHash` — refresh-token revocation covers the rest. Both PII-touching actions get an `AuditLogService` entry attributed to the shop's own admin (`auditlog.actorUserId` is a required FK to `user`, with no actor-is-a-customer shape), same synthesized-system-actor pattern `PaymentsService.applyAdvanceOrderStatus` uses for BNPL webhooks.
  - `abandoned-carts/` — storefront checkout-progress capture (name+phone before order completes), upserted on `[shopId, customerPhone]`: a still-open episode gets its snapshot refreshed in place, a previously-completed one resets fresh; recovery emails are cron-swept but CAS-claimed row-by-row so a completing order and the recovery job can never both act on the same episode.
  - `gift-cards/` — real `giftcard`/`giftcardredemption` models (code, balance, status, per-order redemption audit trail), not fields bolted onto `product` (that's only the config for *selling* a gift-card product — `isGiftCard`/`giftCardDenominations`/etc. — see below); redeem/credit-refund are CAS balance updates run inside the same transaction as order creation/return, and buying quantity N of a gift-card product issues N independent single-balance cards, not one N-balance card.
  - `notify-subscriptions/` — back-in-stock "notify me" subscriptions. Public `POST`/`DELETE /notify-subscriptions` (no shopSlug in the URL — `shopId` is always derived server-side from the given `productId`'s own shop, never accepted from the client), idempotent per `(shopId, productId, variantId, email)`, soft-rate-limited to 3/hour/email/shop. `NotifySubscriptionsService.triggerForProduct` fires — not awaited, always `.catch()`-guarded — from every real 0→positive stock-crossing point (manual stock adjust, outlet-to-outlet transfer, order-cancellation restock), batching the actual emails in chunks of 50 via `Promise.allSettled` so one bad address can't abort the rest of a chunk. CSV import and scan-to-stock don't trigger it yet (deliberate scope cut, not an oversight).
  - `storefront-search/` — separate from the admin-only `search/` below: a public, typo-tolerant **customer-facing** product search, `GET /public/:shopSlug/search?q=&cursor=`. Exact substring match (name/sku/description/tags/collection title) first; falls back to `fuse.js` fuzzy matching only when exact returns nothing, and only a close-enough fuzzy top hit surfaces as a `suggestion` field for the storefront's "Did you mean X?" prompt. Results are cached per `(shopId, query)` for 60s in a plain in-memory `Map` (no eviction beyond TTL-on-read — fine for a single instance, revisit with an LRU cap only if this ever runs multi-instance) and paginated 20/page via an opaque base64-offset cursor.
  - `reports/` — a read-only aggregation layer with no dedicated report tables, querying `order`/`orderitem` directly; General Report deliberately does NOT exclude cancelled orders (raw audit view) while Product Sales Report does (matching the Dashboard/Customers lifetime-value convention), and Monthly Report is just General Report with `month` translated into a `[firstOfMonth, firstOfNextMonth)` range.
  - `common/nominatim.ts` — `geocodeAddress`/`reverseGeocodeAddress`, a shared proxy to OSM Nominatim (free-tier rate limits, so only ever called from a manual merchant/customer trigger — a map click or pin-drag — never autocomplete-as-you-type) used by both `outlets` (admin address entry) and `public` (storefront checkout/saved addresses).
  - `search/`, `audit-log/` — global cross-entity search, but **admin-only** (JWT-guarded product/order/customer command-palette search — not to be confused with the public, typo-tolerant `storefront-search/` above, a separate module with its own separate matching logic); an append-only staff-action log (`AuditLogService.log` deliberately swallows its own write errors so a broken audit insert never fails the real operation it's describing).
  - `theme/`, `seo/`, `whatsapp/` — storefront theme/branding settings (colors, homepage layout, hero content, header/footer layout+density, the `bannerimage` homepage-slideshow gallery), per-shop SEO metadata, WhatsApp integration credentials (encrypted at rest, see `common/crypto.ts` / `CREDENTIAL_ENCRYPTION_KEY`).
  - `policy-pages/` — the 5 fixed legal/policy page types (`TERMS`/`PRIVACY`/`REFUND`/`PAYMENT`/`SHIPPING`), admin-authored rich text, one `policypage` row per type per shop (unwritten types just don't have a row — no placeholder/blank rows).
  - `public/` — the storefront's entire backend surface, mounted at `/public/:shopSlug/...`. No auth; every other module's admin-facing service is deliberately not reused for public reads (separate, narrower response shapes — see `PublicService`). A globally-unique-token feature (order tracking's `trackingToken`, the post-purchase survey's `surveyresponse.token`) gets its own narrow, un-slugged controller instead (`PublicOrderLookupController`, `PublicSurveyController`) — the token alone is self-sufficient, so no `shopSlug` belongs in that URL, even though the storefront *page* consuming it still lives under `/[shop]/...` for chrome/theming (see "Storefront frontend"). Follow this split for the next such token-based feature rather than bolting it onto the shop-scoped `PublicController`.
- **Validation**: a global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true, transform: true`) is set in `main.ts`. DTOs must use `class-validator`/`class-transformer` decorators — unvalidated fields are silently stripped, not passed through. Type-only imports referenced in a decorated class member must use `import type` (or a namespace import) — plain imports fail the build under `isolatedModules` + `emitDecoratorMetadata`.
- **Auth mechanism**: hand-rolled JWT via `@nestjs/jwt` (no Passport — one guard reading `Authorization: Bearer <token>` is simpler than a strategy layer for a single auth method) and `bcryptjs` (pure JS, not native `bcrypt`, to avoid node-gyp compilation on Windows dev machines). Every route is protected by default via guards registered as `APP_GUARD`; use `@Public()` to opt a route out (signup, login, the payment checkout/webhook endpoints) and `@Roles('admin')` to further restrict one. See "Tenant isolation and outlet scoping" above for the `TenantContext`/`resolveOutletFilter` pattern every feature module routes through.
- **Prisma model naming**: model names in `schema.prisma` are lowercase singular (`product`, `order`, `orderitem`, `outletstock`, `paymenttransaction`, ...) rather than the more common PascalCase Nest/Prisma convention, with no `@@map` reconciling them to the DB's differently-cased table names. This only works because local MySQL is case-insensitive for identifiers (Windows default) — keep new models consistent with the existing lowercase style, but be aware this could break on a case-sensitive MySQL host. **Confirmed, not just theoretical (2026-08-05, CI Phase 2):** the original `20260709131814_init` migration actually `CREATE TABLE`d 8 models in PascalCase (`Shop`, `User`, `Product`, `ProductVariant`, `Order`, `OrderItem`, `PaymentTransaction`, `ThemeSettings`) — every migration since has referenced them lowercase, which only ever worked locally because Windows MySQL folds table-name case at creation time (so `Shop` was already stored as `shop` on disk). The first-ever genuinely clean `migrate deploy` (GitHub Actions' Linux `mysql:8.0` service container, case-sensitive by default) failed immediately with P3018 ("Table 'shop_manager.product' doesn't exist") on the very next migration. Fixed by `20260709131815_rename_init_tables_to_lowercase`, inserted right after init. **First version was a plain `RENAME TABLE` and was itself broken against any pre-existing database** — every real dev/staging DB was created on Windows, so it already has the tables stored lowercase (`shop`, not `Shop`); an unconditional `RENAME TABLE Shop TO shop` there hits the exact same 1050 "table already exists" this migration was written to fix, just one migration later. Confirmed empirically (2026-08-05) by seeding a scratch database with the full migration history minus this one folder (simulating "existing DB, not yet migrated") and running `migrate deploy` against it. **Fixed for real** by making each rename conditional on an `information_schema.tables` existence check for the PascalCase source name, wrapped in `PREPARE`/`EXECUTE` dynamic SQL (MySQL has no `RENAME TABLE IF EXISTS`) — no-ops when the source isn't there, renames for real when it is. One more gotcha inside that fix: the existence check itself must compare with `BINARY table_name = 'Shop'`, not a plain `=` — `information_schema.tables.table_name` compares case-insensitively by default, so an unguarded check matched the lowercase `shop` table too and the guard fired the rename anyway (caught by the same empirical test, second iteration). Verified against three scenarios: a scratch DB seeded with everything-but-this-migration (existing-lowercase-DB path, no-op, confirmed via `SHOW TABLES` that no stray PascalCase table was created), a genuinely fresh scratch DB from migration zero (clean-DB path, all 63 apply), and real Linux CI (the only place the actual case-sensitive rename branch ever executes, since Windows can't produce a genuinely case-sensitive MySQL to test against locally).
- **Many-to-many relations** (Product↔Category, Product↔Tag) use explicit join models (`productcategory`, `producttag`) with composite `@@id`, not Prisma's implicit many-to-many — follow this pattern for future join tables so cascade behavior and indexes stay explicit. `outletstock` (composite PK `[outletId, productId]`) follows the same style.
- **Product images are upserted by `url` on update, not deleted-and-recreated.** `ProductsService.update` matches `dto.images` against the existing `productimage` rows by url, updates `order` in place for a url that already exists, and only creates/deletes rows for genuinely added/removed urls. This matters beyond tidiness: `productvariant.imageId` is `onDelete: SetNull`, and the frontend's product-edit form always resends the full `images` array on every save (even when images didn't change) — a naive delete-all-then-recreate assigns every image a fresh id on every save, which silently wipes every variant's image assignment on its very next unrelated edit. Don't revert to delete+recreate for this relation.
- **Two patterns for a per-product child list, chosen by whether it drives variant generation.** `productimage`/`productattribute`/`productfaq` are plain ordered lists embedded directly in `CreateProductDto`/`UpdateProductDto` (full-replace on update inside the same transaction — upsert-by-url for images per above since `productvariant.imageId` FKs into it, plain delete-then-recreate for attributes/faqs since nothing FKs into those) — no dedicated endpoint. `productoption`/`productvariant` instead get their own `PUT /products/:id/options`, because changing them regenerates the variant cartesian product (`variant-generator.ts`) with id-preserving reconciliation against existing variants — a side effect a main-DTO field can't express. When adding a new simple per-product list, embed it in the DTO; only reach for a standalone endpoint if it has real generation/reconciliation logic like options does. `productattribute` (informational, e.g. Material: Cotton) is deliberately a separate model from `productoption`/`productoptionvalue` for this reason — it's not a purchasable variant axis and must never be extended to become one.
- **`product.isCheckoutAddon`** flags a product to be offered in the storefront checkout's "would you like to add any extras?" popup (`storefront/components/checkout/AddonPrompt.tsx`) for any cart that doesn't already contain it — filterable via `GET /public/:shopSlug/products?isCheckoutAddon=true`. A plain catalog flag, no separate config table — same "doesn't earn its own model" reasoning as `product.isGiftCard`/`giftCardDenominations`/etc. (the config for *selling* a gift-card product; the redeemable card itself is a real `giftcard` model, see `gift-cards/` above).
- **`orderitem.note`** is an optional customer-typed note captured on the storefront PDP (below Add to Cart, ~200 char cap), carried verbatim through `CartItem.note` → `CreatePublicOrderDto.items[].note` → `orderitem.note` — no parsing or merchant editing. Shown staff-side on the admin live-orders kanban card (only rendered for items that actually have one, to stay compact) and per line item in `OrderDetailModal`. Distinct from `ordernote` (an order-level, staff-authored note thread) and `order.deliveryNotes` — there is no merchant-authored per-item note anywhere in the schema, only this customer-authored one.
- **Order status transitions are compare-and-swap, not read-then-write.** `OrdersService.updateStatus`/`.cancel` re-check the row's status inside the same `$transaction` via `updateMany({ where: { id, status: <expected>, outletId: order.outletId } })` and inspect `result.count` — this is load-bearing, not incidental style. A plain `findOne` then `update` has a real race: two concurrent "confirm" calls on the same order would both read `pending` and both decrement stock. The CAS pattern means only one write can match per transition; the loser gets a `ConflictException` (409) instead of silently double-applying a stock change. The `outletId` in the `where` clause is defense-in-depth on top of the outlet-scope check already done in `findOne`. Follow this pattern for any future status-driven side effect (stock, payment, notifications) — don't revert to a plain `update`.
- **Stock is decremented on `pending → confirmed`, not on order creation** (so an abandoned cart never holds stock hostage), and restored on cancellation from any status where it was already decremented. `OrdersService.adjustStockForOrder` upserts into `outletstock` keyed by `[outletId, productId]`, not `product.stockQuantity` (removed — see "Tenant isolation and outlet scoping").
- **Editing a confirmed order's item quantities adjusts BOM ingredient stock by delta, not a from-scratch recompute.** `OrdersService.updateItems` only touches `outletingredientstock` when `order.status === 'confirmed' && order.ingredientsConsumedAt !== null` — a still-pending order's ingredients were never consumed yet (that only happens at the `pending → confirmed` transition above), and an order whose ingredients were never consumed to begin with (auto-deduct was off at confirm time) must stay untouched by an edit rather than start being tracked mid-order. A quantity increase reuses `ProductsService.consumeForOrderItems` with `throwOnInsufficientStock: false` — it never blocks the save, even into negative ingredient stock; going negative is surfaced instead as `ingredientStockWarnings: string[]` on the response for the admin UI to toast. A decrease (or item removal) returns exactly its own delta, unconditionally.
- **Payments use a strategy pattern, resolved per-shop, not per-deployment**: `payments/payment-provider.interface.ts` defines `PaymentProvider` (`createCheckoutSession`, `parseWebhookEvent`, and an *optional* `refundPayment` — optional because Nomod/Telr/PayTabs are still structural stubs with no real API integration; Stripe, Tabby, and Tamara implement it for real). `payments/providers/` has one file per gateway; `PaymentProviderRegistry` registers every implemented provider at boot, and `PaymentsService`/`PublicService` resolve the right one at call time from `shop.paymentGateway` (the shop's chosen card processor) or `shoppaymentprovider.enabled` (the independent BNPL-style providers) — there is no single app-wide `PAYMENT_PROVIDER` env selection anymore. Per-shop bring-your-own-keys credentials are resolved via `PaymentSettingsService.resolveCredentials` (encrypted at rest) and fall back to the matching platform-level env var (`STRIPE_SECRET_KEY`, `TELR_STORE_ID`/`TELR_AUTH_KEY`, `PAYTABS_PROFILE_ID`/`PAYTABS_SERVER_KEY`, `TABBY_PUBLIC_KEY`/`TABBY_SECRET_KEY`/`TABBY_WEBHOOK_SECRET`, `TAMARA_API_URL`/`TAMARA_TOKEN`/`TAMARA_NOTIFICATION_TOKEN`) for shops that predate per-shop credential storage. The Stripe client itself is constructed lazily per-key (on first use, cached by key), not in the constructor, so a shop without its own keys configured doesn't crash the whole app at boot.
- **Payment provider toggle-bypass guard — a bug class that has recurred 3 times in this codebase.** Whether a gateway is actually usable for a shop (has real, non-empty credentials) must be checked *inside* the provider's own `createCheckoutSession`/`parseWebhookEvent` (throwing `PaymentProviderNotConfiguredException`), not only by whatever outer caller resolved credentials or checked `shoppaymentprovider.enabled` first (`PublicService.assertPaymentMethodAvailable`, `PaymentsService.getCheckoutSession`, etc.) — an outer-only check is exactly what's been bypassed each time, by some other call path that forgot to repeat it. See `TabbyPaymentProvider`/`TamaraPaymentProvider`'s own "MANDATORY GUARD" comments for the concrete pattern to copy when adding a 4th real provider (Telr/PayTabs/Nomod, if one of those ever gets a real implementation).
- **BNPL webhooks can drive the order's own status, not just `paymentStatus`** — `WebhookResult.advanceOrderStatus` (`'confirmed' | 'cancelled'`, optional, undefined for Stripe/every non-BNPL provider) tells `PaymentsService.handleWebhook` to additionally run the order through the same CAS state machine `OrdersController`'s own status/cancel endpoints use (`OrdersService.updateStatus`/`.cancel`), under a synthesized system `TenantContext` (`role: 'admin'`, attributed to the shop's own admin user — every shop always has at least one, since the last remaining admin can never be demoted/deleted). Only ever applied while the order is still `'pending'` — a provider's approval/expiry signal arriving after a merchant already moved the order forward (or cancelled it) is stale and silently ignored, never forced through; `updateStatus`/`cancel`'s own exceptions on an invalid/superseded transition are swallowed for exactly that reason and never allowed to fail the webhook response itself. Stripe's own `checkout.session.completed` handling deliberately does *not* set this field — payment success there has never implied order confirmation, and this addition doesn't change that.
- **Refunds reuse the webhook's charge reference, not the event id**: `paymenttransaction.gatewayReference` is the *webhook event id* (used only for the delivery-idempotency unique constraint below) — issuing a real refund needs the charge/payment-intent id instead, stored separately as `paymenttransaction.providerChargeReference` (captured from `WebhookResult.chargeReference` at webhook-handling time). Don't try to refund against `gatewayReference`; it's the wrong identifier.
- **Webhook idempotency**: `paymenttransaction` has a `@@unique([gateway, gatewayReference])` constraint, and the idempotency key is the gateway's *event* id (Stripe's `event.id`), not the object the event is about (a checkout session id can't tell two different events about the same session apart). `PaymentsService.handleWebhook` relies on that unique constraint failing — catching both Prisma `P2002` (duplicate key, the common case) and `P2034` (write conflict/deadlock, observed under truly concurrent duplicate delivery) as "already processed, no-op." Don't replace this with a `findFirst`-then-`create` check — that's exactly the TOCTOU race this design avoids.
- **Raw body for webhooks**: `main.ts` passes `{ rawBody: true }` to `NestFactory.create`; the webhook controller reads `req.rawBody` (typed via `RawBodyRequest<Request>` from `@nestjs/common`) because Stripe signature verification needs the exact unparsed bytes, not the JSON-parsed body.
- **Dashboard date math is UAE-local (UTC+4), not server-local or UTC.** `DashboardService` computes "today"/"this week"/"this month" boundaries by shifting into a hardcoded +4h offset before truncating — UAE doesn't observe DST, so this is a stable constant, not a shortcut that will drift. The 30-day daily revenue series and top-products query use raw parameterized `$queryRaw`/`Prisma.sql` (`DATE(DATE_ADD(createdAt, INTERVAL 4 HOUR))`, plus a conditional `AND outletId = ${outletId}` fragment via `Prisma.sql`/`Prisma.empty`) rather than Prisma's `groupBy`, which can't group by a derived/truncated expression.
- **CORS** is an explicit allowlist (`ADMIN_ORIGINS` env var, comma-split) passed to `app.enableCors({ origin })` in `main.ts` — not `app.enableCors()` wide-open. Auth is JWT-header-based (`Authorization: Bearer`), so `credentials: true` is not needed.
- **Email sending** (`common/email.ts`'s `sendEmail()`) is platform-level, not per-shop bring-your-own — one Resend API key, one verified sending domain, unlike Payments/WhatsApp. Chosen deliberately: merchants don't need their own DNS/SPF/DKIM setup to get transactional email working, at the cost of every shop's email coming from the same domain (shop identity is carried in the `From` display name instead — `"${shopName} <notifications@${EMAIL_FROM_ADDRESS domain}>"` — not the address itself). Revisit per-shop sending only if a merchant specifically needs their own sending domain for reputation/branding reasons; it's a real option later (mirror `PaymentSettingsService`'s resolveCredentials pattern), just not needed to get real sending working now. `sendEmail()` falls back to `sendEmailStub()` (console.log) whenever `RESEND_API_KEY` is unset *or* the real Resend call itself fails (bad key, unverified domain, network error) — never throws, so a broken email provider can't fail order creation/checkout/auth. `email/providers/resend-email.provider.ts` is the real implementation (plain `fetch` against Resend's HTTP API, same as `MetaWhatsAppProvider` — no SDK dependency). Every call site must go through `sendEmail()`, never `sendEmailStub()` directly — `common/email-callsites.spec.ts` statically enforces this across `src/`. `RESEND_API_KEY=test` is a reserved sentinel `sendEmail()` short-circuits to the stub on (no network call at all) — this repo's local `.env` is set to it specifically so the e2e suite (every signup fires a verification email) isn't paying for a real, slow, and in this sandbox always-failing Resend round trip on every single spec; swap in a real `re_...` key only to test actual delivery locally.
- **`SignupDto`'s wizard-only fields are all `@IsOptional()` at the DTO level, even though the admin Account Setup wizard treats most of them as required.** `phone` (on `user`) and `businessType`/`trn`/`websiteUrl`/`address`/`operatingModel`/`branchCount` (on `shop`) back the wizard's Business/Location steps (`admin/lib/useAccountSetupForm.ts`) — but 40+ backend e2e specs call `POST /auth/signup` directly with the old minimal `{name, email, password, shopName, subdomain}` payload, so making any of these `@IsNotEmpty` at the DTO level would 400 every one of them. "Required" for these fields is enforced client-side only, in the wizard's own step validation — don't tighten the DTO to match without first updating every e2e spec that calls signup. `operatingModel` is stored on `shop` as a comma-joined string (`dto.operatingModel?.join(',')`), not a JSON array column.
- **Known pre-existing lint gap (as of 2026-08-04)**: `npm run lint` in `backend/` reports 179 errors/16 warnings, all pre-existing (not caused by any change in this session) — `tsc --noEmit` and `nest build` are both clean, so none of this is a compile-time or build-time issue. Categorized by rule, the large majority (`no-unsafe-member-access` 58, `unbound-method` 41, `no-unsafe-assignment` 36, `require-await` 19, `no-unsafe-argument` 15`) live almost entirely in `*.spec.ts`/`*.e2e-spec.ts` files and are the standard Jest-mock-typing false-positive pattern (`expect(mockedService.method).toHaveBeenCalledWith(...)` trips `unbound-method`; accessing fields off a loosely-typed mock/`jest.Mocked` result trips the `no-unsafe-*` family) — cosmetic, not indicative of a real bug. `no-unused-vars` (15) is almost entirely the four structural-stub payment providers' (`nomod`/`paypal`/`paytabs`/`telr`) intentionally-unused constructor params, consistent with their documented not-yet-implemented status. The handful of findings in real (non-spec) source were individually checked and are also not defects: `products.service.ts` (`(response as any).stockByOutlet = ...`) is a deliberate cast to bolt an extra field onto a DTO-typed response; `main.ts`'s `no-floating-promises` on the bare `bootstrap()` call is the standard unmodified NestJS scaffold pattern (a bootstrap failure still crashes the process visibly); `public.service.ts`/`order-notifications.service.ts`'s `restrict-template-expressions` and `products.service.ts`'s `no-base-to-string` all flag stringifying a Prisma `Decimal`/a P2002 `error.meta.target` array in a template literal — both have real, correct `toString()` behavior the linter doesn't model, not an `[object Object]` risk; `csv.util.ts`'s `no-irregular-whitespace` is a deliberately-embedded BOM character being stripped, not accidental whitespace. One finding is a genuine (if latent) type-safety hole worth knowing about: `scan.service.ts`'s `ownedProducts`/`ownedIngredients` (`no-unsafe-return`/`no-unsafe-member-access` on `.id`) come from a `condition ? this.prisma.x.findMany(...) : []` ternary passed into `Promise.all([...])` — TS can't cleanly infer the element type across a `Promise<T[]> | never[]` union, so it silently collapses to `any`; the *current* values are still correct real Prisma rows, but a future rename/reshape of the `select` here wouldn't be caught by the type checker. Not fixed in this session (explicitly out of scope — see `docs/audit-2026-08.md`); flagged here the same way the admin/storefront `react-hooks/set-state-in-effect` gap below is flagged, rather than fixed silently in an unrelated change.

## Admin frontend (`admin/`)

- Plain `fetch` wrapper in `lib/api.ts` (`apiFetch<T>`) calling the backend directly from the browser via `NEXT_PUBLIC_API_URL` — no server actions/route handlers, no data-fetching library (no SWR/React Query). Every page is a client component (`"use client"`) that fetches in `useEffect` and re-fetches after mutations by calling the same `refresh()` closure. The orders list additionally polls every 20s (`POLL_INTERVAL_MS` in `app/orders/page.tsx`) for near-real-time updates — deliberately polling, not a websocket/SSE channel. `apiFetch` attaches `Authorization: Bearer <token>` from `localStorage` (via `getToken()`/`setToken()`/`clearToken()`, SSR-safe behind `typeof window` guards) and clears the token on any `401`.
- **Auth/routing**: `lib/auth-context.tsx` (`AuthProvider`/`useAuth()`) hydrates the current user from `api.me()` on mount if a token exists. `components/RequireAuth.tsx` gates the whole app (wrapped in `app/layout.tsx`, inside `AuthProvider`/`OutletFilterProvider`) — redirects unauthenticated users to `/login`, and redirects authenticated users away from `/login`/`/signup`.
- **Outlet filtering**: `lib/outlet-context.tsx` (`OutletFilterProvider`/`useOutletFilter()`) fetches the outlet list once a user is known; `selectedOutletId` defaults to `null` ("all branches") for admins and is force-pinned to `user.outletId` for branch users, with `setSelectedOutletId` a no-op for branch role. This is UX-only belt-and-suspenders — the real enforcement is server-side (`resolveOutletFilter`) and does not depend on this frontend behaving correctly. `components/OutletSwitcher.tsx` renders `null` entirely for non-admins (hidden, not just disabled/filtered), per the project's explicit requirement that branch users never even see a switcher. Orders (kanban + history), Inventory, and the Dashboard all read `selectedOutletId` and pass it through to their API calls.
- **`/outlets`** (`app/outlets/page.tsx`) is the outlet + branch-account management page: client-side redirects non-admins away (`useEffect` checking `user.role !== 'admin'`), which is UX-only — every mutating endpoint it calls is independently `@Roles('admin')`-gated server-side.
- Shared response/DTO shapes live in `lib/types.ts` and must be kept in sync with the backend DTOs by hand (no generated client).
- **`components/ui/`** is a local design-system (check the directory for the current full set — it grows regularly): tables, cards, skeletons, `Button`/`Input`/`Textarea`/`Checkbox`/`Toggle`/`SegmentedToggle`, `BackButton`, `PageShell`, `Thumbnail`, `ImageDropzone`, `DateRangePicker`, `RichTextEditor`, `BulkActionBar`, chart primitives, `Modal` (see below), `Select`/`Combobox`, `ColorPicker`, `Spinner`/`PageLoader`, and a `Toast`/`useToast` context (`ToastProvider` wraps the app in `layout.tsx`; call `useToast()` from any client component instead of `alert()`). `StatusBadge` (order/payment status pill) lives at `components/StatusBadge.tsx`, not under `ui/`, for historical reasons. A handful of pure/testable pieces (e.g. `Thumbnail`, `lib/color-contrast.ts`) have colocated `vitest` specs — run `npm run test`.
- **`Select` (native `<select>` wrapper) vs. `Combobox` (searchable popover+list)**: `Select` is the default for any dropdown — it's a plain `<select>` for the free keyboard/mobile/a11y semantics, just wrapped for the shared trigger styling (matches `Input.tsx`'s relationship to `<input>`). Reach for `Combobox` only where the option list is genuinely long/searchable (product/category/outlet pickers) — it has no native semantics, so don't use it for short fixed lists (status, role, type enums) where `Select` is strictly better. Neither wraps Radix/cmdk — both are hand-rolled to shadcn's visual/interaction contract, same "no shadcn theme installed here" reasoning as the rest of `components/ui/` (see below).
- **`Button`'s `loading` prop** shows an inline `Spinner` and forces `disabled` — set it (in addition to, not instead of, the existing `disabled={saving}`) on the primary/danger action button of any async operation; don't hand-roll a separate disabled+spinner combination per call site.
- **Row actions on list/table pages are icon-only buttons** (a lucide icon, `aria-label`, no visible text — see `components/ui/Table.tsx`'s own doc comment for the exact class pair), one per action in its own trailing column. Two other treatments (a full `Button` with visible text; a plain underlined text link) existed on different pages before being converged onto this one — don't reintroduce either for a new list page.
- **Variant image assignment resolves by url, not id, while editing.** `VariantEditModal` reads the *live* Media gallery state (threaded down from `ProductForm`), not the product's saved `images` prop — a just-uploaded image already has a real url (upload happens immediately) but no `productimage` row/id until the whole product is next saved. The picker tracks the selection by url and only resolves/persists a real id in the variant's own save handler (via a scoped `updateProduct` call if needed), so a brand-new image can be assigned to a variant in the same editing session without saving the outer form first.
- **`BackButton`** (`components/ui/BackButton.tsx`) always navigates to an explicit parent route passed via its `href` prop (`<Link href="/inventory">`) — never `router.back()`/browser history. This was a deliberate reversal from an earlier history-based convention: switching tabs within a section (e.g. Inventory's Products/Categories/Movement History tabs) polluted history, so "Back" could land on whichever tab was last visited instead of the actual logical parent. Every nested page/section knows and hardcodes its own real parent path. A shared layout's `BackButton` still covers every page nested under it — a child page must not render a second one on top.
- **Theming**: `dark:` is selector-based (`@custom-variant dark (&:where(.dark, .dark *))` in `globals.css`), not the Tailwind default `@media (prefers-color-scheme: dark)` — a manual toggle needs JS control, which a media query can't give it. This is a Tailwind v4 CSS-first project (`@theme`/`@custom-variant` in `globals.css`) — there's no `tailwind.config.js`/`.ts` to check for a `darkMode` setting. An inline script in `app/layout.tsx`'s `<head>` (paired with `suppressHydrationWarning` on `<html>`) applies `.dark` before paint, reading `localStorage["requital_theme"]`. **Light is the hard default**: with no stored preference the script does *not* fall back to `window.matchMedia("(prefers-color-scheme: dark)")` — an earlier version did, which meant the admin silently opened in dark mode on any machine with OS dark mode on; dark mode now only ever activates via the explicit toggle. `lib/theme.ts`'s `useTheme()` (`{ isDark, setTheme }`) is the only other place allowed to touch that class/key — the toggle lives in the profile dropdown (`UserMenu.tsx`). The brand accent is `--color-accent` (`#069494` teal) in `globals.css`'s `@theme inline` block — change the value there, not at call sites (`bg-accent`/`text-accent`/`border-accent`/`ring-accent` etc. come from Tailwind v4 auto-generating utilities for any `--color-*` var). `--color-accent-text` is a darker shade for accent-colored *text* sitting directly on a light background (`#069494` is only ~3.7:1 against white, under WCAG AA's 4.5:1 for normal text; the darker shade clears it) — pattern is `text-accent-text dark:text-accent`, not `text-accent` alone, anywhere accent is used as a text color rather than a background/border/ring. Green/red stay the semantic state colors for `Toggle` (open/closed, active/inactive) — accent is for brand/UI chrome (active nav/tab state, primary buttons, focus rings), not status.
- **Tailwind v4 gotcha — a bare `border` class (no color utility) renders `currentColor`, not gray.** Unlike v3's default gray-200 border, v4 changed the unset default to `currentColor`, so `className="border rounded-lg"` with no explicit color silently renders a harsh black/text-colored border in light mode. This has already caused real bugs here (the Live Orders kanban board and several `OrderDetailModal` section cards) — always pair `border` with an explicit color utility (`border-gray-200`, `border-black/10`, etc.), never leave it bare.
- Several of these primitives were adapted from specific 21st.dev community components (translated from shadcn/Tremor CSS-variable classes to this project's plain Tailwind palette, since there's no shadcn theme installed here) — each carries a comment at the top of its file with the source URL and author for attribution. Check those comments before assuming a pattern is original.
- Page transitions and toast entrances are CSS-only (`page-transition` / `toast-enter`/`toast-exit` keyframe classes in `app/globals.css`), no animation library. `page-transition` is applied per-page (on each page's own root element), not on the shared `<main>` in `layout.tsx` — `layout.tsx` never remounts on navigation, so a class placed there would only ever play once. `TopBar` (persistent, rendered once in `layout.tsx` inside `RequireAuth`) is the only nav chrome — its "Requital" brand text always links home.
- **Navigation feedback is two independent layers, not one.** `components/ui/NavigationProgress.tsx` (mounted once in `layout.tsx`) drives an `nprogress` bar via a capture-phase `document` click listener (starts the bar the instant an internal `<a>`/`<Link>` is clicked — skips external origins, hash-only links, modified/non-primary clicks, and `target="_blank"`) paired with `usePathname()`'s effect calling `.done()` once the new route has mounted; this is the framework-agnostic half (App Router has no built-in "navigation started" event to hook — see `node_modules/next/dist/docs/01-app/01-getting-started/04-linking-and-navigating.md`). Separately, `app/**/loading.tsx` files (Next's route-level Suspense boundary) give the actual skeleton content — most data-fetching pages have one now, composed from `Skeleton.tsx`'s reusable shapes (`ListPageSkeleton`, `FormPageSkeleton`, `SplitFormSkeleton`, `SettingsCardsSkeleton`, `DashboardSkeleton`). **Where a route sits under a persistent `layout.tsx`** (Settings, Affiliate, Theme editor — anything with its own tabs/sub-nav rendered by a `layout.tsx` wrapping `{children}`) the route's `loading.tsx` must cover *only the content area*, not the chrome, since the layout stays mounted and doesn't re-render across sibling navigation. Skipped deliberately: pure-`redirect()` pages and pages with no data fetch before their first paint (auth screens, the home tile grid).
- Known pre-existing lint gap: `npm run lint` flags `react-hooks/set-state-in-effect` on the `useEffect(() => { refresh(); }, [refresh])` fetch-on-mount pattern used across the data pages. `next build` does not fail on it. Not yet fixed — flagged here rather than fixed silently in an unrelated change, since resolving it means restructuring the fetch pattern across every page.
- **All 21 modal components route through the shared `components/ui/Modal.tsx`** (a prior version of this file described them as independent hand-rolled panels — that's no longer true; they were consolidated into one shell). `size` is `"sm" | "md" | "lg"` → `max-w-md`/`max-w-2xl`/`max-w-4xl`; every size gets `max-h-[90vh]` with the scrollable body wrapped in the shared `modal-scroll` class (defined in `globals.css`, hides the scrollbar's up/down arrow buttons while keeping the scrollbar itself visible) and a sticky header. Entry/exit is `modal-in`/`modal-out` (fade+scale, `globals.css`, gated behind `prefers-reduced-motion`) — `onClose` is deferred until the exit animation finishes, so callers don't need their own timing logic.
- **Modals close only via their own X/Cancel button, never backdrop click** — Modal's backdrop `div` carries no `onClick` handler, full stop. `CommandPalette.tsx` (Cmd+K search) is the one deliberate exception (not built on `Modal`), left closable by backdrop click since it has no X/Cancel button of its own and only closes otherwise via Escape.
- **`Modal`'s `children` (and `footer`) accept a render-prop form**, `(requestClose) => ReactNode` — same pattern as `DropdownMenu.tsx`'s `close` callback — so a form's own Cancel/Save button can trigger the exit animation instead of calling the raw `onClose` prop directly. For anything with a native `type="submit"` button, keep the whole form (fields *and* action row) inside one `<form>` passed as `children`, with the action row styled `sticky bottom-0` inside the scrollable body — don't split the submit button into the separate `footer` prop, since that renders outside the `<form>` DOM subtree and silently breaks native submission. `footer` (as plain `ReactNode` or the render-prop form) is only for non-form modals (confirm dialogs, CSV import).
- **No modal in this app has in-modal tabs of its own** — `OrderDetailModal`'s Details/Invoice split (see `invoices/` in Backend architecture) is the one exception, and it reuses `components/ui/SegmentedToggle.tsx` (built for Settings-style page toggles, not originally a tab primitive) as its switcher rather than inventing a real tabs component for a single use site; reach for the same trick before building a new one.
- `VariantEditModal` is the one modal still wrapped in `createPortal(..., document.body)` on top of `Modal` — originally because it's mounted inside `ProductForm`'s own page-level `<form>`, and a nested `<form>` inside another is invalid HTML; portaling out of the DOM tree avoided the browser attributing its submit to the outer form. **Stale as of the Product Wizard rewrite below**: `ProductForm.tsx` no longer renders a `<form>` element at all (every button is `type="button"` with its own `onClick`, submit is triggered directly) — the portal's original reason no longer applies, but it hasn't been re-evaluated/removed. Every other modal renders inline.

### Product wizard (`ProductForm.tsx`)

`/inventory/new` and `/inventory/[id]/edit` both render `ProductForm`, a 3-step wizard (Basics → Pricing & Inventory → Organization), not a single long-scroll form. All state/validation/save logic lives in `lib/useProductForm.ts` (extracted verbatim from the pre-wizard form — the save payload/API calls/validation rules didn't change, only the presentation), returned as one object threaded to each step component (`ProductFormStepBasics/Pricing/Organization.tsx`) — no React Context, plain prop-drilling one level. `components/ui/Stepper.tsx` is the progress indicator (generic: `{label, status}[]`, click only navigates to a `"completed"` step). Step index is component state, not a URL param — there's no `?step=` query string. A few things worth knowing before touching it:
- **Cross-step validation on final submit**: `useProductForm`'s full validation (name/sku/price/image/categories — unchanged from before) only runs at the Step-3 submit button, not on every `Next`. If it fails for a field that lives on an earlier step, `ProductForm.tsx`'s `FIELD_STEP` map jumps the wizard back to the earliest errored step so the error is actually visible.
- **`PageShell variant="wide"`, not `"form"`** — every step's Cards manage their own internal grids (Pricing's 3-up row, etc.), which is what PageShell's own doc comment calls `"wide"` for. `"form"` (max-w-4xl) was tried first and left 700-1100px of dead space at desktop widths — see `tools/screenshot/check-wizard-step2-width.js`, the regression guard for this, and "Page width convention" below for the general lesson.
- **Unsaved-changes guard**: a capture-phase `document` click listener (same technique `NavigationProgress.tsx` uses for its own global click listener) intercepts any in-app link click while the wizard is mounted and confirms before allowing navigation; paired with `beforeunload` for tab close/refresh. Fires for the whole time the wizard is mounted, not a per-field dirty diff. Extracted into `lib/useUnsavedChangesGuard.ts` (was originally a local function in this file) so the Account Setup wizard below can share it instead of a second copy — any future multi-step wizard should reuse it too.

### Account Setup wizard (`AccountSetup.tsx`)

`/signup` renders `AccountSetup`, a 4-step wizard (Personal Info → Business Info → Location & Setup → Review & Confirm), replacing the old single-page signup form — same `useProductForm`-style split as the Product wizard above: `lib/useAccountSetupForm.ts` owns all state/validation/submit logic (individual `useState` per field, not a single dynamic record, matching `useProductForm`'s convention), the four `AccountSetupStep*.tsx` components are pure presentation, and `components/ui/Stepper.tsx` is reused as-is for the progress indicator (its existing click-to-jump-on-completed-step behavior doubles as the wizard's "edit a previous step from Review" affordance — there's no separate per-field Edit button).
- **`lib/validators.ts`** has the pure field validators (`validateEmail`/`validatePhone`/`validatePassword`/`validateTrn`/`validateUrl`, plus `passwordRequirements()` for the live checklist) — framework-free so they're directly unit-testable and so `backend/src/auth/dto/signup.dto.ts`'s hand-mirrored regexes (email/phone/websiteUrl) can be kept in sync by hand against a single source of truth on the frontend side.
- **`components/ui/FieldErrorMessage.tsx`** (icon+text inline error) is deliberately *not* used for every field — `Input`/`Select` already render their own red-border+red-text error via their built-in `error` prop, which covers every text/select field in this wizard. `FieldErrorMessage` is only reached for the Operating Model checkbox group (no wrapping `Input`/`Select` to carry an `error` prop) and the cross-field error modal's bullet list. Don't reintroduce it as a wrapper around `Input`'s own error rendering — that would just duplicate it.
- **Cross-field blocking modal** ("Fix these issues to continue"): pressing Next/Create Account with any invalid field in the current (or, on final submit, any) step opens a `Modal` listing every errored field, non-dismissible via backdrop per the shared `Modal` convention. "Back to Step N" jumps to the earliest errored step and scroll+focuses the earliest errored field via a `fieldRefs` map (`registerFieldRef(field)`, a ref callback registered on each `Input`/`Select`/the checkbox-group's wrapper div) — the focus/scroll is deferred by `Modal`'s own exit-animation duration (150ms) so it runs after the modal has actually unmounted.
- **Success/error modals on final submit**: success shows a non-dismissible "Welcome, {firstName}!" modal whose `onClose` intentionally routes through the same "Enter App" handler (not a no-op) — `Modal.tsx` has no prop to disable its built-in Escape-closes behavior, so leaving `onClose` empty would strand the modal in a half-closed state if the user pressed Escape instead of clicking the CTA. The error modal's "Back" returns to Step 1; "Try Again" stays on Step 4.
- **`AuthCard`'s `maxWidthClassName` prop** (default `"max-w-sm"`, unchanged for every other pre-auth screen) lets this wizard opt into `"max-w-2xl"` for its 2-column Business/Location steps, instead of widening the shared card for every login/forgot-password/etc. screen that doesn't need it.
- Backend support for the extra fields collected on Steps 2–3 (phone, businessType, trn, websiteUrl, address, operatingModel, branchCount) is covered above under "Backend architecture"'s `SignupDto` note — they're wizard-required but DTO-optional.

### Settings/config page layout convention

Worked out iteratively across several passes on Business Settings and the Outlet edit tabs, then generalized — apply it by default to every settings/config page built from here on, not just on request:

1. **Card containers**: every distinct section (a named group of related fields) is wrapped in `components/ui/Card.tsx` (`rounded-lg border border-black/10 dark:border-white/10 bg-white dark:bg-zinc-900 p-6` — the same shade `StatCard` and the `Table` wrapper already use). Never separate sections with just a heading on bare page background. Card boundaries follow whatever headings the content already has — don't invent new sub-sections just to have more cards, and don't split a group of related fields (e.g. Business Type + Currency + Default Language, all under one "General" heading) into one card each.
2. **Grid density matches field length**: short fields (dropdowns, numbers, short text — email, phone, currency, time zone) go `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`, never a single stacked column. Long-form fields (descriptions, addresses, radio groups with long option text) get `sm:col-span-2 lg:col-span-3` to stay full-width within that same grid.
3. **Fill height gaps between side-by-side sections**: if two cards sit side by side (`sm:grid-cols-2`) and a later section could reasonably sit in the shorter column instead of stacking full-width below, do that. Judgment call, not automatic — don't force an unrelated section sideways just to fill space, and don't override an explicit instruction to keep something full-width (e.g. Business Hours, which is a table, not a field).
4. **Toggle, not Checkbox, for binary state fields**: anything representing an on/off *status* (active/inactive, open/closed, enabled/disabled as a single state of one thing — outlet active, delivery/pickup available, force-closed override) uses `components/ui/Toggle.tsx` (green = on, neutral grey = off — off used to be red, but that read as "broken," not "not configured yet"; red is not used anywhere in this control), the same switch `OutletEditSidebar`'s "Outlet is Active" control uses. `Checkbox` is reserved for actual multi-select option lists where several independent boxes are ticked together (e.g. Store Configuration's "Product image zoom", "Show category menu") — not a single status field standing alone.
5. **Compact grouping over spread rows**: related controls in one row (a value plus its own status toggle) sit close together, left-aligned — not stretched to opposite edges of a wide card with `justify-between` dead space in between, unless there's a specific reason (a card header + its action button) to do that.
6. **Responsive collapse**: every grid above degrades to `grid-cols-1` below `sm`. Never ship a multi-column layout that doesn't collapse on mobile.

### Store Configuration "Coming Soon" toggles

Business Settings > Store Configuration has a "Coming Soon" card of `shop.xEnabled` boolean toggles that ship ahead of the feature they'll gate — they persist a preference but do nothing until wired up. `customerSurveyEnabled`/`disableStoreCart` started there and were later wired; only `dynamicThemeBuilderEnabled` remains inert as of this writing. (`productVariantsEnabled`/`productAttributesEnabled`/`productFaqsEnabled` also went through this same path once, but were later removed entirely — the Variants/Attributes/FAQs sections are no longer gated by a shop-wide toggle at all; see "Simple/Advanced product editor mode" below.) The convention for wiring one up, once its feature is actually built:

- The toggle is a pure **admin-UI/storefront-rendering gate**, not backend enforcement — the backend DTO/service usually has no idea the toggle exists (see `customerSurveyEnabled`: `OrdersService` reads it only to decide whether to fire the survey email, nothing in the catalog/pricing path branches on it). Admin fetches it via `getShop()` and conditionally renders the gated behavior. See `disableStoreCart`/`cartDisabledMode` for the pattern.
- Move the toggle out of the "Coming Soon" `Card` into its own real section on the Store Configuration page once wired (see `store-configuration/page.tsx`'s Cart & Checkout/Post-Purchase cards) — don't leave a functional toggle sitting under "Coming Soon" copy.
- A toggle can carry a second field for its own mode/config, validated with `@IsIn` rather than a dedicated Prisma enum for a small fixed string set (see `cartDisabledMode`) — only reveal that control in the admin UI when the parent toggle is on.

### Simple/Advanced product editor mode, and per-product Variants/Attributes/FAQs

`shop.productEditorMode` (`'simple' | 'advanced'`, plain string per this schema's no-Prisma-enums convention, not the shop-wide `xEnabled` toggle pattern above) picks which experience `ProductForm.tsx` renders: `'simple'` is the existing 3-step wizard (Basics → Pricing & Inventory → Organization); `'advanced'` is a single scrollable page (all six sections, including Variants/Attributes/FAQs, stacked with a sticky left anchor nav, `hidden` below `lg`) with no stepper. Set on the Account Setup wizard's Review & Confirm step (defaults to `'simple'`), editable later via a `SegmentedToggle` on Business Information ("Product Editor" card).

This replaced the old shop-wide `productVariantsEnabled`/`productAttributesEnabled`/`productFaqsEnabled` toggles (see "Coming Soon toggles" above) with a **per-product** opt-in instead: `product.showVariants`/`showAttributes`/`showFaqs` (plain booleans, persisted with the product, `@default(false)`). `productEditorMode` only controls a *new* product's starting values for these three (false for simple, true for advanced) — an existing product's own saved values always win regardless of the shop's current mode (see `useProductForm`'s `getShop()` effect). `VariantsSection`/`AttributesSection`/`FaqsSection` all route through the shared `ProductFeatureSection.tsx` wrapper: disabled renders just a "+ Add X" link; enabled wraps the real editor in a native `<details>` (no JS accordion lib) plus a "Remove X" action, with `defaultOpen` read once on mount (simple mode opens immediately since enabling *is* the user's action; advanced mode starts collapsed) — never re-applied on re-render, so a user's manual expand/collapse always sticks. Storefront gating for Attributes/FAQs on the PDP moved the same way, from `shop.productAttributesEnabled`/`productFaqsEnabled` to `product.showAttributes`/`showFaqs`.

`shop.productEditorMode` was later extended beyond the product form to gate UI on Orders, Customers, and the Dashboard too — `lib/useShopMode.ts` is the shared hook for this (a `getShop()` effect identical to `useProductForm`'s own, refetched fresh on every mount rather than held in a shared context, so a mode change saved in Settings shows up on the next client-side navigation with no reload or cross-tab sync needed). Each page branches on the resolved mode rather than maintaining two parallel page trees: `app/orders/page.tsx` hides the History tab and trims kanban-card fields (no delivery date/age/item notes) in simple mode, swapping in `components/SimpleOrderDetailModal.tsx` (status/items/total/Cancel+advance only) for the full `OrderDetailModal`; `app/customers/page.tsx`/`[id]/page.tsx` swap in an Email column for the selection-checkbox/bulk-export column and hide the stat-card row + Birthday field; `app/dashboard/page.tsx` renders `components/SimpleDashboard.tsx` (Revenue Today/Orders Today/Top 3 Products, using `defaultDateRange(1)` instead of the date picker) in place of the full week/month dashboard; and the home page (`app/page.tsx`) greys out — doesn't hide — the Reports tile. Same as every other `xEnabled` toggle in this file: a pure admin-UI rendering gate, no backend enforcement, and simple mode never removes a capability the merchant can't still reach directly (Order History stays a live route, just unlinked from the simple kanban page).

### Page width convention — always route through the shared shell

Narrow/constrained-width layout bugs have recurred repeatedly across both frontends (Settings tabs, the admin homepage tile grid, Theme Advanced, Collections/Draft Orders detail pages, the storefront trust strip, sign-in/order-tracking cards). The root cause each time was the same: a `page.tsx` hand-rolling its own `max-w-*` wrapper instead of rendering through the one component that owns that decision — `admin/components/ui/PageShell.tsx` or `storefront/components/StorefrontPageShell.tsx` — so nothing enforced a deliberately-chosen width; it just inherited whatever cap a wrapper div happened to use at write time.

- **Every `app/**/page.tsx` routes its top-level content through `PageShell` (admin) / `StorefrontPageShell` (storefront).** Pick the variant that matches the content (see the variant comments atop each component) — don't reach for a raw `max-w-*` div as a shortcut, even for content that's genuinely single-column. Single-column doesn't mean "cap it as narrow as looks reasonable in the editor" — measure the rendered result against real available width before assuming a tight cap is correct (see PageShell's `"form"` variant history: `max-w-3xl` was picked once, never re-measured, and read as an arbitrary ~400px dead-space gap on real desktop viewports even though the content genuinely had no multi-column grid).
- **Raw `max-w-*` outside those two files is fine for small elements** (an image, a modal/drawer, a text-truncation span, a preview widget nested inside an already-shelled page) — it's specifically the page's own outermost content wrapper that must not hand-roll a width.
- Exceptions: pages with no dashboard/storefront chrome at all (admin's pre-auth login/signup/forgot-password/reset-password/accept-invite/verify-email) legitimately have nothing to route through. The storefront bio page is deliberately phone-width by design regardless of viewport, matching every other "link in bio" tool's convention.
- **Guardrail**: `node tools/check-page-width.js` greps every `page.tsx` in both apps for a `max-w-` that isn't inside a file importing `PageShell`/`StorefrontPageShell`, modulo a short allowlist for the exceptions above. Run it after adding or editing any page — it should report zero violations. **Known blind spot**: it only scans `page.tsx` files, so a `max-w-` hidden one level down inside a *component* a page renders is invisible to it — e.g. `admin/components/CollectionForm.tsx` hand-rolls `className="max-w-3xl"` on its own `<form>`, nested inside a plain, unconstrained `<PageShell>`; `app/collections/new/page.tsx` itself has no `max-w-` and passes clean. Known, not yet fixed as of this writing.
  It also can't catch a page that imports the shell correctly but picks a variant too narrow for its content (a design judgment, not a text pattern — see the Product Wizard's own `variant="form"` → `"wide"` fix above, where every input already had `w-full` and every grid was already responsive). Two follow-up tools exist for the two other failure modes: `node tools/check-form-width.js` (static heuristic — flags a hardcoded non-responsive `grid-cols-N` or a fixed-width text input missing `w-full`; expect legitimate false positives for grids inside intentionally-narrow containers like Modals or `StorefrontPageShell variant="medium"`, documented in the script itself) and `tools/screenshot/measure.js` (a reusable puppeteer helper — locate your landmark element by text/class in your own `page.evaluate`, never a guessable structural selector, then measure its gap to the viewport's right edge at the four standard breakpoints; `check-wizard-step2-width.js` in the same directory is the example to copy). Neither of these two replaces `check-page-width.js` — each catches a genuinely different failure mode.

### Location picking — duplicated, not shared, between the two apps

`MapPicker`/`MapPickerLeaflet` (Leaflet, not Google Maps) exist as **separate, independently-maintained copies** in `admin/components/` and `storefront/components/` — same deliberate no-shared-package duplication as every other cross-app UI piece. Both wrap the same gotcha: Leaflet's default marker icon resolves its image URLs relative to Leaflet's own module location, which breaks under a bundler (Turbopack/webpack) — fixed by deleting `L.Icon.Default.prototype._getIconUrl` and pointing `iconUrl`/`iconRetinaUrl` at real static files under `public/leaflet/`. Both call the backend's `common/nominatim.ts` proxy (via `outlets` or `public`, respectively) rather than hitting Nominatim directly from the browser.

## Storefront frontend (`storefront/`)

- **Tenant resolution is a path segment, not a domain.** Every route lives under `app/[shop]/...`; the dynamic `shop` param is the shop's slug/subdomain, resolved backend-side by `/public/:shopSlug/...`. This is a deliberate departure from the original SRS's separate-top-level-domain-per-merchant plan (see "What this is") — no middleware/domain routing exists.
- **`lib/shop-context.tsx`** (`ShopProvider`/`useShop()`) fetches the shop + its outlets once per mount and drives live per-shop theming: `resolveThemeCssVars` reads `shop.brandColor`/`shop.colors`/`shop.fontFamily` (falling back to a default teal accent) and sets CSS custom properties directly on the root, including an auto-contrast text color (`color-contrast.ts`, same WCAG-AA-guard pattern as admin's `--color-accent-text`) rather than ever hardcoding white/black on top of a merchant-chosen color.
- **Homepage layout is theme-driven**: `app/[shop]/page.tsx` dispatches on `shop.homepageLayout` (`classic` / `slideshow` / `featured_grid`, set from the admin Theme editor's Advanced tab) to one of `components/home-layouts/*` — an unrecognized/`"custom"` value falls back to Classic rather than rendering nothing.
- **Header/footer chrome is real and theme-driven, not a fixed shell**: `components/AnnouncementBar.tsx` (off by default; static-joined or CSS-marquee-scrolling text — name any new keyframe-animation class without an `animate-` prefix, Tailwind v4 tries to resolve that prefix against a `--animate-*` theme token and silently produces no animation if one doesn't exist), `components/Footer.tsx` (`footerLayout`: `columns` | `centered`; brand/logo/description, `Useful Links` linking only to policy types that actually have content, `Follow Us` from `shop.socialLinks`, `Contact Us`, payment-method badges derived from real enabled providers), and `components/WhatsAppFloatingButton.tsx` (gated on `shop.whatsappFloatingButtonEnabled`) are all real, independently-toggleable sections, not a static per-template shell. `headerDensity`/`footerDensity` (`compact` | `regular` | `spacious`, height/padding only) are orthogonal to `topBarLayout`/`footerLayout` (arrangement) — any density pairs with any arrangement. `components/home-layouts/SlideshowHero.tsx` reads real `shop.banners` (the `bannerimage` model, admin-managed, uncapped) with a product-thumbnail fallback only when no banners exist.
- **Policy pages** (`policypage` model — `TERMS`/`PRIVACY`/`REFUND`/`PAYMENT`/`SHIPPING`, admin-authored rich text) are per-shop-optional: `app/[shop]/policies/[type]/page.tsx` renders a real 404-shaped "not published" state rather than a broken/empty page when a type has no content, and the footer's Useful Links column only ever links to types that do. `components/CookieConsentBanner.tsx` (mounted in `ShopLayoutClient.tsx` alongside `WhatsAppFloatingButton`) is a separate, dismissible, non-blocking bottom bar (Accept all / Decline non-essential) — choice persisted per-shop in localStorage (`requital_storefront_cookie_consent:${shopSlug}`, same scoped-key convention as `lib/cart.tsx` below) with no analytics wiring behind it yet, just the preference.
- **`components/SearchBar.tsx`** — the header search icon (wired into all 3 `TopBar` layout variants), a debounced (300ms) dropdown against `storefront-search/` (see Backend architecture) with a loading state and a "Did you mean X?" prompt when the response's `suggestion` field is set. `components/NotifyMeForm.tsx` is the PDP's "notify me when available" form, shown only when the selected product/variant is out of stock (see `notify-subscriptions/` above); its restock email links to `app/[shop]/unsubscribe-notify/page.tsx`, a one-click unsubscribe landing page.
- **`lib/cart.tsx`** is a localStorage-persisted cart context (items + `outletId` + `discountCode`, plus an optional per-item `note` typed on the PDP that rides along to order creation as `orderitem.note`). The discount code rides along with the cart for UX, but the discount *amount* is never trusted client-side — checkout re-validates and the server atomically claims/computes it at order-creation time, same as the admin-side discount redemption path.
- **Checkout add-ons**: before rendering `CheckoutSteps`/`CheckoutSinglePage`, `app/[shop]/checkout/page.tsx` gates on a one-time `AddonPrompt` popup (`components/checkout/AddonPrompt.tsx`) whenever the shop has any `isCheckoutAddon` product not already in the cart — skipped entirely for `cartDisabledMode === "contact_to_order"` shops. Selecting an add-on just calls the same `useCart().addItem` any normal add-to-cart action uses; skipping/dismissing (or having zero eligible add-ons) proceeds straight to the real checkout layout.
- **`lib/payment-methods.ts`**'s `resolvePaymentMethods` is a pure function (no React, directly unit-tested) computing the delivery vs. pickup payment-method lists from the shop's per-method toggles — it also checks that the shop's active card processor is actually enabled, not just that "online card" is toggled on, so checkout never offers an option that would 400.
- **`lib/api.ts`** follows the same plain-`fetch`, no-data-library convention as `admin/lib/api.ts` (`resolveImageUrl` for backend-relative upload paths, etc.) but is unauthenticated throughout — every call hits a `/public/:shopSlug/...` route, never an admin-authenticated one.
- Order tracking (`app/[shop]/orders/track/`) looks orders up by `order.trackingToken`, an opaque per-order token handed to the customer at checkout — not the sequential order id, which is never treated as a lookup credential on its own.
- The logged-in customer's own order-history detail page (`app/[shop]/account/orders/[id]/`) shows a "Download Invoice" link only when `hasInvoice` is true on that order's summary (see backend `customer-account/`'s note) — fetched as an authenticated JS request and turned into a Blob download client-side, not a plain `<a href>`, since the endpoint needs the customer's bearer token attached.
- Real unit-test coverage via `vitest` (`npm run test`) on the pure-logic modules — `cart`, `api`, `bio-page`, `phone`, `referral`, `seo`, `sitemap`, `slots`, `color-contrast`, and the `home-layouts` components.
