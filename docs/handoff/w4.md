## Decisions

* **Documents only.** `CreditNotesService` writes only to `creditnote`, `invoicecounter` and the audit log. `test/credit-notes.e2e-spec.ts` snapshots order, orderitem, paymenttransaction, orderreturn(+items) and invoice rows before and after issuing and asserts they are byte-identical.
* **Two shapes.** Full (`reason` cancellation|correction, no returnId): copies the invoice's frozen subtotal/tax/total, i.e. the exact reversal incl. delivery and discount. Return (`reason` return + `returnId`): the returned units at captured price, pro rata share of the order discount (by gross), and `taxAmount * returnedQty / lineQty` per line, each rounded once with `roundMoney(.., currency)`; total is built from the ROUNDED components so the column adds up (exclusive: sub - disc + tax; inclusive: sub - disc).
* **NULL tax = unknown.** Return credit note on an order where a returned line has NULL `taxAmount` -> 400 ("predates per-line tax capture ... Issue a full credit note instead"). Nothing is inserted and no CN number is burned. A FULL credit note on such an order is allowed: it needs no per-line tax, `creditnote.taxAmount` is the invoice's own frozen order-level figure, and the lines print their tax as unknown (em dash, no Tax summary), exactly like the invoice. Known-zero (captured 0) is credited normally.
* **Cap.** Inside one transaction: `SELECT ... FROM invoice WHERE id AND shopId FOR UPDATE` (serialises all issuance for that invoice), then `SUM(total)` of existing notes, compared in integer minor units (`toMinorUnits`) against `invoice.total`; over -> 400. Also: one note per return (409, plus `UNIQUE(returnId)` backstop), at most one full note, and a full note is refused once any note exists (409). The CN number is allocated only after every check passes, so a rejected attempt burns no number.
* **Permissions.** Roles as `POST /invoices` (`admin, branch, order_manager` write; plus `viewer` read). Scope = `OrdersService.findOne` (shop + outlet + `orders.view`, 404 across shops/outlets). Issuing additionally calls `BranchRolesService.assertPermission(ctx, order.outletId, 'orders.manage')` - STRICTER than invoice generation, which only needs view. Observation (not changed): `POST /invoices` itself has no `orders.manage` check, so a read-only branch role can still generate an invoice.
* **Reason `cancellation`** requires `order.status = 'cancelled'`; `correction` has no precondition.
* **Rendering.** Reuses `renderInvoiceHtml` (new `type: 'CREDIT_NOTE'` + optional `creditNote` block: title "Credit Note", "Against invoice INV-xxxx (date)", "Reason", "Total credited", no cash-due box). Money uses the credit note's own captured `currency` and `toMajorUnitString` (KWD = 3 decimals). Snapshot (`creditnote.snapshotJson`, JSON, version 1) holds shop/customer blocks, lines, original invoice number/date, credited discount/delivery, tax-inclusive flag; render never reads live order/shop data. Tax summary rebuilt from the frozen lines with `buildTaxBreakdown`.
* **Not built (per brief):** invoice reissue, customer route, bilingual layout, auto-issue on return/cancel, free-text notes on the credit note.

## Endpoints
`POST /credit-notes {orderId, reason, returnId?}`, `GET /credit-notes?orderId=`, `GET /credit-notes/:id/pdf` (text/html, same as invoices). Admin: "Credit notes" panel on the order's Invoice tab (list, issue, preview, print).

> ### Credit notes (I18N-10)

Numbered `CN-0001` per shop from `invoicecounter` with `type='CREDIT_NOTE'` (`nextInvoiceNumber` takes it; it is NOT in `INVOICE_TYPES`, which gates `POST /invoices`). NULL per-line tax = unknown: a return note on a pre-capture order is a 400; a full note is allowed. The sum of notes can never exceed `invoice.total`: enforced under `SELECT ... FOR UPDATE` on the invoice row in the issuing transaction (`test/credit-notes.e2e-spec.ts` has the concurrency tests); one note per return (`UNIQUE(returnId)`), one full note per invoice. Issuing needs `orders.manage` at the order's outlet. Still deferred: invoice reissue (needs the `UNIQUE(orderId,type)` change), customer route, bilingual layout (I18N-9).
