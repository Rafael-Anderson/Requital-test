# T1: 128-bit survey tokens

No migration (`surveyresponse.token` is VARCHAR(191) with a UNIQUE index since 20260802190000; db/types.ts unchanged). Branch fix/survey-token-128bit.

## Change
- `common/token-hash.ts`: `generateSurveyToken()` is now `randomBytes(16)` as 32 uppercase hex characters (128 bits). Hex on purpose: the column is utf8mb4_unicode_ci (case-insensitive), so a mixed-case alphabet such as base64url would lose entropy per character.
- `OrderNotificationsService.notifySurveyRequest`: the INSERT retries with a fresh token on a duplicate TOKEN (up to 3 attempts); a duplicate ORDER (a concurrent call already created the row) returns quietly instead of throwing.
- Old tokens: untouched, not backfilled. Every consumer is an exact match on the unique column. Verified that nothing validates a token's length or shape: the three controller routes take a raw `@Query('token')` (only a trim-empty check, 400), there is no DTO `@Length/@Matches`, the storefront page and `lib/api.ts` pass the token through `encodeURIComponent` only, and the email link builder (`storefrontUrl(shop, '/survey?token=' + token)`, also in `notifySurveyConsentGiven`) is length agnostic.

## Where tokens are generated / compared / logged
- Generated: only `generateSurveyToken()` (one caller, order-notifications.service).
- Compared: `lookupSurvey`, `submitSurvey`, `withdrawSurveyConsent` in public.service.ts (SQL `WHERE token = ?`), the admin reviews module addresses rows by id, not token. Logged: nowhere (the email job payload carries the link, as before).
- Constant-time comparison is not needed: the comparison happens inside the database's unique-index lookup, which an attacker cannot time at byte granularity through network and query noise, and the guess space is now 2^128. There is no secret-vs-input comparison in application code to leak through timing.
- Unknown and malformed tokens of any length keep the identical 404; the state-changing routes keep the 20/min/IP throttle.

## Same-weakness review of other short public tokens (reported, NOT changed)
- `order.trackingToken` (`generateTrackingCode`, `randomBytes(5)` = 40 bits, uppercase hex, VARCHAR(191) unique). Used by `GET /public/orders/lookup?token=` (unthrottled beyond the global 100 req/min/IP) and shown to customers as a code they may read out or type (`orders/track`), which is why it is short. Read-only status page; the response excludes phone, email and address. Widening it is not the same one-line change: the code is displayed for hand entry and two generators (public.service.ts:1790, orders.service.ts:492) plus the UI would change. Recommendation: keep the short code for hand entry but stop treating it as a link credential (a separate long link token), or add a per-IP throttle to `/public/orders/lookup`.
- Case-insensitivity: all these lookups are case-insensitive and ignore trailing spaces (utf8mb4_unicode_ci PAD SPACE). Harmless for hex tokens; worth knowing for any future mixed-case token.
- Array-valued `?token=a&token=b` reaches `token.trim()` as an array: existing behaviour, answered with an error status rather than a data leak (the withdraw spec accepts 400 or 404). Not changed.
- Gift card codes: 80 bits (`randomBytes(10)`), fine. Opaque auth tokens: 256 bits.

## Tests
- `src/common/token-hash.spec.ts`: 2000 tokens match `^[0-9A-F]{32}$`, no repeats.
- `test/survey-consent-withdrawal.e2e-spec.ts` ("token width"): a notify-created token is 32 hex and works for lookup, submit, withdraw while its 10-char prefix 404s; a legacy 10-hex token looks up, submits and withdraws; malformed tokens (31/33/5000 chars, non hex, prefix, extended, SQL-ish) get the identical 404 on all three routes; a forced token collision is retried (3 generator calls, one row, fresh token).
- `storefront/app/[shop]/survey/page.test.tsx`: both token shapes pass through lookup, submit and withdraw verbatim.
