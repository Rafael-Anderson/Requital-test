## 1. Premises checked (file:line evidence)

| Brief premise | Result |
|---|---|
| An order-level marketing-consent field may already exist | **No.** The only record of a cookie choice is `localStorage` key `requital_storefront_cookie_consent:<shop>` written by `storefront/components/CookieConsentBanner.tsx` (comment there: "no analytics wiring yet"). `grep -i consent` over `backend/src` finds nothing relevant, `order` has no such column, and `createOrder` (`backend/src/public/public.service.ts`) never saw consent. So consent is captured at checkout and stored in `order.attributionJson.consent.marketing` (`true`/`false`/`null`; NULL or absent = unknown). The CAPI trigger **and** handler both treat anything but an explicit `true` as "send nothing". |
| `applyWebhookResult` covers webhook and reconciliation | **Yes.** `payments.service.ts` `applyWebhookResult` is called by `handleWebhook` (line ~265) and by `payment-reconciliation.service.ts:133`. One non-obvious point that shaped the design: a webhook (`evt_x`) and a later reconciliation (`reconciled:<session>`) have **different** `gatewayReference`s, so the `paymenttransaction` unique index does NOT stop the second one from reaching the "paid" branch. Dedupe therefore has to be the job key, not the payment idempotency. |
| Job queue idempotency mechanism | `job.idempotencyKey` has a **global** `UNIQUE` index (`20260806090000_job_queue`), and `JobsService.enqueue` swallows 1062/lock-conflict and returns the existing row (`jobs.service.ts:82`). The key is `capi:purchase:<orderId>`; order ids are global, so there is no cross-shop collision. |
| Two triggers: paid transition for online methods, creation for pay-on-delivery and pickup | Confirmed, plus a third the brief did not name: an order fully covered by a gift card is created already `paid` with no gateway session, so it never reaches `applyWebhookResult`. It is handled by the creation trigger (`!(gatewayName && remainderTotal > 0)`). Staff-created / draft-order "mark paid" (`draft-orders.service.ts:301`) is deliberately not wired: those orders have no browser, no attribution and no consent, so CAPI would send nothing anyway. |
| "orders and revenue in the shop currency via the money hook" | **Adapted.** Since A6 a shop can hold orders in several currencies over its life; summing them under one label would be a wrong number. The report groups by source, medium, campaign **and the order's own captured currency**, and each row is rendered with `formatMoney(row.revenue, row.currency)`. No aggregate is shown across currencies, so `useShopCurrency` is never needed. |
| CSP/helmet | There is no helmet. The storefront CSP is a static header in `storefront/next.config.ts`. A static header cannot vary per shop, so provider hosts are allowed globally (script, connect, img only), and the real gate is the consent switch. See risks. |
| `STOREFRONT_URL` / `event_source_url` | Built with `storefrontUrl(shop, ...)` like every other customer-facing URL (check-storefront-url guardrail passes). |

Pre-existing quirk replicated on purpose: the other reports treat a bare-date `dateTo` as midnight, so the end day is
excluded (`reports.service.ts:20-23`). The attribution report uses the same semantic so its numbers reconcile with the
General Report for the same range. Not fixed here (out of scope).

## 2. What was built

### Backend
- `shopanalytics` table (migration `20261005100000`), one row per shop, created lazily on first save. Only `metaCapiTokenEnc` is secret
  (AES-256-GCM via `common/crypto.ts`). `GET/PATCH /analytics-settings` is admin-only and scoped to `ctx.shopId` (no id in the path).
  `null` clears, an absent key is left alone. The token is write-only: responses carry `metaCapiTokenSet: boolean` only; the audit-log row
  records field **names**, never values. Every id is format-validated (`shop-analytics/analytics-ids.ts`) because it ends up inside script URLs.
- `GET /public/:shopSlug` gains `analytics`: only configured public ids, `null` when none. `metaTestEventCode` and the token never appear.
- `order.attributionJson` (migration `20261005110000`, real `JSON NULL`, no backfill, NULL = unknown). `CreatePublicOrderDto.attribution` is a bare
  `@Allow()` object run through `sanitizeAttribution`, which never throws: attribution is untrusted marketing metadata and must not turn an order into a 400.
  It bounds lengths, strips control chars, strips query strings from referrer/landing path, lower-cases source/medium, and **drops click ids, fbp, fbc and
  the user agent unless `consent.marketing === true`** (so unconsented identifiers are never even stored).
- **`SELECT *` leak control.** Adding a column to `order` would have put it into every response that spreads an order row. Stripped (and covered by a leak
  test) at: `OrdersService.toResponse` (list/status/detail), `PublicService.createOrder` response (and the notification payload), and `trimOrderRow`
  (customers detail). The order detail alone gets `attribution`, a narrowed view (touches + consent, no click ids/fbp/fbc/UA). `lookupOrder`,
  `toOrderSummary` (customer account) and `loadOrderForInvoice` already build explicit shapes.
- PDPL: `anonymiseCustomer` now `JSON_REMOVE`s click ids / fbp / fbc / user agent from that customer's orders (UTM kept so the report does not move).
- **CAPI**: job type `send_conversion_event`, key `capi:purchase:<orderId>`, payload carries no secret and no PII (shop, order, event id, event time, value, currency).
  `ConversionEventsService.enqueuePurchase` queues only when the shop has pixel id **and** token **and** the order recorded marketing consent; it never throws.
  Triggers: `applyWebhookResult` paid branch (webhook + reconciliation), the duplicate-delivery branch too (at-least-once repair if the first delivery died
  between commit and enqueue; the key makes it still one job), and `createOrder` for orders needing no online payment. The handler re-checks tenant
  (`o.id = ? AND o.shopId = ?`), consent and credentials at send time, hashes email/phone with SHA-256 after Meta's normalisation, sends fbp/fbc/UA only if stored
  (i.e. consented), `value` in the order's own currency at its own precision (KWD = 3 dp), `event_id = order_<id>` shared with the browser event.
  `MetaCapiClient` is an injectable class (tests replace it; nothing in this PR ever calls graph.facebook.com). The token goes in the JSON body, and
  errors are built from HTTP status + Meta error code only, never the response body or the original error.
- Report: `GET /reports/attribution` (admin, viewer) with its own DTO (date range, outlet, `model=first|last`; an unsupported filter is a 400 instead of
  silently ignored) and ANL-11 export kind `attribution` (`ExportQueryDto`/`ExportContext` gained optional `dateFrom/dateTo/model`). One shared query
  (`reports/attribution-report.ts`). Excludes cancelled orders and online-payment orders that were never paid (an abandoned checkout is not a conversion).

### Storefront
- `lib/consent.ts` (single reader/writer of the choice + a change event), `CookieConsentBanner` now writes through it and, on decline, purges stored click ids.
- `lib/analytics.ts`: vocabulary (`page_view` added for SPA routing, plus the ten in the brief) mapped to GA4, Meta, TikTok, Snap and Google Ads; pure `buildProviderCalls`;
  `setAnalyticsConsent(true)` is the **only** place a script tag is added. `components/Analytics.tsx` is mounted in `ShopLayoutClient`, never in the theme-builder preview.
  Ids are re-validated (`lib/analytics-ids.ts`) before they reach a URL.
- `lib/attribution.ts`: first/last touch + referrer + landing path + click ids in first-party `localStorage` (90 days, per shop), payment-gateway referrers ignored,
  `buildOrderAttribution` sent with `createOrder` (click ids / `_fbp` / `_fbc` / UA only with consent).
- Events wired: `view_item` (PDP), `view_item_list` (collection), `select_item` (ProductCard), `add_to_cart`/`remove_from_cart` (cart context, the single chokepoint),
  `begin_checkout`, `add_payment_info`, `purchase`, `search`, `sign_up`. Purchase for pay-on-delivery fires at checkout; for online payment the data is parked in
  `sessionStorage` and sent (once, the stash is taken) on `/orders/<id>?paid=1`.
- CSP: provider hosts added to script/connect/img only.

### Admin
- Integrations > **Analytics & Pixels** tab (`SecretField` for the token, "Saved (hidden)" indicator, Remove token), client-side format hints mirroring the backend.
- Order detail **Source** card (renders "Not recorded" for NULL, never "direct").
- Reports > **Attribution** (group by source/medium/campaign, first/last touch, date + outlet, Export CSV).

## 4b. Security review
Ran the `security-review` skill. Its harness handed it an EMPTY diff (it inspected the main checkout, not this worktree), so I reviewed the branch diff by hand
against the same criteria: SQL (every dynamic fragment comes from a closed list or is a bound parameter; the JSON path is a closed pair), secrets (token write-only,
encrypted, never in responses, jobs, errors, logs or audit rows: each asserted by a test), tenant isolation (settings, report, export, handler all shop-scoped, cross-tenant e2e),
XSS (storefront ids are allow-list validated twice before reaching a script URL; admin renders attribution as React text), SSRF (fixed Meta host, numeric pixel id).
One finding at my own confidence of about 7, below the skill's bar of 8 but cheap to close, so I closed it rather than ship it: **CSV formula injection** in the new
attribution export, because source/medium/campaign are text any visitor can put in a URL (`utm_campaign==HYPERLINK(...)`) and a merchant opens the file in Excel.
`neutraliseFormula` now prefixes `'` on those three columns (test + injection proof above). The pre-existing exports have the same class of exposure (customer names)
and are not changed here. Nothing else surfaced above the bar.

## 5. Risks and gaps (please read)
1. **Deploy order matters: backend before storefront.** The storefront now sends `attribution` on `POST /public/:shop/orders`; the global ValidationPipe has
   `forbidNonWhitelisted`, so an OLD backend would answer 400 to every checkout. Migrate and deploy the backend first. (Admin against an old backend only 404s on new pages.)
2. **Provider scripts and event names are inferred, not observed.** I wrote the Meta / TikTok / Snap / gtag bootstraps from memory of their official snippets and
   could not load them (no network, and the rule is no real third-party calls). Event names (e.g. TikTok `CompletePayment`) and the CSP host lists are from memory of the
   providers' docs. A merchant should verify with each platform's test tool (Meta Test Events, TikTok Events Manager, GA4 DebugView, Snap's pixel helper) before relying on it.
3. **CSP is global, not per shop**, and `googletagmanager.com` can serve arbitrary tag containers, so it is a slightly wider landing zone for an XSS that already exists
   (the CSP already allows `'unsafe-inline'`, a documented reviewed tradeoff). Consent, not CSP, is the real gate.
4. **No withdraw-consent control.** After accepting, a visitor cannot re-open the banner (there is no footer "Cookie settings" link; both footer layouts would need touching).
   Declined/unanswered never loads anything, and `track()` stops if consent is later revoked, but already-loaded scripts cannot be unloaded without a reload. Follow-up.
5. **Meta match quality**: `client_ip_address` is not sent (not captured: it would be PII behind two proxies). `client_user_agent` is captured with consent. Meta documents both as
   expected for `website` events; events may be accepted with reduced match quality or a diagnostics warning. Unverified against the live API.
6. The browser `purchase` on an online-payment order fires on `?paid=1` (a return URL is not proof of payment, per `pay/success`). It only fires from a stash the same tab wrote
   at checkout, once. The server-side event (paid webhook / reconciliation) is the authoritative one, and Meta deduplicates on the shared `event_id`.
7. The server trusts the browser's claim of consent for that browser's own order (it cannot verify it). A forged claim can only cause an event about the forger's own order to be
   sent to the merchant's own Meta pixel. Click ids/fbp/UA are only stored when the claim is true.
8. Existing orders have `attributionJson` NULL and report as "(unknown)"; that is intentional (no backfill, "never recorded" is not "direct").

## 7. Deploy notes
- Two additive migrations (`20261005100000_shop_analytics`, `20261005110000_order_attribution`), no backfill, no data touched. `order` ADD COLUMN JSON NULL is instant-ish on MySQL 8 (metadata change); `shopanalytics` is a new table.
- No new env vars. `CREDENTIAL_ENCRYPTION_KEY` (already required by payments/WhatsApp) encrypts the token. No new dependency in any app.
- Order: migrate -> backend (registers the `send_conversion_event` handler on boot) -> storefront -> admin. A job queued by a new process and picked up by an old one fails with "no handler" and is retried with backoff, so a rolling restart is safe.
- Nothing is sent to any third party until a merchant enters ids AND a visitor accepts the banner; server-side Meta events additionally need a token and a consenting order.
