### Premise corrections
1. The audit says "a flags table + a resolver; migrate the existing booleans onto it". Built as the brief overrides it: column-backed adapter, no data migration, table only for overrides.
2. `externalDeliveryEnabled` is dead and not hidden (above).
3. The brief names the PK column `key`; it is `featureKey` because `KEY` is a MySQL reserved word. Same shape.
4. `PlatformAdminGuard` returns 404 on GET for non-platform callers, but a state-changing request from a non-platform caller is answered **403** by the platform CSRF middleware before the guard runs. Pre-existing behaviour for every platform route (suspend etc.), not changed; tests accept 403 or 404 and assert nothing was written.

## 2. What was built

- `backend/src/features/feature-keys.ts`: typed registry. `source: 'column' | 'table'`, `default`, `description`. Ten column-backed keys. No table-only key is registered (no consumer yet, so none would be real); the table-backed path is covered by the pure `resolveFlag` unit tests.
- `backend/src/features/features.service.ts`: `isEnabled(shopId, key, conn?)`, `getFlags(shopId, conn?)` (2 queries), `describe`, `enabledShopIds(key)` (resolves the same precedence in SQL for the cron sweeps), `setOverride`/`clearOverride`, `planDefault()` stub, pure `resolveFlag`. Precedence: override row, then shop column (column-backed only), then `planDefault` (always `undefined`), then registry default. A shop id that does not exist resolves every flag to `false`, never to a default.
- Migration `20261004100000_shop_feature_override`: `shopfeatureoverride(shopId, featureKey, enabled, note, updatedBy, updatedAt)`, PK `(shopId, featureKey)`, FK to `shop` (cascade) and `platformadmin` (set null). No backfill, no existing column touched. `db/types.ts` updated by hand.
- Platform endpoints (`@Public()` + `PlatformAdminGuard` via the existing controller): `GET /platform-admin/shops/:shopId/features`, `PUT .../features/:key` `{enabled, note?}`, `DELETE .../features/:key`. Override write and the `platformauditlogentry` row (`shop.feature_override.set` / `.clear`) are ONE transaction (`PlatformAuditLogService.log` gained an optional `conn`), so a failed audit insert rolls the override back and fails the request. Clearing an override that is not set changes nothing and logs nothing.
- Admin: a "Feature flags" section on `admin/app/platform/shops/[shopId]/page.tsx` (the real route), plus 3 functions and a type in `admin/lib/platform-api.ts`.
- `tools/check-feature-flags.js` + a new step in CI's `guardrails` job (job name untouched).

## 3. Security notes (verified by test unless marked)

- A shop admin has no write path: the table is written only by `FeaturesService.setOverride`, called only from `PlatformAdminService`. `PATCH /shop` with `featureOverrides` or `enabled` is rejected 400 by `forbidNonWhitelisted` (test).
- Merchant bearer token against the new GET: 404; against PUT/DELETE: refused (403 from CSRF, or 404), nothing written (test).
- Cross-tenant: an override on shop A leaves shop B's `getFlags`, public payload and `enabledShopIds` membership unchanged (test, three call sites). Every read takes the shop id from the authenticated user or the resolved slug; no client-supplied id is used for flag reads. The write endpoints take `shopId` from the URL, which is correct for a platform admin; it 404s for a non-existent shop and for an unknown key (including `constructor`).
- Public storefront path: `getShop` resolves the shop from the slug and calls `getFlags(shop.id)` for that shop only, and returns only the three resolved booleans. Override rows, notes and `updatedBy` never leave the platform endpoints. One-shop-per-request, so no cross-shop enumeration. Cost: two extra indexed queries on the public shop fetch (inferred acceptable; not benchmarked).
- Effective value is shown to merchants only through the public payload and the Slider status; `GET /shop` still echoes the merchant's own column. A merchant can therefore see a toggle "on" that a platform override has forced off. Not changed (inferred to be acceptable; flagged).

## 5. Risks / things the coordinator should know

- `LowStockDigestService.sendForShop`'s CAS claim no longer has `AND notifyLowStockDigest = true` in its `WHERE`: a column predicate there would veto an override that turns the digest ON. The flag is checked just before; the only change is a millisecond race if a merchant turns the toggle off between the check and the claim. `lastSentAt` still makes it once-per-day.
- `enabledShopIds` resolves the plan layer by omission (`planDefault` is always undefined). When PLT-1 lands, `planDefault` and that SQL must change together; `features.e2e-spec` asserts the two agree for every key, which will fail if they drift.
- `consumeForOrderItems` reads flags on the order's own connection, so no second pool connection is taken inside the transaction.
- Deploy: one additive migration, backend + admin rebuild. With no override rows nothing changes behaviour. Rollback: `DROP TABLE shopfeatureoverride` (nothing else references it); the code needs the table, so roll the code back first.
