# S2: INV-3 scan receive + INV-5 reorder points (money + stock). Adversarial checklist for /security-review

Branch `feat/po-scan-receive-reorder`. Migration `20261025100000_reorder_points` (two nullable INT columns on `outletingredientstock`).

## Design decisions (with evidence)

**INV-3: the scan only RESOLVES, it never writes.** `POST /purchase-orders/:id/scan` (`PurchaseOrdersService.resolveScan`) maps a barcode/SKU to one open line and checks the caller's draft tally; the tally lives in the browser and is committed through the existing `POST /purchase-orders/:id/receive`. There is no second ledger implementation: the `FOR UPDATE` lock order, the per-line cap restated in the UPDATE's WHERE, the status CAS, the `(poId, idempotencyKey)` unique index and `applyStockReceipt` are untouched. The only change in `receive()` is none. `receive()` was not edited.
- Match rule (one SQL, all joins carry shopId/productId): `l.supplierSku = ?` OR (variantId NULL and `product.barcode|sku = ?`) OR (variantId set and `productvariant.barcode|sku = ?`). Ingredients have no barcode/SKU column, so an ingredient-only line matches on the PO line's `supplierSku` (premise correction: the scan module itself is OCR invoice scanning, it has no barcode lookup; barcodes live on product/productvariant).
- 0 matches: 409 `no_matching_line`. >1: 409 `ambiguous_code` (never guessed). Fully received: 409 `line_fully_received`. tally + qty > outstanding: 409 `exceeds_ordered`. PO not sent/partially_received: 409.
- Permission `purchase_orders.receive` asserted against the FETCHED PO's outlet (`getVisible` pins branch users, 404 for another outlet), roles admin/branch only.

**INV-5: where the reorder point lives.** `outletingredientstock.reorderPoint` / `reorderQuantity` (per outlet, ingredient is shop-wide; PK already `[outletId, ingredientId]`). Distinct from the existing `lowStockThreshold`: that column is the merchant's low-stock ALERT (digest email); reusing it would silently start PO suggestions for every merchant who ever set an alert, and a quantity column is needed anyway. Evidence: `low-stock-digest.service.ts:178`, `product-stock.service.ts` `setLowStockThreshold`.
- NULL = unknown. No point means no suggestion (`baseOrderQuantity` returns `no_reorder_point`); 0 is a real point; blank clears to NULL (the DTO makes the key required, `null` clears, so the whitelist pipe cannot turn "clear" into "unchanged").
- Rule (s, Q) on the inventory position: `position = stock + outstanding on open POs (draft, sent, partially_received) at that outlet`; reorder when `position <= point`; qty = `Q * ceil((point + 1 - position) / Q)`, raised to the supplier item `minOrderQty`, capped at 1,000,000. supplieritem has no pack size column, so only min order qty exists.
- Supplier choice (stated in the UI): one currency among a candidate's priced supplier items -> cheapest; several currencies -> prices are not comparable (no rate applied) so shortest lead time; ties lead time then supplier id. Only ACTIVE suppliers; an item is priced only with BOTH cost and its own currency (the PO currency comes from the item, never defaulted). One supplier priced in two currencies yields two suggestions. Items with no supplier / unpriced item / no reorder quantity are listed separately.
- Money: `lineAmount` + `sumAmounts` (integer minor units, KWD 3 dp), no toFixed.
- **Idempotency rule for "create draft POs"**: the action runs in one transaction whose FIRST statement is `SELECT ... FROM outlet WHERE id AND shopId FOR UPDATE`, then recomputes the suggestions inside that lock with drafts counted as on order. A repeat or concurrent click serialises behind the lock, sees the first click's drafts, finds nothing left to order, and creates none. Drafts are written by `PurchaseOrdersService.insertPurchaseOrder(conn, ...)`, extracted from `create()` (same code path as the admin form), never sent.
- Read permissions: admin + branch (pinned; `purchase_orders.view` when an outlet is resolved). Setting a point: admin only, audit-logged (`reorder_point.set`, before/after). Creating drafts: `purchase_orders.manage` at the outlet, audit-logged per PO (`purchase_order.created`, source `reorder_suggestion`).

## Adversarial checklist (what to attack)

1. **Tenant**: every query on `outletingredientstock` (no shopId column) joins `ingredient.shopId = ?` AND `outlet.shopId = ?`; `setPoint` calls `assertOutletInShop` and `resolveShadowStockTarget` (shop-checks ingredient/product/variant). `supplieritem` and `supplier` are shop-scoped in the suggestion query. Try: outlet id of another shop in `PUT /reorder/points`, `GET /reorder/*?outletId=`, `POST draft-pos`; another shop's ingredient id; another shop's supplierId filter; a barcode string identical in two shops.
2. **Cross-outlet / branch**: `resolveOutletFilter` pins branch users (their `outletId` wins over a spoofed one); scan checked against the fetched PO; admin all-outlets reads skip the permission by design (unresolved outlet) but still group per outlet.
3. **Money/stock**: scan can never over-receive (resolve check, then receive's check + the UPDATE's restated cap); race of N receives on the last unit -> exactly one wins; same idempotency key racing itself posts once; conservation `SUM(stockmovement.delta) = outletingredientstock` after mixed scan and modal receives; `PURCHASE_RECEIPT` movement only. A reorder-point write creates the stock row at quantity 0 with NO movement (conserved at 0), same as `setLowStockThreshold`.
4. **Idempotency / double apply**: draft creation under the outlet lock. The lock only serialises callers that use it; a manual PO created concurrently by hand is not blocked (it shows up as on-order on the next click). Lock order: outlet row, then `purchaseordercounter` row, then PO rows; `receive` takes the PO row first and never the outlet row, so no inversion.
5. **No nested pool use**: `createDrafts` passes `conn` into `computeSuggestions` via an `Exec` closure; `insertPurchaseOrder(conn, ...)` touches only `conn`. `tools/check-nested-pool.js` passes (see below).
6. **Currency**: no default anywhere. A priced item needs cost AND currency; `insertPurchaseOrder` receives the item currency; groups never mix currencies; `belowMinimumOrderAmount` is informational and compared only when the supplier's currency equals the group's.
7. **Validation**: reorderPoint 0..1,000,000 or null, reorderQuantity 1..1,000,000 or null, omitted = 400, unknown fields 400 (forbidNonWhitelisted); scan `code` trimmed, 1..191, `pending` max 200 entries.

## Known limits / not built (stated, not hidden)
- The draft tally is client-side; a closed tab loses it (nothing was posted, so nothing is wrong). A server-side draft receipt was not built because it would need a second lifecycle for the same receipt.
- Variant lines match on the variant's SKU/barcode only; a product-level code never matches a variant line.
- No pack-size column exists, so rounding is to `minOrderQty` only.
- The `supplier`/`supplieritem` `shopId` scoping in `computeSuggestions` is defence in depth: a cross-shop `supplieritem` cannot be created through the API (PUT item validates both ids), so no test can distinguish it; it is NOT injection-proven.
- Camera scanning is not built (no dependency added): a hardware/keyboard-wedge scanner or typed code, Enter submits.
