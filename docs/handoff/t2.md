# T2 / SHP-5: dispatch to a merchant's own drivers (handoff, coordinator deletes before merge)

Branch `feat/driver-dispatch`, migration `20261030100000_driver_dispatch` (additive, replayed from empty).
Commits: a drivers+runs backend, b magic-link API, c proof+cash, d admin UI, e driver web view, f run sheet, plus a small follow-up.

## What exists today (evidence, before building)
- Order timeline = `auditlog` rows (`order.status_changed`), read by `OrdersService.getHistory` (orders.service.ts) through `AuditLogService.listForEntity`. `auditlog.actorUserId` was NOT NULL FK to `user` and every read was an inner JOIN to `user`. A driver is not a user, so: `actorUserId` nullable + `actorLabel` ("driver Omar"), reads LEFT JOIN + COALESCE (migration, audit-log.service.ts).
- COD gate: `OrdersService.updateStatus` refuses `delivered` for COD until `cashCollectedAt` is set; `collectCash` stamps `cashCollectedBy` (INT FK to `user`). Slider's delivered webhook calls it under a synthesized admin ctx. For a driver: new nullable `order.cashCollectedByDriverId` (FK `driver`), `collectCash` reads `ctx.driver`; `cashCollectedByName` becomes "Driver <name>". No staff user is faked. `userId` of a driver ctx is 0 (no such row, so any stray FK use fails loudly).
- Order status machine is linear (`constants.ts`), no backwards move. A failed delivery therefore leaves the order `out_for_delivery` (re-runnable), writes `order.delivery_failed` on the timeline (shown as `delivery_failed` in history), touches no stock.
- `order.orderType='delivery'` is the delivery type; admin-created orders are pickup with no paymentMethod (tests flip by SQL).
- Storage module is public by design (local `/uploads`, S3 path-style); no read API. Proof photos therefore are CAPABILITY URLs (256-bit random key), returned to staff only. See "Known limits".
- Premise note: the brief said "outlets nullable or required per evidence": required (orders, stock, POs, branch pinning are all outlet-required).

## Design decisions
- Link secret: opaque 256-bit random, only SHA-256 stored (`deliveryrunlink.tokenHash`). No JWT, no env secret (nothing to add to env-validation). Revocable by row; 12h expiry in SQL (`NOW(3)`); one live link per run (issuing revokes the previous one); dies on run cancel/complete, driver deactivation, shop suspension.
- Web app location: admin `/driver/<token>` (not storefront). Storefront `proxy.ts` prepends the tenant slug on any real host (so a route outside `[shop]` 404s on a subdomain) and the dev path shape differs from prod; admin has no tenancy rewrite, no shop slug in the link, no cookie banner. `RequireAuth`/`AppChrome` bypass `/driver/`; `next.config.ts` sets `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Robots-Tag` for it. API calls use `credentials: "omit"` + `X-Driver-Token` (no cookie, no CSRF surface).
- Proof: per run `proofRequirement` = `photo_or_otp` (default) | `photo` | `otp` | `none`. Customer code: 6 digits, salted SHA-256, 15 min, 5 attempts per code (counted in SQL BEFORE the compare), max 3 sends per stop, 30s apart, constant-time compare, sent through the existing email job / customer WhatsApp provider (no stub fallback, so the code never reaches a log).
- Cash: exact decimal strings -> integer minor units in the ORDER's currency (`drivers/cash.ts`, BigInt, no floats); mismatch recorded (`cashDiscrepancy`, audit `delivery.cash_discrepancy`) and never blocks delivery nor is silently accepted; `collectCash` is the single writer of the order fields.
- Delivered/failed use compare-and-swap on the stop, then the same `OrdersService.collectCash` + `updateStatus` the kanban uses. Retry/double tap: the stop is already delivered, the second call only "finishes" the order (repairs a crash between the two steps).
- One active run per order: `deliveryrunstop.activeOrderId` UNIQUE (NULL when not active). Atomic under races (test: 4 parallel creates, exactly 1 wins).

## Adversarial checklist for the /security-review (each has a test; "inj" = injection-proven)
Driver-token surface (`driver-link`, `driver-proof-cash` e2e):
1. Forged / flipped / truncated / oversized / path-traversal token -> identical 404 body to a missing header. (inj: removing `expiresAt` check fails)
2. Expired, revoked, run cancelled/completed, driver deactivated (even if revokedAt were NULL), shop suspended -> same 404. (inj: dropping the `d.active` join fails)
3. Token of run A cannot read or act on run B's stop (same shop) or another shop's stop: deliver/fail/code/photo all 404, stops untouched. (inj: dropping `runId` scope fails)
4. No client-supplied shop/run/order id is accepted anywhere in `/driver-app` (extra query params ignored, test).
5. A staff bearer is not a driver credential and a driver token is no staff credential (401/404 both ways).
6. OTP: no code sent -> unusable; 5 wrong guesses burn it even for the right code; 12 parallel guesses -> exactly 5 counted; expiry; resend cooldown + 3-send cap; spent code hash cleared; code never in any response. (inj: dropping the attempt cap fails)
7. Idempotency: parallel triple deliver -> exactly one non-idempotent, one `delivered` timeline row; retry after crash repairs the order. (inj: dropping the CAS status guard fails)
8. Photo: JPEG/PNG/WebP only by magic bytes (GIF, SVG, text-with-jpg-name, magic-bytes-but-undecodable rejected), 5MB cap, 40MP decode cap, re-encoded (EXIF/GPS dropped), key `delivery-proof/<shopId>/<64 hex>.jpg`, driver view never contains the URL.
9. Cash: required for COD, rejected for non-COD, 3-decimal for AED rejected, KWD 10.505 exact, 10.5 vs 10.505 flagged, staff-collected cash not overwritten. (inj: float math fails `cash.spec`)
10. Per-link ceiling (120 reads / 40 writes per minute) in addition to per-IP Throttler (skipped under Jest by design).
Staff surface (`driver-runs` e2e):
11. Every drivers/runs/stops/link/sheet/cash-reconciliation endpoint 404s cross-tenant; list endpoints exclude other shops. (inj: dropping shopId in `loadRun` fails)
12. Branch pinned to its outlet (body outletId ignored, other outlet = 404, list filtered); order_manager/viewer 403; restrict-only branch role without `deliveries.*` is 403 (list too).
13. Orders from another shop/outlet, pickup, wrong status, external courier handoff -> refused with indistinguishable reasons; failed create leaves no run.
14. One-active-run race. (inj: dropping the UNIQUE index fails)
15. Timeline attribution to the driver with `actorUserId` NULL and no token anywhere in auditlog. (inj: removing the `ctx.driver` branch fails: the FK insert is refused and the delivery does not complete)
16. Run sheet: every dynamic value escaped incl. quotes (unit test with hostile names), staff-only, tenant scoped.
Things the reviewer should look at hardest:
- `OrdersService.collectCash`/`updateStatus` now run under a synthetic `role: 'admin'`, `userId: 0` ctx carrying `driver`. It is built only in `DriverAppService.driverCtx` from a verified link row.
- `auditlog.actorUserId` is now nullable (shared table). Other readers: `reports.service.ts` prep-time (no user join), `auth.service.ts` countWhere (unaffected).
- The WhatsApp link send puts the secret URL in a `job.payload` (queue retries need it); it expires in 12h and an admin could mint one anyway.

## Known limits / not built (owner decisions)
- Proof photo is a capability URL on the public storage (not a private bucket / proxied read). Moving to private needs a `read()` on `StorageProvider` (local + S3) and a staff proxy route.
- Orders can only be added to a DRAFT run (not once dispatched). Reorder/remove work while live.
- Per-shop default for the proof requirement is not built (per run only).
- Per-link limiter is in-memory per process like the Throttler.
- After the last stop closes the run the link is revoked; a double tap on that last stop gets a 404 (the app shows "run finished").
- Cancelled order on a live run: stop is closed `order_cancelled` the next time the driver app refreshes (not instantly for staff).
- Customer tracking page shows order status only (it follows the state machine); the failed attempt is a timeline entry, not a customer-facing status.
- Slider and runs are mutually exclusive per order (an order with a non-cancelled `externaldelivery` cannot join a run).
