# p4-small-items: fix/product-delete-with-variants

ROOT CAUSE (VERIFIED by raw SQL in a rolled-back transaction and by e2e repro): `DELETE FROM product` on a product with options+variants fails 1452 because of FK cascade ordering, not a stray insert. product -> productoption (CASCADE, 'ProductOption_productId_fkey') -> productoptionvalue (CASCADE) -> productvariant.optionValue1/2/3Id (ON DELETE SET NULL). That SET NULL is an UPDATE of a productvariant row whose parent product is already mid-delete, so InnoDB re-checks `ProductVariant_productId_fkey` and raises 1452 (error text names productvariant/ProductVariant_productId_fkey). `DELETE FROM productvariant WHERE productId=?` first, then the product, succeeds in the same raw SQL. A product with options but no variants, or with no options, never hit it.
FK graph (information_schema, VERIFIED): product children CASCADE: discountproduct, ingredient.shadowProductId, notifysubscription, productattribute/collection/faq/image/ingredient/option/tag/variant, stockmovement, templateproduct; SET NULL: biolink, menucolumnlink; RESTRICT: orderitem.productId, draftorderitem.productId. productvariant children: CASCADE ingredient.shadowVariantId, notifysubscription, productingredient, stockmovement; SET NULL draftorderitem.variantId, orderitem.variantId. ingredient children all CASCADE (outletingredientstock, productingredient, stockmovement).
FIX: `product-catalog.service.ts` `remove()` deletes `productvariant` for the product inside the existing transaction before `DELETE FROM product` (same order the options-wipe path at updateOptions already used). `bulkRemove` goes through `remove`, so it is fixed too. Order history stays a 409 ("has order history, mark it Unavailable instead") via the pre-existing 1451 handler in handleDbError (orderitem/draftorderitem RESTRICT); the transaction rolls back so the variants (and metafield values) are not lost. shopId scoping, audit log and admin-only role unchanged (findOne(ctx,id) is still the tenant/permission gate before the transaction).
TESTS: backend/test/product-delete.e2e-spec.ts (4): success with 2 options/4 variants/image/stock/collection + orphan sweep over 10 tables + audit row; bulk-delete; 409 with order history and nothing lost; cross-tenant 404 (single and bulk).
INJECTION-PROOF (VERIFIED): reverting remove() makes the success and bulk tests fail with the 1452 error; history/tenant tests pass either way (that behaviour already existed).
NOTE (VERIFIED, existing, not touched): `PATCH /products/stock/bulk-adjust` writes no stockmovement (known F4), so the orphan sweep uses outletingredientstock, not stockmovement, as the stock evidence.
INFERRED/not tested: draftorderitem-referenced product also gives the 409 text "order history" (same RESTRICT/1451), message slightly loose for draft orders.
