### Group-level graph (acyclic, no `forwardRef`)

```
ProductsService (facade) --> Catalog, Stock, Import, Bom, OrderItems
Catalog  --> Read, Bom
Import   --> Stock, Bom
Read, Bom, Stock, OrderItems --> (leaves: DatabaseService + Branch/Notify/Discount collaborators only)
```

Shared private helpers: none had to be duplicated. The only helpers called across groups are the 15 listed below, and they became public on their own service (`private` keyword dropped, body untouched):
`assertIngredientLinksValid`, `provisionShadowForProduct`, `provisionShadowForVariant`, `syncShadowMeta`, `deleteShadowForProduct`, `deleteShadowsForVariants` (Bom); `resolveShadowStockTarget` (Stock); `loadProductsWithRelations`, `loadVariantsWithRelations`, `loadIngredientLinks`, `rowToIngredientLink`, `toResponse`, `toVariantResponse`, `getUnitsSoldByProduct`, `attachOutletStockBreakdown` (Read).
`handleDbError` and `dedupeCaseInsensitive` are only used by catalog methods, so they live there. `resolveEffectiveRecipeRows` is unused dead code on main (only mentioned in a comment); moved verbatim with the order-items group rather than deleted (pure refactor).

Deviation from the brief's five groups: a sixth leaf, `ProductReadService`, holds the read model (batch loaders + `toResponse`), because catalog (find/create/update/variant) is its main consumer but it is also a self-contained, DB-only layer; keeping it inside catalog would have left a ~2,300-line catalog file.

## 3. What changed

- New: `product-catalog.service.ts` (1,495 lines), `product-read.service.ts` (728), `product-stock.service.ts` (589), `product-import.service.ts` (674), `product-order-items.service.ts` (479), `product-bom.service.ts` (222).
- `products.service.ts`: 4,088 -> 146 lines, `@deprecated` facade; each method is `name(...args: Parameters<X['name']>) { return this.x.name(...args); }`.
- `products.module.ts`: six extra providers (not exported; the facade stays the export).
- `tools/check-outlet-scoping.js`: five `ALLOWLIST` entries retargeted from `products/products.service.ts:<m>` to the new file that now holds `<m>` (consumeForOrderItems, applyImportStock, loadProductsWithRelations, loadVariantsWithRelations, loadIngredientLinks). Same reasons, no new exemption.
- Method bodies are moved byte-for-byte; the only edits inside bodies are (a) `this.x(` -> `this.<collab>.x(` for cross-group calls, (b) `private` removed from the 15 cross-called helpers, (c) `ReturnType<ProductsService['toResponse']>` -> `ReturnType<ProductReadService['toResponse']>`. Verified mechanically: each of the 54 original method blocks, whitespace- and trailing-comma-normalised and after applying (a)-(c), is a substring of its new file (54/54). Files are NOT run through prettier on purpose: `origin/main`'s own `products.service.ts` already fails `prettier --check`, and reformatting would bury the move.

## 4. Proof (verified, not argued)

**Before/after deep-equal.** Throwaway e2e capture (not committed; lives outside the repo) scripts one fixture shop and records 134 HTTP responses: admin list (all / outlet A / outlet B), admin detail of 5 products incl. variants + recipe + gift card, public list (+ outlet, brand, collection filters), public product by id and slug, related, public search/brands, stock movements (filters, pagination, types), stock adjust/bulk/transfer/threshold for product, variant and ingredient, options/variant CRUD, update/duplicate/availability/bulk status/price/delete, CSV import preview + confirm (create, update, variant rows, rejects, idempotent re-run, bad outlet), admin + storefront orders (recipe consumption on confirm, restock on cancel, gift card amounts, missing-variant rejection), plus 4xx error bodies.
Each run uses a **freshly dropped and re-migrated scratch DB** (`rq_w3_scratch`), so auto-increment ids are identical and are **not** normalised. The only normalisation: the run id inside strings -> `RUN`; ISO timestamps -> `<ts>`; 10-hex `trackingToken` -> `<tracking>`; `-COPY-XXXXXX` duplicate-sku suffix; `tags` arrays sorted (producttag read has no ORDER BY); stock-movement `data` rows sorted by id (list orders by a 1s-resolution `createdAt`, ties unordered).
- main vs main (determinism check): 134/134 records identical after normalisation.
- main vs refactor: **134/134 identical, 0 diffs.**
- Harness sensitivity (injection): changing `Math.floor` to `Math.ceil` in `ProductReadService.computeIngredientAvailability` -> 2 records differ (`detail-p3-after-confirm`, `detail-p3-after-cancel`); reverted.

**Suites on the refactor** (jest `--maxWorkers=2`, one invocation at a time): unit 74 suites / 759 tests pass; full e2e 88 suites / 1,012 tests pass; `tsc --noEmit` clean.

**Guardrails**: `check-outlet-scoping` (after the allowlist retarget), `check-no-console-log`, `check-no-emirate-list`, `check-page-width`, `check-region-validation`, `check-storefront-url` pass. `check-form-width` not run (pre-existing failure). **Lint**: `node tools/check-lint-baseline.js backend` -> baseline 260, current 260, delta +0 (same on pristine main); admin/storefront untouched.

## 6. Risks / notes

- Facade `Parameters<>` delegation means a signature change in a split service silently flows to the facade; that is the intent (no drift) but it also means a caller-visible change is now one edit instead of two.
- Anything outside this repo that greps for `products.service.ts` symbols will not find the implementations there any more.
- `ProductCatalogService` is still large (1,495 lines: `update` 312, `updateOptions` 248, `duplicate`, `create`); splitting variants/options out is a possible follow-up, deliberately not done here to keep the diff mechanical.
- Deploy: no migration, no env change; a normal backend rebuild + pm2 restart. No behaviour change expected.
