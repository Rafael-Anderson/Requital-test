# W3 handoff: store credit and gift card on edited orders, amount due everywhere, Stripe findings

Branch `fix/store-credit-amount-due`. Migration `20261103100000_store_credit_edit_release`.

## The rule (for CLAUDE.md, coordinator)

An order holds `giftCardAmount + storeCreditAmount` of its total as already paid. When an edit changes `order.total` (`OrdersService.updateItems`, `updateDeliveryFee`; no other path writes `total`):

- total >= gift + credit: nothing changes. A larger total never spends more credit or gift card; the difference is simply still to pay.
- total < gift + credit: the excess goes back, **store credit first**, then the gift card for the remainder (credit comes back exactly as a ledger entry; a card may have been disabled or expired meanwhile). `order.storeCreditAmount` / `giftCardAmount` shrink to what is still held.
- Integer minor units of the order's own currency; one transaction with the edit; idempotent (a repeated edit finds no excess).
- Ledger: new entry type `spend_release`, `storecreditentry.editSeq` (INT NOT NULL DEFAULT 0, 1-based edit number for a release, 0 for all other entries). Unique key is now `(orderId, entryType, editSeq)` (created before the old `(orderId, entryType)` key is dropped, because the orderId FK needs an index). `spend`/`spend_reversal` keep their one-per-order guarantee (their editSeq is always 0).
- Cancel reverses what is held NOW: `-(spend + SUM(spend_release))`, nothing written when that is 0. Returns already read the (updated) `storeCreditAmount`/`giftCardAmount` columns, so they split what is still held.
- Gift card: `GiftCardsService.releaseForOrderEdit` = `creditRefund` + `giftcardredemption.amountUsed` shrinks. Gift cards are still NOT restored on cancel (known gap 5, unchanged).
- Lock order: **order row -> customer row -> stock -> ledger rows -> gift card row**. Customer-first deadlocked against cancel in the concurrency test (1213): cancel holds the order row and its ledger insert takes a shared lock on the customer row through the FK. Checkout locks the customer first but only inserts a NEW order row, so no cycle. Customer merge (customers then orders) can still deadlock with cancel/return/edit; MySQL fails one side, a retry succeeds (pre-existing for cancel/return).
- `updateDeliveryFee` now locks the order row and 409s if its status moved since the read (it had no lock).

## Amount due

`common/amount-due.ts`: `amountDueMinor` / `amountDueDecimal` (exact decimal parsing via `drivers/cash`, no float multiply, order's own currency, never below zero). `payments.service.ts` `amountStillDue` is now a thin wrapper. Readers switched from `order.total`: payment-link session and /pay summary (already, S4), webhook `paymenttransaction.amount`, packing slip CASH TO COLLECT and the invoice "Cash Due" box (INVOICE keeps its frozen total, minus the tenders in its snapshot), driver app cod amount and `codExpected`, staff run detail (`order.amountDue`, `cash.pending`), printable run sheet. Packing slip with due 0 prints "PAID - no collection required".
Left on `order.total` on purpose: `readyOrders` list (display), the delivery-code notification, `OrdersService.collectCash`/`updateStatus` (they compare no amounts: premise correction).
`invoices.service.ts` printed `shop.currency` (live) on a document whose amounts are the order's; it now prints `invoice.currency` (frozen at issue) and the live read uses `order.currency`.

## Stripe findings (docs/investigations/pay-1-wallet-buttons.md section 6)

- VERIFIED and FIXED: payment-link path charged `order.shopCurrency` (live shop currency); now `order.currency`. Test in `kwd-end-to-end`.
- VERIFIED and FIXED: `paymenttransaction.amount` was `order.total`; now the amount due.
- Premise correction: the doc's `Number(order.total)` in `getCheckoutSession` was already `amountStillDue` since S4.
- Other providers (Tabby, Tamara, PayPal) use `toMajorUnitString`; none hard-code 100. Stripe uses `toMinorUnits` for session and refund. No `amount_total` comparison exists anywhere (the webhook trusts the signed event), so there is nothing to fix there.
- **NOT DONE, OWNER DECISION (design change): Stripe's three-decimal rule (R1).** INFERRED from Stripe's docs, not verified (no live Stripe): for BHD, KWD, OMR the API amount must be a multiple of 10 minor units (last digit 0). Our total 33.091 KWD = 33091 minor units would be rejected. Options: (a) round the Stripe charge to the nearest 10 (charge differs from the stored total by up to 0.005; then refunds, the paid-in-full decision and the stored `paymenttransaction.amount` disagree with the charge); (b) quantise KWD/BHD/OMR order totals to 0.010 at order time (a money-layer policy change touching `roundMoney`); (c) refuse Stripe for those currencies. Needs a Stripe test-mode check first. The e2e still pins 33091 (the existing behaviour). Until decided a KWD/BHD/OMR Stripe checkout whose total has a non-zero third decimal probably fails at Stripe.

## Known, not fixed

- Editing an order UP after it is `paid` (credit or gateway) leaves `paymentStatus = 'paid'` while more is due. Pre-existing.
- Editing DOWN a gateway-paid order overpays the gateway portion; no provider refund is triggered by an edit.
- The webhook amount is the CURRENT due, not what the session was created with, if the order was edited between.
