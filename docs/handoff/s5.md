# S5: release a discount redemption on cancel / full refund

No migration. Branch fix/release-discount-redemption-on-cancel.

## What changed
- `backend/src/discounts/release-redemption.ts`: `releaseDiscountRedemption(conn, shopId, orderId)`, a plain function on the caller's connection.
  Finds the order's `discountredemption` row (joined to `discount.shopId` and `order.shopId`), locks the discount row (same lock order as `redeem()`: discount, then redemption), DELETEs the redemption row, and only if that DELETE's `affectedRows === 1` runs `UPDATE discount SET timesUsed = GREATEST(timesUsed - 1, 0) ... WHERE id AND shopId`. The delete is the idempotency guard (orderId is UNIQUE), never a read-then-write.
- `OrdersService.cancel`: called in BOTH successful CAS branches, inside the transaction, next to `markInvoicesSuperseded`.
- `ReturnsService.create`: called in the branch that sets `paymentStatus = 'refunded'` (cumulative refunds reach the order total), same transaction. A partial return never reaches it.
- `OrdersService.updateStatus`: `status = 'cancelled'` now delegates to `cancel()`.

## Paths that move an order to cancelled (investigated)
| Path | Goes through | Released |
|---|---|---|
| `POST /orders/:id/cancel` (staff) | `cancel()` | yes |
| `PATCH /orders/:id/status {status:'cancelled'}` and `PATCH /orders/bulk-status` | `updateStatus()` | yes, NOW (see correction) |
| Tabby / Tamara `advanceOrderStatus: 'cancelled'` (BNPL expiry/rejection webhook) | `PaymentsService.applyAdvanceOrderStatus` -> `cancel()` | yes |
| Draft order cancel (INVOICE_SENT) | `DraftOrdersService.cancel` -> `cancel()` | yes |
| Slider "cancelled" webhook / cancel | only touches `externaldelivery.status`, not the order | n/a |
| Payment reconciliation sweep | never changes order status (only marks `settledAt`) | n/a |
| Customer-initiated cancel | does not exist | n/a |
| Full refund (return) | `ReturnsService.create` | yes (on `paymentStatus -> refunded`) |

No path moves an order OUT of cancelled (`isValidStatusTransition` returns false from cancelled/delivered; `cancel()` 400s on both; CAS WHERE clauses name the source statuses). A cancelled order cannot re-consume.

## Premise correction found on the way
`PATCH /orders/:id/status` with `cancelled` was accepted by the DTO and by `isValidStatusTransition`, and ran only a bare status CAS: no stock restock, no invoice-superseded marker, no audit/affiliate sync. It is now delegated to `cancel()`, which fixes the stock leak too (test: stock +1). Nothing in admin or the existing tests used it.

## Semantics worth knowing (decisions, not bugs)
- "Full refund" means `paymentStatus` flips to refunded, i.e. cumulative refunds >= order total. A default refund excludes the delivery fee, so returning every item of an order that has a delivery fee does NOT by itself flip it (existing behaviour) and does not release. A manual `refundAmount` covering the total does.
- Auto discounts write no `discountredemption` row and never touch `timesUsed`: nothing to release. Gift cards are separate and untouched (test asserts the card row is unchanged by the release).
- The order row keeps `discountId/discountCode/discountAmount` (the record of what was charged); only the use-counting rows are released.
- The phone-spelling evasion of the per-customer limit (CLAUDE.md open follow-up) matters slightly more now that a cancel frees a use; unchanged by this PR.
- Unpaid-but-not-cancelled orders still count, as before.

## Production notes
No env, no migration. Existing already-cancelled orders keep their redemption (nothing is backfilled; releasing them would change campaign counts retroactively, an owner decision).

## Review follow-up (A1, A2c)
- A1 lock order: checkout locks stock rows, inserts the order, then locks the discount row (`redeem`). `cancel()` now takes order, stock, discount in that same order: `releaseDiscountRedemption` is the LAST call in both CAS branches, after `adjustStockForOrder` and `markInvoicesSuperseded`. A returns release is also after its restock. Regression: a call-order test spies on `adjustStockForOrder` and the release in both branches and asserts `['stock','release']` (not a true two-connection deadlock reproduction; the interleaving is not deterministic without a lock-wait harness). Injection: release moved before the restock in either branch fails it. The atomicity test now lets the real release run and THEN throws, so it proves the release is coupled to the cancel transaction (a separate-transaction release fails it).
- A2c: the return branch releases only if `totalMinor > 0` (a total-0, 100% discount order satisfies `alreadyMinor + refundMinor >= totalMinor` on any return). `paymentStatus = 'refunded'` still flips for it, as before; test + injection included.
