## (a) Storefront fonts: next/font/google -> next/font/local

Done. `storefront/app/layout.tsx` now uses `next/font/local` for the same five families, same CSS
variables (`--font-inter`, `--font-poppins`, `--font-playfair-display`, `--font-roboto`,
`--font-geist-mono`), `display: "swap"` (the old default).

- Font files: the exact woff2 files `next/font/google` itself fetches (the `latin` unicode-range block
  of the Google Fonts CSS2 response for the same family/weight request), downloaded once from
  fonts.gstatic.com and committed in `storefront/app/fonts/`, with each family's `OFL-*.txt` beside
  them (copied from github.com/google/fonts `ofl/<family>/OFL.txt`). Inter, Playfair Display and Geist
  Mono are variable files (`100 900`, `400 900`, `100 900`); Poppins is four static files
  (400/500/600/700). Roboto is ONE variable file declared as three faces (400, 500, 700) on purpose:
  the first attempt declared a single `400 700` range and a before/after pixel compare caught it, because
  Google's old setup snapped an in-between request such as 600 to the 700 face while the range renders a
  true 600. Three faces reproduce that.
- Verified: `next build` succeeds; dev server log has no font fetch. Before/after screenshots of my own dev
  server (backend 3600, storefront 3602, seeded `test-shop` published, homepage 1280x900): byte-identical
  PNGs (`cmp`) for the default Inter shop and with `themesettings.fontFamily` set to `poppins`,
  `playfair-display` and `roboto` (4 of 4). Screenshots not committed (size); the page is the hero +
  trust bar + footer of the seed shop.
- Not verified: Geist Mono is not rendered on the homepage, so only its load path (build OK, face present)
  is checked, not its pixels.
- Known difference (honest): the old CSS carried `@font-face` rules for every Google subset
  (latin-ext, cyrillic, vietnamese ...) even though only `latin` was preloaded. Only latin is shipped now, so a
  glyph outside Basic Latin + Latin-1 (e.g. an `ő`) renders in the fallback font. None of the five families
  covers Arabic either way. Add the latin-ext file(s) if a merchant needs them.
- `lib/shop-context.tsx:201` still injects a browser-side `fonts.googleapis.com` stylesheet link for
  non-curated fonts. That is a runtime browser fetch, not a build/dev-server one, so it is not the e2e flake and
  is untouched. The CSP in `next.config.ts` still allows it.
- Playfair uses `adjustFontFallback: "Times New Roman"` (serif metrics); the others use the local default
  (Arial). Fallback metrics matched visually in the screenshots; not measured for CLS.

## (c) Platform admin shop detail: currency of the amount

Premise PARTLY FAILS; adapted, flagging because it touches money display.

- The only money on `admin/app/platform/shops/[shopId]/page.tsx` is the Slider "Test dispatch" fare
  (`:250`, was hardcoded `AED {v.deliveryFee}`). It is not a shop-currency figure: it is Slider's fare for a
  UAE-only courier, and Slider's fare endpoint returns no currency
  (`backend/src/delivery-providers/slider/slider-delivery.provider.ts:118-147`; contrast `CreatedDelivery.currency`).
  `slider-caps.ts:22-26` already states Slider prices in AED. Since A6 a shop's currency is independent of the
  courier, so rendering with the VIEWED SHOP's currency (as the brief says) would mislabel a 12 AED fare as e.g.
  "12.000 KWD" for a KWD shop. That would have been a new money bug, so I did not do it.
- Done instead: `SLIDER_CURRENCY = 'AED'` constant (`slider.constants.ts`), the platform
  `slider-test-dispatch` response now carries `currency: 'AED'`, and the page renders
  `formatMoney(v.deliveryFee, quote.currency)` (2-decimal AED, `199.00 AED` shape, instead of a raw number).
  This is a provider fact, not a defaulted shop value; if Slider ever returns a currency on the fare, use that.
- The viewed shop's currency is NOT added to the platform detail payload: nothing on that page displays it
  (no other amount exists there), so it would be a field without a consumer. Say so if you want it anyway.
- Test: `slider-delivery.e2e-spec.ts` "platform test-dispatch labels fares with Slider's currency ..." runs the
  endpoint for a shop whose currency is KWD and asserts `currency === 'AED'`. Injection proof: returning the bare
  quote fails it (`Expected "AED" Received undefined`).

## (d) D-R7 phone normalisation by shop country

`normalizePhoneToE164(raw, countryCode?)` (`backend/src/common/phone.ts`). `DIAL_CODES` AE 971, SA 966, KW 965,
QA 974, BH 973, OM 968. NULL / undefined / unknown countryCode keeps the legacy +971, documented in the file as
LEGACY (not a default for new countries). Non-971 codes additionally require 8+ digits after the code before a bare
digit string is taken as "already carries the dial code" (8-digit KW/QA/BH/OM locals can start with the dial code's
digits); for 971 the old unconditional rule is kept so AE/NULL output cannot change.

Byte-identical proof (verified): the OLD function's outputs for a 39-entry corpus (05x, 5x, +9715x, 9715x,
009715x, spaces, dashes, parens, 0501234567 variants, +1 numbers, too-short/too-long, 966/965 prefixed, 971971..,
junk, Arabic digits) were captured at origin/main BEFORE the edit and pasted as literals into
`phone.spec.ts` (`LEGACY_CORPUS`), asserted with no countryCode, `null` and `'AE'` (117 cases) plus unknown and
`'constructor'`. Injection: applying the 8-digit rule to 971 too fails 3 corpus cases; ignoring countryCode fails
10 of 137.
