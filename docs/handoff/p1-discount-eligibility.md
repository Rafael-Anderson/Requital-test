# p1-discount-eligibility (F8), branch fix/discount-scoped-eligibility

## Root cause (VERIFIED by reading the code and by the injection proof)
- `DiscountsService.evaluate(discount, { cartSubtotal, productIds?, collectionIds?, customerId? })` rejects a SPECIFIC_PRODUCTS / SPECIFIC_COLLECTIONS code as `not_eligible` when none of the supplied ids match (`discounts.service.ts`, old lines ~327-338).
- The validate endpoints take `productIds` from the client (storefront `PromoCodeField` sent product ids; admin `DraftOrderBuilder` too), so validate said valid.
- Every charge path called `evaluate()` with ONLY `{ cartSubtotal }`: `PublicService.createOrder` (public.service.ts ~1521), `OrdersService.create` (~357), draft attach (`DraftOrdersService.resolveDiscountOrThrow`, ~415, so a scoped code could not even be attached to a draft). `OrdersService.updateItems` (~933) passed `productIds` but never `collectionIds`, so a collection-scoped code was silently dropped on any item edit.
- Nothing ever passed `collectionIds` server-side (the storefront never sent them either), so SPECIFIC_COLLECTIONS could not validate from the storefront either.
- Amount: `computeAmount(discount, cartSubtotal)` ran on the WHOLE cart in validate, checkout and the draft total preview, never on eligible lines. The auto-discount path (`findBestAutoDiscountAmount`) already scoped per line.

## Semantics decision (money; coordinator please note)
A scoped code now discounts ONLY the eligible lines (percent of the eligible subtotal; fixed amount capped at the eligible subtotal), the same as the auto-discount path and the F8 test's expectation ("10% of A only, not of the 150 cart"). Eligible subtotal is on the line's post-auto-discount price (what the customer pays for the line before a code). So a scoped code on a mixed basket charges LESS than the old (never reachable) whole-cart number would have; ALL_PRODUCTS is byte-identical. Minimum purchase is still checked against the WHOLE cart subtotal (unchanged). FREE_SHIPPING unchanged: eligible if any line is in scope, amount 0, delivery fee zeroed.
- Discount amount is now rounded ONCE to the order currency's minor unit (`roundMoney`) inside the shared function, and that rounded figure is what is stored and fed to `computeOrderTotals`. Before, `order.discountAmount` was stored unrounded (e.g. 3.333) and only the total was rounded. Effect: stored discountAmount is a whole minor unit; the total can differ by at most one minor unit from the old unrounded path in half-way cases. Existing KWD/AED specs pass unchanged.

## Fix (VERIFIED)
- New pure `backend/src/discounts/discount-eligibility.ts`: `lineMatchesScope`, `computeDiscountAmount`, `computeEligibility(discount, lines, currency)` -> `{ eligible, eligibleLineIndexes, eligibleSubtotal, discountAmount }`.
- `DiscountsService.evaluate` now takes `{ lines, customerId?, currency?, wholeCartSubtotal? }` and delegates to it. `computeAmount` and `findBestAutoDiscountAmount` use the same primitives (auto discount keeps "ALL_PRODUCTS never applies").
- New `DiscountsService.buildLines(shopId, resolvedItems)`: server prices (from `resolveOrderItems`) plus shop-scoped `productcollection` membership. Callers: `PublicService.createOrder`, `OrdersService.create`, `OrdersService.updateItems`, `DraftOrdersService.resolveDiscountOrThrow` (create/update), both validate endpoints. Client ids are never used for a charge.
- Validate: `ValidateDiscountDto` gains optional `items: [{ productId, variantId?, quantity, giftCardAmount?, priceOverride? }]`. The server prices them with `resolveOrderItems` (so validate == charge). `priceOverride` is honoured only on the admin route and not forwarded on the public one. The old shape (`cartSubtotal` + `productIds`/`collectionIds`) still works for compatibility (eligibility from ids, amount on the whole cart total, exactly as before), but it cannot match the charge on a mixed basket, so storefront `PromoCodeField` and admin `DraftOrderBuilder` now send `items`.
- Admin route `POST /shop/discounts/validate` moved from `DiscountsController` to a new `DiscountValidationController` in `draft-orders/draft-orders.controller.ts` (same URL, same `@Roles('admin')`), because `DiscountsModule` cannot import `ProductsModule` (which imports it; `DiscountsService` also cannot inject the product resolver without a provider cycle).
- Draft order `subtotal/discountAmount/total` preview now comes from the same eligibility function (draft `currency`), so the draft display equals what completion charges.
- `redeem()` (CAS on usageLimit in the order transaction) and the per-customer-limit check are untouched.

## Tests (VERIFIED)
- `backend/test/order-gift-discount-tax.e2e-spec.ts`: F8 `test.failing` -> plain `it`; the characterisation that asserted 400 now asserts 201.
- New `backend/test/discount-eligibility.e2e-spec.ts` (34 tests): 27-cell table {ALL_PRODUCTS, SPECIFIC_PRODUCTS, SPECIFIC_COLLECTIONS} x {PERCENTAGE, FIXED_AMOUNT, FREE_SHIPPING} x {eligible, ineligible, mixed}: public validate == admin validate == storefront order == admin order (discountAmount, total, delivery fee; usage claim once per order; rejection messages identical). Plus auto-discount x code, draft create/preview/complete (+ refusal at attach), order item edit keeps/drops a collection code, scoped usageLimit race (exactly one wins), per-customer limit, cross-tenant (other shop's code `not_found` on public validate, admin validate and checkout; other shop's product id 400).
- New `backend/src/discounts/discount-eligibility.spec.ts` (pure unit).
- Injection proof: (1) charge paths reverted to the old call (`lines: []`, `wholeCartSubtotal: subtotal`): 20 failures, 15 of them "Expected 201, Received 400" (scoped code rejected at checkout), plus the F8 spec and draft/edit/auto/race cells. (2) `computeEligibility` summing ALL lines instead of eligible lines: SPECIFIC_* mixed PERCENTAGE cells, draft, edit, auto and F8 fail with amounts 20/15/13 instead of 10/8 etc. Both restored.

## Found, NOT changed (premise notes)
- Per-customer limit is not enforced at storefront or admin order creation, only at validate (with `customerId`) and draft attach: `createOrder`/`OrdersService.create` call `evaluate` with no `customerId` (the customer row is created after), and `redeem()` has no per-customer check. Pre-existing, left unchanged as briefed. A guest can exceed `usageLimitPerCustomer` at checkout. Worth its own ticket (check inside the order transaction after `findOrCreateForOrder`).
- Minimum purchase for a scoped code is measured on the whole cart, not the eligible subtotal (unchanged; a merchant-policy question).
- `updateItems` / draft attach still do not re-run per-customer limits on edit beyond what `evaluate` already did.

## Deploy
Backend and frontends are compatible in either order: the new backend still accepts the old validate shape, and old frontends keep working (they just keep the whole-cart amount preview for a scoped code until the storefront/admin deploy). Deploy backend first.
