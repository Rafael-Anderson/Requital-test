## VERIFIED vs INFERRED

**VERIFIED (by tests run here):** everything in the code paths: parsers, planner rules, money exactness, tenant scoping, idempotent re-confirm, customer dedupe, no consent/no email, SSRF checks, the queue flow with a stubbed fetch. Backend unit + e2e counts are in the final report.

**INFERRED (cannot be verified from here, no real export was available):**

* **EVERY Salla and Zid column header.** Written from memory of the two dashboards' product export/import templates. None is verified. The tables are `SALLA_SPEC` and `ZID_SPEC`; correcting the mapping after seeing a real export means editing those arrays only. The matcher ignores case, spacing, brackets, BOM, zero-width marks, Arabic diacritics/tatweel and folds alef/yeh variants, and tries every alias.
* **The row shape** assumed for both: one row per product, then extra rows with no product name for variants (option name/value columns) or extra images. A product's own row that has no option values but is followed by variant rows is treated as a parent only.
* **Salla status words** (`ظاهر`, `مخفي`, `sale`, `out`, `hidden`, ...) and the meaning of a blank quantity (taken as "not tracked").
* **Zid bilingual names:** English-named column wins, Arabic is the fallback, a warning is shown when both are present and differ.
* **Weight:** imported only when the file has a weight unit column with kg or g (or Arabic equivalents). No unit column, or lb/oz, leaves the weight NULL with a warning. Chosen over guessing.
* **Header row on line 1.** A file with a title or notes above the header is refused (missing columns), not guessed at.
* An `.xlsx` numeric cell is read as the text Excel stored. A price typed 10.505 is exact; a value Excel keeps in scientific notation (1E3) is rejected by the decimal parser.
* Real behaviour of Salla/Zid CDNs for image copy (redirects, content types) was not exercised against the live internet (no third-party calls were made).

## Money rules (products)

Prices are exact decimal strings. Arabic-Indic digits and the Arabic decimal mark are transliterated as text; `1,234.50` loses its thousands comma only when unambiguous; `12,5`, `150 SAR`, `1e3`, `-5` are rejected with a row-numbered error. A sale price below the price becomes price + compare-at (string comparison, no floats); a sale price that is not lower, or zero, is ignored (warning for the first). Nothing is converted between currencies; the report states the shop currency.

## Customers: the phone rule (decision)

`customer` is unique on `[shopId, phone]` but checkout stores phones RAW (`CustomersService.findOrCreateForOrder` matches the exact string), so `0501234567`, `050 123 4567` and `+971501234567` are three rows today. Import rule:

1. Every phone in the file is normalised to E.164 with the SHOP's `countryCode` (`normalizePhoneToE164`).
2. Every existing customer's stored phone is normalised the same way and the file is matched against that. A match is never duplicated.
3. A matched row keeps its own stored phone (rewriting could collide and would change a registered customer's login). A NEW row is stored as E.164, the form the admin editor writes.
4. Same person twice in the file: first row stands; identical details collapse (`skip`), different name or different non-blank emails make ALL rows of that phone a `conflict` and none is imported.
5. Several existing rows that already normalise to one number: `conflict`, nothing touched.
6. `onExisting=skip` (default) leaves a matched customer alone; `update` fills an EMPTY email and appends an address they do not have. It never overwrites a name or an email (warns instead).

**Known gap (pre-existing, not fixed here):** a customer imported as `+971501234567` who later checks out typing `0501234567` becomes a second row, because checkout still matches the exact string. The fix is normalising in `findOrCreateForOrder` (the CLAUDE.md "phones stored raw" follow-up); it touches the shared checkout path so it was left alone.

**Consent / PDPL:** nothing writes a consent field (the `customer` table has none, asserted in the e2e), `newslettersubscriber` is never touched, no job and no email are queued, a marketing-looking column is ignored with a warning. Messages name the row and the field only; the preview shows the name and a masked phone (`+971•••••••67`), never an email; the audit row holds counts only. Addresses are imported as text (+ area, label) with no `regionId` (the customer picks a region at checkout), and "notes" have nowhere to go, so a Notes column is reported as not imported.

## Collections: rules

Identity: a row with a slug matches the existing slug; a row without matches an existing collection by name (case-insensitive), and two same-named collections make it an error that asks for a slug. A parent is a slug or a name (ambiguous = error); a blank parent leaves an existing collection where it is. Cycles (including a move under its own descendant and self-parent) are errors, walked over the combined existing + file parent map; depth is unlimited and creation order is computed iteratively (3,000-deep chain tested). Confirm re-reads the shop's collections `FOR UPDATE` inside the transaction and re-plans from the bytes. Images are recorded as URLs only (collection images are NOT copied; only product images are).

## SSRF-safe fetch: design and choices

`common/safe-fetch.ts`:

* **https only.** `allowHttp` exists as an explicit option; the importer never sets it (choice: a plain-http fetch can be rewritten in transit, and Salla/Zid/Shopify CDNs are https).
* No userinfo; only the scheme's default port (443). Any `:port` is refused.
* DNS resolved by us (`dns.lookup all`); EVERY address must be public (a name with one private A record is refused); IP literals are checked without any lookup (WHATWG URL canonicalises decimal/hex/octal forms to dotted, tested).
* Refused ranges: 0/8, 10/8, 100.64/10, 127/8, 169.254/16 (incl. metadata), 172.16/12, 192.0.0/24, 192.0.2/24, 192.88.99/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, 224/4, 240/4; IPv6 ::/96 (unspecified, loopback, compat), ::ffff:0:0/96 (every IPv4-mapped form, hex or dotted), 64:ff9b::/96, 100::/64, 2001::/32, 2001:db8::/32, 2002::/16, fc00::/7, fe80::/10, fec0::/10, ff00::/8. **Gotcha found:** Node's `BlockList` treats an IPv4 address as IPv4-mapped IPv6 when checked against v6 rules, so the `::ffff:0:0/96` rule blocked every IPv4 address when both families shared one list; there are two lists now (test caught it).
* **Connects to the validated IP** (`host: ip`, `servername`/`Host` kept), resolves once per hop, so a rebinding resolver cannot swap the target. Redirects are followed manually (cap 3), every hop re-runs the whole pipeline (scheme, port, userinfo, DNS, address). No cookies, no credentials, `Accept-Encoding: identity`, compressed responses refused.
* Caps: 5 MB (declared `Content-Length` and streamed), 10 s total wall time, content-type allowlist (jpeg/png/webp/gif) AND magic-byte sniff (the bytes win over the declared type; SVG/HTML under an image type is refused).
* Queue: `confirm` queues one `import_copy_image` job per image AFTER the import transaction commits, never inside the request. Caps: 10 per product, 500 per import (the preview reports `willQueue` / `overCap`). Idempotency key `imgcopy:<shop>:<product>:<sha256(url)[:32]>` (the job table's UNIQUE key); that key is also the ledger the classifier consults so a re-run does not re-add an image whose row now holds our copy. The job re-checks that the product belongs to the job's shop and still lists the URL, fetches, stores through `StorageService.uploadImage` (resized variants, magic-byte checked again), then updates `productimage.url` and `product.thumbnail` by exact old URL. Non-retryable refusals (blocked, wrong type, 404, too large) complete the job and leave the original URL; retryable ones (timeout, 5xx, network) back off and dead-letter after 3 attempts (visible in Settings > Diagnostics).

### Injection proofs (safe-fetch)

Each weakening applied to `safe-fetch.ts`, spec re-run, then restored (script kept out of the repo). All KILLED (spec fails): userinfo check removed, port check removed, scheme check removed, `every` -> `some`, address check removed, redirect hops unchecked, connect by hostname instead of the validated IP, content-type check, magic-byte check, Content-Length cap, streamed cap, redirect cap, encoding check, timeout, forwarding a Cookie header, and removing each of 13 blocked ranges one at a time (169.254/16, 10/8, 100.64/10, 127/8, 172.16/12, 192.168/16, 0/8, 224/4, ::/96, ::ffff:0:0/96, fc00::/7, fe80::/10, ff00::/8).

### Injection proofs (behaviour)

Each weakening applied, the named spec re-run (unit or e2e), restored. All KILLED: customers matched on the RAW stored phone (3 e2e failures), same-phone-different-name no longer a conflict, `onExisting=skip` ignored (needed a new e2e case: it survived the first time), update overwriting an existing email, a marketing/newsletter insert added to the create path (e2e fails), collections cycle guard off, duplicate-row detection off, ambiguous name guessed, sale-price comparison inverted, required-column check removed, image ledger ignored (re-run re-adds an image), copy job not scoped to the job's shop, `collectionId` not validated against the shop, `.xlsx` accepted on the plain CSV path, per-product copy cap removed, a job queued from the wrong place, zip-bomb output cap removed, encrypted xlsx entries accepted.

## Adversarial checklist for the security review

* [ ] SSRF: any path where a URL from a file reaches a socket without `safeFetchImage`? (Only `ProductImageCopyService.handle` fetches. `grep -rn "safeFetchImage\|https.request" backend/src` should show only safe-fetch + that service.)
* [ ] DNS rebinding / redirect to private / IPv4-mapped / decimal IP forms: tests in `safe-fetch.spec.ts`.
* [ ] Job payload forgery: the handler re-validates `(productId, shopId, url)` against `productimage JOIN product`; cross-shop payload does nothing (e2e).
* [ ] Fetch size/time DoS: caps above; 500 jobs/import max; `maxAttempts` 3.
* [ ] xlsx: zip bomb (declared size cap + `maxOutputLength`), encrypted entries, zip64, truncated archive, entity expansion (fixed table, no DTD). Formulas never evaluated; cells starting `= + - @` are data.
* [ ] Tenant isolation: every query takes `ctx.shopId`; `collectionId`/`outletId` validated on preview AND confirm; parent refs only resolve inside the shop; customers matched only inside the shop; image jobs scoped.
* [ ] Idempotency: product re-confirm (skip), image ledger, collections re-confirm, customers re-confirm: e2e.
* [ ] No PII in logs/audit: audit rows are counts; the copy handler logs reason + host only.
* [ ] Customer concurrency: no lock on the customer set; an identical-spelling race ends in the unique key (409 "run the preview again"); a different-spelling race can still duplicate (same pre-existing checkout gap).
* [ ] Nested pool rule / outlet scoping guardrails run clean (see report).
