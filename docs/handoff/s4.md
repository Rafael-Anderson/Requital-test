## Premise corrections and findings (VERIFIED unless marked)

1. **Phones are stored raw** (`customer` is unique on `[shopId, phone]`, `customers.service.ts` `findOrCreateForOrder`). Unchanged. Merge is the tool for "0501234567" vs "+971501234567" duplicates; a merged phone keeps resolving to the primary at checkout (`customermerge.duplicatePhone`). Customer REGISTRATION under a merged phone is not alias-aware (it would create a fresh customer). Not fixed.
2. **`GET /customers` and the existing customers export sum `order.total` across currencies** (known gap). Segments use `SUM` per currency (`currency` is a required field of the `lifetimeSpend` rule). The new `customer-segment` export prints spend per currency.
3. **The newsletter widget is a separate subscription list** (`newslettersubscriber`, keyed by email). It is NOT copied into consent. The consent card shows it read-only; segments can filter on it (`newsletterSubscriber`) separately from `consent`. Nothing double-stores.
4. **Nothing in the backend sends marketing mail gated on consent.** Consent is recorded and filterable but no sender consults it (abandoned-cart recovery is transactional). Wiring a sender to `customerconsent` is the follow-up that makes consent enforceable.
5. **Gift card balances are NOT restored when an order is cancelled** (`OrdersService.cancel` never touched `giftcard`). Store credit IS (idempotent reversal). Left as is, flagged.
6. **VERIFIED with curl (RFC 6265 path matching, not a real browser): customer session cookies never reach the backend through the storefront's `/api` proxy.** Backend on :3124, storefront dev on :3324: `POST :3324/api/public/test-shop/auth/register` -> 201 with `Path=/public/test-shop` cookies; replaying the jar, `GET :3324/api/public/test-shop/account/profile` -> **401**, `GET :3124/public/test-shop/account/profile` -> 200. `customerAccessPath` (`customer-auth.constants.ts`) predates `apiBase() === "/api"` (custom-domain Phase 5) and `custom-domain-cookie.e2e-spec.ts` only tests the backend directly. So a real shopper cannot use their account, wishlist or store credit through the proxy until the cookie Path is fixed. The backend half of store credit is fully tested; the end-to-end browser path is blocked by this. Outside S4's scope (auth); a follow-up task card was queued.
7. A logged-in customer's POST `/public/:slug/orders` carries the session cookie, so the global customer CSRF middleware requires `X-CSRF-Token` on it. The storefront `createOrder` therefore goes through `authedFetch` when `useStoreCredit` is set (guest checkout is unchanged). Tested: a cookie without the CSRF header gets 403 and spends nothing.

## Design decisions to review

- **Roles** (evidence: `CustomersController` comment, customers are shop-wide with no outlet boundary): everything here is admin write, admin + viewer read; `branch` and `order_manager` get 403 on every new endpoint (role-matrix test in each spec). Store credit especially: a branch user could otherwise mint credit spendable at every outlet.
- **Consent**: unknown is the ABSENCE of a `customerconsent` row. Writers: admin (grant needs a "how obtained" note) and the customer's own account toggle (wording and version are the server's). Imports, guest checkout and orders never write it, so S3's import leaves consent NULL by construction. Deleting the account withdraws granted channels (event source `account_deletion`).
- **PDPL**: customer export now includes `marketingConsent` and `storeCredit`. Staff notes and tags are NOT in the customer-facing export (decision for the owner: notes are "never shown to customers"; GDPR-style access rights may argue otherwise). Anonymise deletes notes, withdraws consent, replaces staff-typed ledger reasons with `[removed]` (the ledger itself is kept), and blanks merge-record contact snapshots.
- **Store credit order wiring**: `order.storeCreditAmount` (like `giftCardAmount`, total unchanged). Payable = total - gift card - store credit; remainder 0 marks the order paid and creates no gateway session. The order belongs to the logged-in account, not to the customer matched by the typed phone. Admin-created orders and draft orders cannot spend credit (by design).
- **Return refund to store credit**: built (cheap): `refundTo: 'store_credit'`. The store-credit-paid share always returns to credit by the same proportional rule as gift cards (`orderreturn.storeCreditRefundAmount`).
- **Merge is NOT reversible.** Typed `MERGE` in the UI and `confirm: "MERGE"` required by the API. A duplicate with a storefront account (or a deleted one) is refused; merge the other way round. Ledger rows are re-pointed (the only UPDATE the ledger ever sees), never copied.
- **Lock order**: checkout/admin adjust/return credit lock the customer row first; a merge locks customers by ascending id then re-points orders. Cancel/return take the order row before the customer, so a merge racing a cancel/return of the same customer can deadlock; InnoDB kills one side, the merge retries 3 times, then answers 409. Rare and safe (full rollback).
