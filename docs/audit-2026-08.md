Real, actionable items surfaced by this sweep, roughly ranked:

6. **No observability**: no health endpoint, no structured logging, no error tracking (§1.7).

7. **`next@16.2.10` had multiple high-severity CVEs in both frontends — FIXED same-day (§1.8)**:

8. **Upload MIME validation trusts the browser's `Content-Type`, no magic-byte sniffing**

9. **JSON-LD, Twitter cards, canonical URLs, and custom 404/500 pages are all missing** from

10. **Cookie consent banner enforces nothing** (§1.6) — moot today since there's no tracking

## 1.1 Auth lifecycle

> **Update (2026-08-04, later same session):** the rate-limiting finding below is FIXED —
> see `4b5fa94`. Password reset/email-verification/lockout findings are unchanged; not
> addressed this session.

**Password reset / forgot-password**: EXISTS — full stack present.
- Token model: `authtoken` (`prisma/schema.prisma:1808-1819`), shared table with a `purpose`
  discriminator (`'password_reset'` | `'email_verification'`), hashed at rest (`tokenHash`),
  single-use via `usedAt` CAS.
- `POST /auth/forgot-password` / `POST /auth/reset-password`
  (`src/auth/auth.controller.ts:58-68`) → `AuthService.forgotPassword`/`resetPassword`
  (`src/auth/auth.service.ts:449-514`). 30-minute TTL. Enumeration-safe — identical
  `{success:true}` response whether or not the email exists (`:453-457`). Reset revokes all
  outstanding refresh tokens (`:507-511`).
- Email sent via `sendEmail()` (`src/common/email.ts`), plain text + auto-derived HTML.
- Admin UI: `admin/app/forgot-password/page.tsx`, `admin/app/reset-password/page.tsx` — both
  real pages, not stubs.
- **Flag for the human reviewer**: `isDev` (`NODE_ENV !== 'production'`) echoes the raw reset
  link back in the API response body as `devResetLink` (`auth.service.ts:39-46,476`),
  explicitly commented as a dev-only escape hatch. Worth confirming `NODE_ENV=production` is
  actually set in every real deployment.

**Email verification on signup**: PARTIAL — token, send, and verify endpoint all exist, but
verification gates almost nothing.
- `authtoken` (purpose `email_verification`), sent on signup and via
  `POST /auth/resend-verification` (`auth.service.ts:545-558,584-606`, 24h TTL).
- `POST /auth/verify-email` → `AuthService.verifyEmail` (`:516-543`), single-use CAS.
- **What's missing**: `emailVerified` is checked in exactly one place app-wide —
  `changePassword` (`auth.service.ts:425`). `login()` (`:117-130`) has **no** `emailVerified`
  check — an unverified account logs in with full access to every other endpoint. Verification
  is effectively decorative outside the change-password flow, not "blocks publishing the shop"
  as a conservative default would suggest.

**Account lockout / brute-force protection on login**: MISSING.
- `AuthService.login` does one `bcrypt.compare` and throws on failure — no attempt counter, no
  `lockedUntil`/`failedAttempts` column on `user` (`schema.prisma:1755-1782`), no in-memory
  tracking. Same for `customer-auth`. Zero matches for
  `lockout|failedAttempt|maxAttempts|lockedUntil|LoginAttempt|isLocked` anywhere in `src/`.

**Rate limiting**: PARTIAL at audit time — **FIXED same-day, see `4b5fa94`.** Original finding,
left as written for the record:
- Reference mechanism: `notify-subscriptions.service.ts:7,55-67` — 3/hour, scoped per
  `(shopId, email)`, plain count-then-insert (explicitly commented as an accepted race,
  `// ponytail: soft rate limit`).
- No `@nestjs/throttler` (or any throttler) in `package.json`, no `ThrottleModule`/`@Throttle`
  anywhere.
- Confirmed **absent** on: `/auth/login`, `/auth/signup`, `/auth/forgot-password`,
  `/auth/reset-password`, all `customer-auth` equivalents, and every public storefront POST
  endpoint (order creation, cart capture, geocode proxy). No per-IP limiting exists anywhere.

Now: `@nestjs/throttler` applies a 100/min/IP global default plus 5/min/IP on every listed
auth endpoint and 20-30/min on the listed public POSTs (`ThrottlerGuard` registered first in
the guard chain, `app.module.ts`/`auth.module.ts`). Verified live via curl (5 attempts allowed,
6th and 7th rejected with 429) and with a dedicated e2e regression test
(`test/rate-limiting.e2e-spec.ts`) that deliberately bypasses the test-mode `skipIf` for its
own requests to prove the wiring holds outside Jest. Note: this is IP-based throttling, not
account-lockout tracking — a distributed attacker using many IPs against one account is not
covered by this fix (that would be the account-lockout item, still open above).

**Session handling**: EXISTS — staff and customer auth are structurally parallel, not one
weaker than the other.
- Access token: 15 minutes (`auth.service.ts:30`, `auth.module.ts:14,18-21`).
- Refresh tokens: staff auth has its **own** full rotation-with-reuse-detection stack —
  `refreshtoken` model (`schema.prisma:1790-1802`), 30-day TTL, CAS single-use rotation with
  whole-family revocation on reuse (`auth.service.ts:137-180`). CLAUDE.md's framing (this
  pattern belongs to `customer-auth`) undersells it — staff auth independently implements the
  same discipline, not a lesser one.
- Logout: real server-side revocation, not just client-side deletion — `AuthService.logout`
  revokes the entire refresh-token family (`:186-197`). Caveat: the 15-minute access token
  itself has no denylist, so an already-issued access token stays valid until its own natural
  expiry after logout — "session-family revocation," not "immediate token invalidation."

**Password hashing**: EXISTS — `bcryptjs`, cost factor `10`
(`auth.service.ts:29`, `customer-auth.service.ts:21`).

## 1.2 Background work & scheduling

**Abandoned cart recovery**: EXISTS, cron-driven. `@Cron(CronExpression.EVERY_10_MINUTES)` on
`AbandonedCartsService.sendDueRecoveryEmails` (`abandoned-carts.service.ts:144-160`), registered
via `ScheduleModule.forRoot()` (`app.module.ts:45-48`). CAS-claimed per-shop send.

**Low-stock alerts**: EXISTS, as a daily digest, not real-time per-item.
`LowStockDigestService` (`products/low-stock-digest.service.ts`),
`@Cron(CronExpression.EVERY_DAY_AT_8AM)`, per-shop opt-in, CAS-guarded via
`lowStockDigestLastSentAt` (once/day/shop). Live-queries current stock rather than a persisted
event log.

**Back-in-stock notifications**: confirmed exactly as CLAUDE.md describes — synchronous
fire-and-forget, `.catch()`-guarded, never awaited, no queue involved. Three real callers:
`orders.service.ts:1097-1099` (cancellation restock), `products.service.ts:1073-1076,1081-1086`
(manual adjust), `products.service.ts:1288-1291` (outlet transfer). CSV import and
scan-to-stock confirmed still unwired (matches the documented scope cut).

**Job queue / worker infrastructure**: MISSING, definitively. No `bullmq`, `bull`, `agenda`, or
`node-cron` in `package.json`. Only `@nestjs/schedule` exists, used solely for the two `@Cron`
jobs above. No hand-rolled polling loop anywhere in `src/`.

**Slow synchronous work in the request path**:
- **Order confirmation email + WhatsApp — was awaited inline, blocking the HTTP response —
  MITIGATED same-day, see `069caea`.** At audit time, `PublicService.createOrder` (storefront
  checkout) did `await this.orderNotificationsService.notifyOrderConfirmed(...)`
  (`public.service.ts:991`) after the DB transaction commits, before the response returns; same
  in `orders.service.ts:407-410,533-539` for admin-created/status-updated orders — a
  `Promise.all` of a real email send (Resend) and WhatsApp send (Meta Cloud API), genuinely slow
  external HTTP calls sitting on the checkout critical path. All four call sites are now
  fire-and-forget (`.catch()`-guarded, never awaited), matching the notify-subscriptions
  pattern this finding originally contrasted against. This is the cheap mitigation only — no
  retries, no dead-letter path, no delivery guarantee if the process crashes mid-flight; that's
  still Phase 5's job.
- **OCR (Tesseract) — awaited inline.** `ScanService.preview`
  (`scan.service.ts:27`) awaits `tesseract.js` recognition synchronously inside
  `POST /scan/preview`.
- **Geocoding — awaited inline, but low-frequency by design.** Nominatim proxy calls are
  manually-triggered (map click/pin-drag) `GET` routes, not on the checkout path; the
  free-tier-limit justification is explicit in code (`outlets.service.ts:173-175`).
- **CSV import/export — awaited inline**, no background job for `products`/`ingredients`
  import-confirm.
- **Invoice generation — inline, but cheap.** Plain HTML string templating (no PDF library, no
  headless browser), so despite being synchronous this isn't actually slow.

## 1.3 File storage

**Storage backend**: EXISTS, local disk — and explicitly acknowledged in-code as a
limitation. `common/image-upload.config.ts:5-11` — `UPLOAD_ROOT = join(process.cwd(),
'uploads')` via multer's `diskStorage`, carrying its own comment: *"ponytail: local disk
storage — fine for a single dev/staging instance, does not survive container redeploys or
horizontal scaling."* `main.ts:23` serves it back via `app.useStaticAssets(...)` from the
same directory. **Implication**: any deploy without a shared/persistent volume across
instances will lose or 404 on images after a redeploy or when scaled horizontally — a second
instance won't see a sibling's uploads. No S3/Cloudinary/GCS code path exists anywhere.

**Where uploads go**: all routed through one shared factory, `createImageUploadOptions(subdir)`
(`common/image-upload.config.ts:23-55`), parameterized only by feature subdirectory — products,
categories, collections, ingredients, theme (including slideshow banners — no dedicated
banner-upload endpoint, they reuse the theme uploader), bio-links, shop, seo, scan-to-stock
photos. CSV imports use a separate, memory-only config (`common/csv-upload.config.ts`,
`multer.memoryStorage()`) — parsed once, never written to disk.

**Upload validation**:
- **Size cap: EXISTS** — 5 MB for both images and CSVs.
- **Extension/MIME whitelist: PARTIAL — MIME only, browser-supplied, not sniffed.** The
  `fileFilter` checks `file.mimetype`, which multer populates directly from the client's
  `Content-Type` header — not real magic-byte content sniffing (no `file-type` or equivalent
  library anywhere). **A file with a spoofed `Content-Type: image/png` and arbitrary bytes
  (e.g. an HTML/SVG-with-script polyglot) would pass the filter, be written to disk, and get
  served back as static content from the same origin** — a real gap given `/uploads/` is
  served as public static content with no further processing. CSV upload is extension-based by
  design and never re-served, so lower risk there.
- **Path traversal on filename: MITIGATED.** Saved filename is `randomUUID() + extname(original)`
  — only the extension is taken from client input, the base name is always server-generated.
  Blocks `../../`-style traversal and collision/overwrite.

**Image resizing/optimization**: MISSING. No `sharp`/`jimp`/`image-size`/resize library in
`package.json`. Originals are stored and served exactly as uploaded — no thumbnailing, no
format conversion, no dimension cap beyond the 5 MB byte limit.

**Per-shop storage scoping**: MISSING at the filesystem level — isolation is DB-row-only.
Subdirectories are per-**feature**, not per-**shop**, and filenames are bare `randomUUID()`
with no shopId prefix anywhere in the path — every shop's product images sit together under
the same `uploads/products/` directory, distinguished only by an unguessable UUID filename.
Collision is astronomically unlikely and URLs aren't enumerable, so this isn't an active
exploit path today, but there's genuinely no tenant boundary at the filesystem layer — nothing
but the DB row pointing to a given URL enforces which shop "owns" a file, and `/uploads/` is
public static content with no auth check on read.

## 1.6 Cookie consent enforcement

**Finding: the banner gates nothing — confirmed, not assumed.**

`CookieConsentBanner.tsx` is a real, working, non-blocking bottom bar that persists a genuine
per-shop choice to `localStorage`, and its own comment states the ground truth directly:
*"no analytics wiring yet, this only persists the choice."* Tracing every reader of the stored
consent value across the entire storefront turned up exactly three hits: the component itself,
its own test, and its mount point (which just renders `<CookieConsentBanner />` with no
consumer reading the stored value back). A separate search across all of `storefront/` and
`admin/` for any analytics/tracking SDK or script (`gtag`, `fbq`, `googletagmanager`,
`analytics`, `pixel`, Segment/Mixpanel/Hotjar/Clarity/PostHog/Amplitude in either
`package.json`) found **none** — no Google Analytics, Meta Pixel, or any other third-party
tracking script exists anywhere in this codebase today. The two `dangerouslySetInnerHTML`
usages found in the whole storefront (`ProductDetailClient.tsx`, policy page) both render
sanitized merchant rich-text content, not scripts.

**Conclusion**: this isn't a bug in the banner — it's a compliance-shaped UI component with
nothing behind it to gate yet, because there's no tracking in the app at all. Worth stating
plainly per the original brief: a banner that gates nothing is not itself a compliance
violation (nothing is being tracked without consent), but it does mean the banner currently
provides no actual protection — only a preference log — and would need real wiring the moment
any analytics/tracking script is added.

**No missing index was found on any of the three tables the brief specifically named**
(`order`, `auditlog`/general log tables, `stockmovement`) — all three already declare the
`[shopId, createdAt]` composite by name, suggesting this was already a deliberately maintained
concern rather than an oversight. `customer` is the one plausible gap worth a follow-up ticket.

**N+1 query patterns**: checked the four named services plus a broader sweep; **no N+1 found
in any list/reporting endpoint** — `dashboard.service.ts` (top-products), `products.service.ts`
(`findAll`, `resolveOrderItems`), `orders.service.ts`, `customers.service.ts`, and every
`reports.service.ts` query all batch their per-row lookups into a single `findMany({where:{id:
{in:[...]}}})` or one raw `$queryRaw` joined in-memory via a `Map` — none loop-and-query.

**One genuine N+1 was found, outside the four named files**: the CSV bulk product-import flow
in `products.service.ts` (`confirmImport`/`previewImport`, ~lines 2285-2295 and 2349-2366).
Inside the loop over parsed CSV rows, each row does its own `findFirst` to decide
create-vs-update by SKU/name, and the nested loop over each row's variant lines does the same
per variant — one DB round-trip per CSV row and again per variant row, rather than one batched
`findMany({where:{sku:{in:[...]}}})` up front. A 500-row CSV with variants issues 500-1000+
sequential queries during preview/confirm. Real, and a good candidate for a future fix
(batch-resolve all SKUs/names once before the loop), though it's a bulk-import action rather
than a request-latency-sensitive list endpoint.

**Missing shopId filters on tenant-owned models**: **none found**, checked broadly (not just
the four named services) via a systematic grep for every bare-`id` `findUnique`/`update`/
`delete` across all `*.service.ts`, each traced back to confirm scoping. The codebase
consistently follows a "resolve-with-shopId-check first, mutate-by-id second" convention via
private `assert*BelongsToShop`/`findRaw` helpers — this looks like a deliberately enforced
pattern, not incidental. The handful of bare-`id` lookups with no shopId in their own query
(`notify-subscriptions.service.ts`, `bio-links.service.ts`'s public click-redirect) are the
two intentionally-public, unauthenticated endpoints already covered in the 1.9 sweep above —
not a new finding, just cross-confirmed from the schema/query side.

## 1.4 Checkout & inventory integrity

**Guest checkout**: EXISTS, genuinely end-to-end. `POST /public/:shopSlug/orders` is
`@Public()`; `CreatePublicOrderDto` has no password field;
`CustomersService.findOrCreateForOrder` creates/updates a `customer` row without ever setting
`passwordHash` (nullable by design — "null passwordHash = guest, never registered",
`schema.prisma:1197`). Order tracking post-purchase also needs no login (token-based lookup).
An optional password-protected account exists for repeat customers but is never required.

**Stock reservation / concurrency window**: PARTIAL — CLAUDE.md's description (decrement only
at pending→confirmed via CAS) turns out to be accurate for only one of two order-creation
paths; the customer-facing one behaves differently and better than documented.
- **Storefront (guest/customer) orders reserve stock immediately at creation**, not at confirm.
  Inside `PublicService.createOrder`'s transaction (`public.service.ts:776,832-851`), each
  tracked item runs a CAS `updateMany({ where: { ..., stockQuantity: { gte: quantity } },
  data: { decrement } })`; a loser gets `result.count === 0` → `ConflictException`, and order
  creation fails outright. `orders/constants.ts:43-46` names this explicitly:
  `IMMEDIATE_STOCK_RESERVATION_CHANNELS = ['storefront', 'draft_order']`, and the
  pending→confirmed transition in `orders.service.ts:499-512` explicitly *skips* decrementing
  again for these channels to avoid double-counting. **Net effect: there is no realistic
  oversell window on the storefront checkout path** — the DB row lock on the CAS update
  serializes concurrent buyers of the last unit.
- **Admin/manual orders are the ones that actually match the documented pattern**, and this is
  where a real gap lives: `OrdersService.create` for non-immediate-reservation channels
  creates a `pending` order with **zero stock held**. Two admin operators could both create
  orders against the last unit while both stay `pending` — nothing blocks it. The
  pending→confirmed CAS (`updateStatus`) correctly lets only one *status transition* win, but
  `adjustStockForOrder` (`orders.service.ts:1025-1139`) has **no stock-sufficiency guard at
  all** — it's an unconditional `upsert`/`increment`/`decrement`, so confirming the second
  order can silently drive stock negative with no error surfaced anywhere. This is real and
  reproducible, but scoped to admin/staff-entered orders only (not customer-facing), which
  meaningfully limits blast radius (requires two staff members racing each other, not two
  anonymous customers).
- `continueSellingOutOfStock` products intentionally skip the floor guard entirely (allowed to
  go negative) via `upsert`+`decrement` — documented, deliberate behavior, not a bug.

**COD (cash on delivery)**: EXISTS, genuinely payment-provider-free.
`cash_on_delivery`/`cash_on_pickup` are real `PAYMENT_METHODS` values
(`public/dto/create-public-order.dto.ts:60-71`); for these (and `card_on_delivery`/
`card_on_pickup`), `gatewayName` resolves to `null` and the checkout-session/provider call is
skipped entirely (`public.service.ts:999-1026`) — the order is created directly with
`checkoutUrl: null`.

**Tax / VAT**: EXISTS, with one explicit product decision worth knowing.
- Per-shop `taxInclusive` toggle drives inclusive-vs-exclusive calculation
  (`public/order-pricing.ts:1-20`), shared by both storefront checkout and admin order-item
  edits.
- **Tax is explicitly not applied to the delivery fee** — stated outright in the code comment
  ("a common default... revisit if a merchant needs delivery fees taxed too"). Delivery fee is
  added to `total` after tax is computed on `subtotal` alone.
- Discount applied before tax; gift card applied after total, as a payment credit.

**Invoice numbering**: EXISTS, confirmed atomic/gapless as currently implemented — verified
against the actual raw SQL, not just the CLAUDE.md description.
- `nextInvoiceNumber` (`invoices.service.ts:174-197`) uses
  `INSERT ... VALUES (..., LAST_INSERT_ID(1)) ON DUPLICATE KEY UPDATE lastNumber =
  LAST_INSERT_ID(lastNumber + 1)` — confirmed the previously-buggy seed branch fix is in place
  (plain-insert path also wraps in `LAST_INSERT_ID(1)`, not just the update branch).
- Runs inside the same `$transaction` as `invoice.create`; `generateForOrder` separately
  catches `P2002`/`P2034` on the `(orderId, type)` unique constraint for same-order concurrent
  double-generation.
- **Test coverage gap**: `test/invoices.e2e-spec.ts` has a real concurrent-HTTP test for two
  simultaneous generate calls on the *same* order (proves P2002 idempotency), and a sequencing
  test proving per-shop counter independence — but no test exercises genuinely parallel
  invoice generation for *different* orders on the *same* shop simultaneously, which is the
  scenario that actually stresses the counter row-lock's serialization rather than the
  idempotency catch. The atomicity is real (guaranteed by the raw SQL's row lock), but it's
  currently unproven by a true concurrency test — only reasoned about from the SQL itself.

## 1.5 SEO / storefront meta

**sitemap.xml**: EXISTS, dynamic, per-shop, but incomplete. Global
`storefront/app/sitemap.xml/route.ts` lists only published shops' home URLs. Per-shop
`storefront/app/[shop]/sitemap.xml/route.ts` includes the shop home URL, category filter URLs,
and product URLs — but **not collection pages or policy pages**.

**robots.txt**: EXISTS, dynamic (Next `MetadataRoute.Robots` convention), but global only —
one blanket `allow: "/"` for every shop, not per-shop. Deliberate per an in-code comment
(crawlers reach per-shop sitemaps from the one global entry point).

**JSON-LD structured data**: MISSING entirely. Zero matches for `application/ld+json` anywhere
in `storefront/`. No Product schema on the PDP, no Organization schema on the homepage, no
CollectionPage/BreadcrumbList anywhere.

**Open Graph + Twitter card meta**: PARTIAL. OpenGraph is set on 3 pages via
`lib/seo.ts` (shop-level default inherited by every `[shop]` page, PDP override, bio-page
override) — but **no page anywhere sets Twitter card meta** (zero matches for `twitter:`).
Collection pages and policy pages have no page-specific metadata at all (inherit the shop
default only).

**Canonical URLs**: MISSING. Zero matches for `alternates: { canonical` or
`<link rel="canonical"` anywhere. Notably absent on the PDP, which has both an id-route and a
slug-route for the same product — exactly the duplicate-content scenario a canonical tag
exists to prevent.

**404 and 500 pages**: MISSING — falls back to Next.js's generic defaults. No
`not-found.tsx`, `error.tsx`, or `global-error.tsx` exists anywhere in `storefront/app`. Some
individual pages render their own inline "not found" UI for known cases (e.g. an unpublished
policy page), but that's page-level conditional rendering, not the framework-level convention —
an actual unhandled render error or an unmatched route still hits Next's unbranded default.

## 1.9 Cross-shop isolation — full endpoint sweep

Exhaustive over all 41 backend controllers and every route handler in them (no sampling).
Global mechanism: `AuthGuard` + `RolesGuard` registered as `APP_GUARD` in `AuthModule` — every
route is guarded by default; `@Public()` opts out; `@Roles(...)` further restricts. Outlet
scoping goes through `resolveOutletFilter`; a separate `BranchRolesService` permission layer
can further restrict (never expand) a user at a specific outlet.

*(Full per-endpoint tables — Method / Path / Auth / Role / ShopId scoping mechanism / file:line
— for all 41 controllers were produced by three parallel research passes and are long; they're
available in the session transcript. This section keeps the actionable output: the consolidated
CONCERNS list, most severe first, deduplicated across all three passes.)*

### CONCERNS (consolidated, most severe first)

> **Update (2026-08-04, same day, later in this session): items 1 and 2 below are FIXED.**
> Both were closed in Phase 1.5 of this session, immediately after this audit was written —
> see `4ce5ef9` (item 1) and `b445b69` (item 2). The analysis below is left exactly as
> originally written (it's what a snapshot audit is for), but a reader landing on this
> document should not treat these two as live/open — they aren't. A repo-wide grep-based
> re-verification confirmed no other instance of either bug class remains unaddressed;
> see `tools/check-outlet-scoping.js` and its own commit for the full accounting (2 genuine
> sites found and fixed, 21 other `outletId`-taking methods individually confirmed safe and
> allowlisted with reasoning, 0 unresolved at HEAD).

1. **FIXED (`4ce5ef9`) — `ingredients.service.ts` `confirmImportIngredients` — `outletId` (from query) is used
   directly for `outletingredientstock` upsert and `stockmovement` writes with no verification
   it belongs to `ctx.shopId`.** Admin-only route, so exploitation requires an admin from Shop
   A guessing/knowing an outlet id belonging to Shop B — but if they do, this is a genuine
   cross-tenant **write** (stock levels + a stock-movement audit row created against a foreign
   shop's outlet), not just a read leak. Contrast with `findAll`/`findOne` in the same service,
   which correctly run `outletId` through `resolveOutletFilter`. **Recommended fix**: add the
   same `outlet.findFirst({id: outletId, shopId: ctx.shopId})` check this method's siblings
   already have, before the upsert.
   The identical bug was independently present in `products.service.ts confirmImportProducts`
   too (not flagged by this audit's own `products.controller.ts` review, which checked
   shopId/SKU matching but not this specific outletId-for-stock-write path) — found via a
   dedicated grep sweep after fixing item 1, and fixed the same way in the same commit.

2. **FIXED (`b445b69`) — `invoices.service.ts` `findOne(ctx, id)` and `GET /invoices/:id/pdf` — shop-scoped only,
   no outlet dimension for `branch` role.** Unlike `generateForOrder`/`findAllForOrder` (which
   route through `ordersService.findOne`, itself outlet-scoped via `resolveOutletFilter`), a
   direct invoice-id lookup only checks `{id, shopId}`. A `branch` user who knows/enumerates an
   invoice id belonging to a **different outlet in the same shop** can read that invoice/PDF,
   even though they're blocked from the underlying order via `/orders/:id`. Same-tenant,
   cross-outlet only — not cross-shop. **Recommended fix**: thread the invoice's `orderId`
   through `ordersService.findOne(ctx, orderId)` (or an equivalent outlet check) before serving
   `findOne`/`:id/pdf`, matching the pattern the other two methods already use.

3. **`GET /dashboard/*` (summary, revenue-daily, top-products) has no `@Roles` restriction at
   all** — any authenticated staff role, including `order_manager` (documented elsewhere as
   scoped to "Orders/Draft Orders domain only — no pricing, catalog, or settings access"), can
   pull shop-wide revenue/AOV/top-products analytics. Every query is still correctly
   `shopId`-scoped — **this is not a cross-tenant leak**, it's a same-tenant privilege-scope
   question. No comment in the code states intent either way (contrast with `customers`/
   `audit-log` controllers, both explicitly `admin`/`viewer`-only with a documented reason).
   Flagging for a product decision, not asserting it's a bug: should `order_manager` see shop
   financials?

4. **`GET /public/bio-links/:id/click` fetches by bare numeric id with no shopId scoping in the
   query at all** (`biolink.findUnique({where:{id}})`). Low real-world severity — it only
   302-redirects to an already-public storefront URL and increments a click counter, no PII/
   admin data in the response — but it does mean bio-link ids are enumerable platform-wide with
   no rate limit, allowing click-count inflation/observation across any shop's links.
   Recommended: not urgent, but a candidate for basic rate-limiting if click-fraud ever
   matters to the business.

5. **`POST /public/:shopSlug/auth/logout` and `.../auth/reset-password` never use their own
   `:shopSlug` param** — both operate purely on the opaque token hash, which genuinely is the
   real credential (30+ byte generated token), so this is assessed as **not exploitable**: no
   cross-shop read/write is possible by varying `:shopSlug` against a token that resolves to a
   different shop's row. Flagged only as an inconsistency versus sibling methods
   (`register`/`login`/`refresh`/`forgot-password`, which do resolve and use the shop) —
   recommend a code comment (or the redundant check for defense-in-depth) so a future refactor
   doesn't assume `shopSlug` is load-bearing there.

6. **Legacy platform-wide Stripe webhook (`POST /payments/webhook/stripe`, no `:shopId` in
   path) has no post-resolution `order.shopId` cross-check**, unlike its `:shopId`-suffixed
   sibling route (which explicitly verifies `order.shopId !== shopId` after parsing). Not
   currently exploitable — the event still requires a valid platform-secret signature, and
   `orderId` is an internal id round-tripped through the customer's own gateway session — but
   there's no defense-in-depth check here the way there is on the newer route. Worth confirming
   this legacy route is only ever used with the one platform-wide Stripe account, and
   considering adding the same cross-check for consistency.

7. **`products.service.ts` `resolveOrderItems`'s variant lookup isn't itself `shopId`-filtered**
   — safety currently comes from a chained invariant (`found.productId !== product.id`, where
   `product` was already shop-verified), not a direct filter. Correct today; fragile to a
   future refactor that reorders the checks. Recommended defense-in-depth: add an explicit
   `shopId` join/filter, not because it's exploitable now.

**Everything else reviewed across all 41 controllers** (auth, abandoned-carts, affiliate,
audit-log, bio-links, branch-roles, categories, collections, customer-account,
customer-auth, customers, delivery-zones, discounts, draft-orders, external-deliveries,
gift-cards, ingredient-categories, orders, outlets, payments, payment-settings, policy-pages,
products, all 5 `public/` controllers, reports, returns, scan, search, seo, shop,
storefront-search, theme, whatsapp-settings) consistently re-derives `shopId`/outlet from an
authenticated `TenantContext`/`CustomerContext` or a resolved `:shopSlug`/opaque token — never
trusts a client-supplied shopId/outletId without independent verification. **The historical
outlet spread-overwrite bug** (`{ id, shopId, ...(role==='branch' && { id: ctx.outletId }) }`
silently letting the spread overwrite `id` last) was specifically checked for across every
outlet-touching endpoint and **was not found anywhere** — `outlets.service.ts` and
`orders.service.ts`'s `findOne` methods both use the corrected explicit-check-first shape, and
no sibling endpoint reproduces the vulnerable pattern.
